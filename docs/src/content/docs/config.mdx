Holocron looks for `holocron.config.ts` (preferred) or `holocron.config.json` in the current working directory (or the path passed to `--cwd`). TypeScript configs import `defineConfig` and the ready-made presets from `@theholocron/cli`; see [Presets](#presets).

## Presets

A preset is a ready-made config fragment: spread it into `defineConfig()`. They ship with the CLI, from one entry point, `@theholocron/cli/presets` (they used to be the separate `@theholocron/holocron-config` package, which is deprecated).

```ts
import { defineConfig } from "@theholocron/cli";
import { nodePreset } from "@theholocron/cli/presets";

export default defineConfig({
  ...nodePreset(),
  name: "my-project",
});
```

| Export           | For                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| `nodePreset`     | A Node.js repository.                                                                           |
| `docsPreset`     | A TypeScript library that also publishes a docs site.                                           |
| `docsSitePreset` | A docs-only site with no TypeScript source to check.                                            |
| `nextjsPreset`   | A single-package Next.js app: Vercel deploy, Lighthouse, Storybook and interaction tests.       |
| `reactPreset`    | A single-package React/Vite app: Storybook, interaction tests, and a Knip and Lighthouse audit. |
| `monorepoPreset` | Wraps another preset for a monorepo root: `monorepoPreset(nextjsPreset())`.                     |

The presets list tasks by their flat ids (see [Task vocabulary](#task-vocabulary)): `lint:code`, `lint:editorconfig`, `lint:markdown`, `format`, `lint:data`, `scan:secrets`, `lint:commits` and `test:unit` (all required), then `scan:code`, `annotate`, `mark-stale`, `greet`, `update-deps` and `label`; `docsPreset` adds `typecheck` and `deploy-docs`, `withAudit` adds `measure:bundle` (plus `lint:unused` and `test:perf` on request) and `withWiki` adds `publish-wiki`. `compose()` merges tasks by flat id, so listing an old dotted name such as `verification.unitTests` in your own config still overrides the preset's `test:unit` entry. The pre-flat names the presets used to carry (`lint`, `test`, `security`, `review`, `stale`, `greetings`, `dependencies`, `bookkeeping`, `audit`, `wiki`) are gone from the preset output. {/* holocron-allow-old-name */}

To build your own, `compose()` capabilities. `withCapabilities` holds the factories: `withNode`, `withTypecheck`, `withDocs`, `withAudit`, `withWiki`, `withReact`, `withNextjs` and `withMonorepo`.

```ts
import { compose, withCapabilities } from "@theholocron/cli/presets";

const { withNode, withTypecheck } = withCapabilities;
const preset = compose(withNode(), withTypecheck());
```

## Full schema

```ts
import { defineConfig } from "@theholocron/cli";

export default defineConfig({
  // Project name. Derived from package.json#name when absent.
  name: "my-project",

  // Short description. Written to package.json#description and the GitHub repo by `holocron sync`.
  description: "Short description",

  // Project homepage. Synced to package.json#homepage and the GitHub repo's website field.
  homepage: "https://github.com/my-org/my-project",

  // Repository identity and metadata.
  repo: {
    // "owner/name" — injected into every plugin's context so --repo isn't needed on every call.
    name: "my-org/my-project",

    // Branch protection preset applied by `holocron setup`.
    // "balanced" — squash merge only, delete branch on merge, no force-push.
    // "strict"   — same + required status checks. In a repo that contains the `ci`
    //              aggregate the list is `ci / Required checks` and `DCO`: the aggregate waits on every
    //              `{ required: true }` task, the hand-written checks and the
    //              codecov statuses in `extraRequiredChecks`. In any other repo it
    //              is `DCO`, every required task's check context (in CI order) and
    //              `extraRequiredChecks`. No hand-maintained list.
    // "none"     — no protection applied.
    protection: "balanced",

    // GitHub teams granted repo access. String shorthand → push (Write) permission.
    teams: ["my-org/engineers", { slug: "my-org/bots", permission: "push" }],

    // GitHub repository topics.
    topics: ["typescript", "node", "cli"],
    // GitHub Actions variables (workflows read them as `vars.NAME`): literal values, or `sync` names the vault
    // environment `holocron sync secrets` fills them from (names only; one source per name).
    variables: {
      org: { TURBO_TEAM: "my-team" },
      sync: [{ environment: "Vars", scope: "org=my-org", keys: ["CLOUDFLARE_ACCOUNT_ID"] }],
    },
    // Secrets that must exist; `holocron doctor secrets` reports the missing ones. Names only.
    // `sync` names the vault environments `holocron sync secrets` fills secrets from, and where (no `keys` = every key).
    // An `org=` scope must name its readers: `repos` (visibility "selected"), never every repository.
    // `deploy` names what a deployment or Worker may receive from `sync secrets` (a `prefix` and/or `keys`; required).
    secrets: {
      repo: ["TURBO_TOKEN"],
      org: ["NPM_TOKEN"],
      sync: [
        { environment: "prd" },
        { environment: "prd", scope: "org=my-org", repos: ["my-repo"], keys: ["NPM_TOKEN"] },
      ],
      deploy: [{ environment: "prd", prefix: "MYAPP_" }],
    },

    // GitHub org-level custom properties synced by `holocron setup`.
    properties: {
      lifecycle: "active", // "active" | "experimental" | "deprecated"
      open_source: true,
      runtime_environment: "node", // "node" | "browser" | "universal" | "none"
      uses_external_packages: true,
    },
  },

  // The task manifest — what this repo runs, named by intent, not by tool.
  // `@theholocron/astromech` reads it for `holocron run` / `holocron run ci` /
  // the generated CI workflow thin callers. String form: default inputs.
  // Object form: pass custom `with:` inputs. See "Task vocabulary" below
  // for the full list of task names and what each actually runs.
  // `required: true` marks a task merge-gating: `holocron run ci` runs it by
  // default and `holocron setup` (strict) adds its check context to branch
  // protection.
  tasks: [
    { name: "lint:code", required: true },
    { name: "test:unit", required: true },
    { name: "typecheck", required: true },
    { name: "release", with: { "run-build": false } },
    "stale",
    "greetings",
  ],

  // Required status-check contexts **not** backed by a `{ required: true }` task
  // — codecov gates, a docs/storybook publish job, etc. The `ci` aggregate waits on
  // them: a `codecov/` entry is polled as a commit status, any other entry
  // (`"Generated files / Check"`) as a check run named `<id> / ...`. List the aggregate
  // `codecov/patch` and `codecov/project` only: a ruleset takes no wildcards, and a
  // package a PR does not touch posts no `codecov/patch/<package>` status, so
  // per-package contexts neither scale nor reliably appear.
  extraRequiredChecks: ["codecov/patch", "codecov/project"],

  // `holocron sync` reconciles package.json#scripts (merge, never clobber): the
  // `holocron` entry + a script per runnable task: `turbo run <task>` in a workspace,
  // `holocron run <task>` in a single package.
  // `syncScripts: false` disables it; `holocronScript` sets the `holocron`
  // entry's command (default "holocron", the installed bin).
  // syncScripts: false,
  // holocronScript: "node cli/cli/dist/cli.mjs",

  // Git hooks installed by `holocron setup`. `true` / `{ prePush: true }`
  // writes `.husky/pre-push` (runs `holocron run ci` before every push) and adds
  // `prepare: "husky"` to package.json; `false` / `{ prePush: false }` opts out.
  // Omitted → on for `protection: "strict"`, off otherwise. `holocron setup
  // --hooks` / `--no-hooks` override per-run. Bypass a single push with
  // `git push --no-verify`.
  // hooks: true,

  // Agent runtime — determines where skills are installed.
  // "claude" → .claude/skills/<name>  (symlinks to .agents/skills/<name>)
  agent: "claude",

  // Skill names from @theholocron/skills to install via `holocron setup`.
  // Installed to .agents/skills/<name>/ — gitignored and regenerated each run.
  skills: ["git-safety", "pr-workflow", "commit-standards", "security-review"],

  // Capability → provider bindings.
  providers: {
    source: "github",
    ci: "github",
    secrets: "github",
    environments: "github",
    issues: "github",
    vault: ["1password", { vault: "acme-app" }],
    deployment: ["vercel", { teamId: "team_xxx" }],
    storage: "neon",
    auth: "clerk",
    tooling: ["postman"],
    // errors and logs are env-var-activated at runtime (HOLOCRON_SENTRY_DSN / HOLOCRON_AXIOM_TOKEN).
    // The provider entry is used by `holocron setup` and `holocron doctor` only.
    errors: "sentry",
    logs: "axiom",
  },

  // The default environment for the `credentials` providers (`providers.credentials`).
  // A name, not a secret, so it is committed. A provider can name its own instead,
  // `credentials: ["1password", { environment: "Demo" }]`, which wins; a 1Password entry with
  // neither derives `<org>/<repo> - <layer>` from the git remote (see /tokens); each
  // provider needs one or the other. List an entry per Environment to read several
  // (the same provider twice is fine); a name is found in the first one that has it.
  credentials: { environment: "Demo" },

  // Every entry that names a vault Environment (`repo.secrets.sync`, `repo.variables.sync`,
  // `repo.secrets.deploy`, `githubApps`, `dev` and the `vault` provider's options) can name a
  // `layer` instead: "local", "dev", "ci" or "prod". The Environment is then
  // `<org>/<repo> - <layer>`, from the git remote. `vault: ["1password", { layer: "ci" }]`.

  // How `holocron dev` runs this directory's application locally behind a development
  // tunnel. Every field is optional here and has a flag; a flag wins. Names and a
  // hostname, not secrets, so they are committed.
  dev: {
    layer: "dev", // the layer whose Environment its variables come from: <org>/<repo> - dev
    // (or `environment: "Name"` for a literal name; both together are a ConfigError)
    tunnel: { name: "sentinel-dev", hostname: "sentinel-dev.example.dev" },
    port: 3000, // default 3000
    command: ["pnpm", "run", "serve"],
  },

  // Structured-logging config. `level` is the lowest-priority level source:
  // --verbose/--quiet and HOLOCRON_LOG_LEVEL both outrank it. `axiom.dataset`
  // is a per-repo override of the CLI's dataset (HOLOCRON_AXIOM_DATASET)
  // — the token still comes from an env var or the OS keyring, never here.
  log: { level: "info", axiom: { dataset: "my-repo" } },

  // CLI self-telemetry override layer (see /telemetry). Env
  // (HOLOCRON_TELEMETRY=false) still wins and is checked first; this is the
  // committed way to opt a repo out or drop usage analytics only. No
  // credentials here — the Sentry DSN / PostHog key come from env or ship as
  // fallbacks.
  //   enabled: false      → no-ops Sentry + PostHog for every command
  //   analytics: "none"   → PostHog off, Sentry error reporting unaffected
  telemetry: { enabled: true, analytics: "posthog" },
});
```

## Task vocabulary

Tasks are named by **intent**, not by tool — `tasks: ["test:unit"]`,
not `["vitest"]`. Tool names never appear in `holocron.config.ts`; the table
below is the full registry (`@theholocron/astromech`'s `TASKS`) — every task
name it knows, what it actually runs, and why.

An id is flat and verb-first (spec `ci-flat-task-vocabulary`, epic #1612): `<verb>`, `<verb>-<object>` or
`<suite>:<leaf>`. A colon means "member of the suite named before it" (`test:unit`, `lint:code`); a hyphen is part of a
verb phrase and implies no suite (`deploy-preview`). Five **suites** exist, declared by their leaves in the registry:
`test` (`test:unit`, `test:visual`, `test:perf`), `lint` (`lint:code`, `lint:editorconfig`, `lint:markdown`,
`lint:data`, `lint:unused`, `lint:commits`), `scan` (`scan:secrets`, `scan:code`), `measure` (`measure:docs`,
`measure:bundle`) and `validate` (`validate:specs`, `validate:docs`, `validate:deps`, `validate:generated`). A suite is never a `tasks:` entry:
list the leaves, and the leaves a repo lists are what `holocron run <suite>` runs. `format` is a verb of its own, not a
suite: prettier only, it writes by default and `--check` is the read-only form.

The old dotted names (`verification.unitTests`, `sourceQuality.staticAnalysis`, …) are still accepted in `tasks:` and by {/* holocron-allow-old-name */}
`holocron run`, which prints a one-line deprecation notice on stderr. `sourceQuality.formatting` stands for
`lint:editorconfig`, `lint:markdown` and `format --check`; `delivery.publish` is now `release`. A manifest spelled either way generates the same files. The workflow callers are named for the flat id (workflow, job and {/* holocron-allow-old-name */}
file, `ci.test-unit.yml` in holocron) in the repo that contains the reusables; any other repo keeps the old caller names
until its callers move to the flat reusables (`ci-v1`), because its ruleset lists those checks.

| Task                                 | Runs                                                              | Notes                                                                                                |
| ------------------------------------ | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `test:unit`                          | vitest                                                            | always runs with coverage (`vitest run --coverage`); there is no `--coverage` flag                   |
| `typecheck`                          | tsc                                                               | `tsc --noEmit`                                                                                       |
| `test:visual`                        | Chromatic                                                         | no local equivalent — CI only; a repo opts in by listing it                                          |
| `test:perf`                          | Lighthouse CI                                                     | only runs with a `lighthouse.config.*` present                                                       |
| `lint:code`                          | eslint, actionlint, git-merge-conflict-markers                    | bundles more than one tool under one required check; in CI it also runs the `format --check` step    |
| `lint:editorconfig`, `lint:markdown` | editorconfig-checker, markdownlint-cli2                           | each is a `linterGroup` of one tool                                                                  |
| `format`                             | prettier                                                          | writes by default, `--check` is read-only; no workflow of its own (its CI step lives in `lint:code`) |
| `lint:data`                          | yamllint                                                          |                                                                                                      |
| `lint:unused`                        | knip                                                              |                                                                                                      |
| `scan:secrets`                       | gitleaks                                                          |                                                                                                      |
| `scan:code`                          | CodeQL                                                            | no local equivalent — CI only                                                                        |
| `check-tokens`                       | `holocron doctor secrets --verify`                                | scheduled daily in CI; fails on a rejected token or one with 7 days or fewer left                    |
| `build`                              | tsdown / vite / rollup / tsc, detected from the repo's own config |                                                                                                      |
| `release`                            | semantic-release                                                  | no local equivalent — CI only; carries `preview` (npm dist-tags)                                     |
| `deploy`                             | Cloudflare Pages / Vercel                                         | no local equivalent — CI only; carries `preview`                                                     |
| `deploy-preview`                     | a preview deployment                                              | no local equivalent — CI only; runs when a preview deployment exists                                 |
| `check-preview`                      | checks against a preview deployment's URL                         | no local equivalent — CI only; runs from the preview's `deployment_status` event                     |
| `measure:bundle`                     | bundle-size upload to Codecov                                     | no local equivalent — CI only                                                                        |
| `measure:docs`                       | `holocron probe docs coverage`                                    | upload to Codecov as the `documentation` flag                                                        |
| `sync-repo`                          | `holocron sync`                                                   | keeps generated files current                                                                        |
| `sync-templates`                     | `holocron sync github`                                            | holocron's own repo only: opens sync pull requests in `theholocron/.github` and the consumer repos   |
| `check-notify`                       | `holocron notifications` end-to-end check                         | no local equivalent — a workflow run by hand; never part of `holocron run ci`                        |
| `lint:commits`                       | commitlint                                                        | no local equivalent — enforced by the `commit-msg` hook locally, over the PR's commit range in CI    |
| `validate:specs`                     | ADR/spec frontmatter (`holocron probe specs check`)               | not a linter — a process/governance check                                                            |
| `validate:docs`                      | docs presence and token docs (`holocron probe docs validate`)     | not a linter; presence only warns, token docs fails                                                  |
| `validate:plugin`                    | the plugin package's own `scripts/validate.mjs`                   | a live check against the provider, run by hand; no workflow, not part of `holocron run ci`           |
| `publish-wiki`                       | Fern                                                              | publishes `docs/wiki/*.md` — a publish, not a sync; carries `preview`                                |
| `deploy-docs`                        | Astro build                                                       | the docs site itself; carries `preview` (defaults on)                                                |
| `deploy-components`                  | Storybook build                                                   | a browsable component catalog; carries `preview` (defaults on)                                       |

`preview` is a cross-cutting feature, not a namespace — npm has staging
dist-tags, Cloudflare/Vercel do per-PR preview deploys, Fern previews docs.
None of these earn their own task; it's one capability any
publish/deploy-shaped task can carry, toggled via that task's `with:`.

### Switching docs presence off

`validate:specs` and `validate:docs` are two tasks of the `validate` suite, each with its own workflow and its own check.
A repo that does not want one leaves it out of `tasks:` in `astromech.config.ts`; there is no `jobs:` switch (it went with
the split, and the old `validate` name, which stood for both, still lists both):

```ts
{ name: "validate:specs", required: true }
```

The `validate:docs` task runs `holocron probe docs validate`: `docs presence`, which only ever warns, then `docs tokens`, which fails for a token a plugin resolves that [the token reference](/holocron/tokens/) does not list. Presence warns for a new public package with no docs change, and for a `feat`
that changes a public package's source (`src/**`, or a root `index.ts`) without a docs signal for that package: its
README, a docs page named after it, or a doc comment in the diff. When no docs change is needed, say why in the pull
request description or in a commit message:

```text
[skip docs] the new option is internal and has no page
[skip docs: array-utils, fs-utils] only these two need no page
```

Like `[skip ci]`, the marker is read from the text, and the reason after it is required: a bare `[skip docs]` still
warns. The description is read from the run's event, so editing it after the run needs a new push (a commit message
works the same way); a re-run uses the old description.

### Doc-comment coverage

`repoValidation.docsCoverage` decides what `holocron probe docs patch` and the `documentation` Codecov flag do about an
exported function, class, interface, type or constant that a pull request adds or changes without a doc comment (TSDoc is the source of truth for the API
reference, so this is what keeps it complete):

```ts
export default defineConfig({
  repoValidation: { docsCoverage: "required" }, // "off" (default) | "warn" | "required"
});
```

| Value        | `holocron probe docs patch`                                 | `documentation` Codecov flag                                                        |
| ------------ | ----------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `"off"`      | skipped: nothing is measured or written, the check is green | nothing is added to `codecov.yml`                                                   |
| `"warn"`     | reports each miss, exits 0                                  | `codecov/patch/documentation` and `codecov/project/documentation` are informational |
| `"required"` | fails for each miss                                         | the statuses are not informational                                                  |

Left out, it is `"off"`, so a repo that does not set it sees no change. `holocron setup` adds the `documentation`
flag and its two statuses to `codecov.yml` for `"warn"` and `"required"` and moves them between the two; it never removes
them, and `"off"` leaves what is there alone. The value never puts a check in the branch-protection required checks:
that is `extraRequiredChecks` and a ruleset change. A value other than the three is a config error. The check itself and
the `--lcov` upload are described under [`holocron probe`](/holocron/commands/probe/#documentation).

No super-linter: every task above runs its own tool directly, through the
same mechanism that resolves it locally — CI runs the identical command a
developer runs.

## Provider entry forms

Holocron supports multiple entry forms for flexibility:

```ts
// Short form — single provider, no options
"source": "github"

// Tuple form — single provider with options
"deployment": ["vercel", { teamId: "team_xxx" }]

// Multi form — multiple providers (only for "many" cardinality capabilities)
"tooling": ["postman", "other-tool"]

// Multi with options
"notifications": [
  ["slack",   { channel: "#ops" }],
  ["discord", { webhook: "env:HOOK" }],
]
```

A provider's options hold its own config; for `monitoring` they list the `checks`, each of which may name the `alertChannels` it alerts through, and the alert channel's settings (`feeds.monitoring.alerts`) sit in the `notifications` layout. See the [Checkly plugin](/holocron/plugins/checkly/#alert-channels) and [Server as Code](/holocron/server-as-code/).

An org-wide identifier that is a provider option and that CI does not need (the Vercel `teamId`, a Checkly or Cloudflare `accountId`, the Sentry `org`) can live in `.holocron/org.ts` instead of the tuple: the loader fills an option the entry leaves out, and setting it in both places is an error that names both. The area is shared with the configs in subdirectories of the repository: an app's config also reads the root's `.holocron/org.ts`, and its own file wins for a key set in both (that is not an error). See [The `.holocron/` directory](https://github.com/theholocron/holocron/blob/alpha/cli/cli/README.md#the-holocron-directory).

Short provider names (e.g. `"github"`) are resolved to `@theholocron/holocron-plugin-github`. Fully-qualified package names and community plugins (prefixed `holocron-plugin-`) are passed through verbatim.

## Agent and engineering knowledge

### `agent` + `skills`

`agent` sets the AI runtime (`"claude"` | `"codex"` | `"gemini"`). When set, `holocron setup` installs the listed skills from `@theholocron/skills` into `.agents/skills/<name>/` with an agent-specific symlink (e.g. `.claude/skills/<name>` for Claude Code). The installed paths are gitignored and regenerated on every run.

```ts
agent: "claude",
skills: ["git-safety", "pr-workflow", "commit-standards", "security-review"],
```

When `agent` is set, `holocron setup` also writes nine AI engineering workflow role prompts to `.agents/prompts/` — one file per agent role (`discovery.md`, `design.md`, `discussion.md`, `adr.md`, `spec.md`, `implementation-plan.md`, `implement.md`, `review.md`, `verify.md`). The prompts directory is gitignored and always regenerated from the current CLI version.

### `docs` — decisions structure

When `docs` is configured, `holocron setup` also provisions the engineering knowledge structure on first run. Existing files are never overwritten, so existing ADRs are safe.

| Path                              | Created                                     |
| --------------------------------- | ------------------------------------------- |
| `docs/wiki/decisions/template.md` | MADR ADR template with required frontmatter |
| `docs/wiki/decisions/README.md`   | Index and usage guide                       |
| `docs/engineering/README.md`      | Internal engineering site stub              |

Any repo with a docs site gets the structure — it costs nothing and is ready when needed, even if ADRs are never written.

## Capability cardinality

| Capability      | Cardinality | Description                                                                                                                       |
| --------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `source`        | single      | Repository + branch + workflow file operations                                                                                    |
| `ci`            | single      | CI run listing and status                                                                                                         |
| `secrets`       | single      | CI/platform secret sync destination                                                                                               |
| `environments`  | single      | Named deployment environments                                                                                                     |
| `issues`        | single      | Issue tracker (create, search, transition)                                                                                        |
| `deployment`    | single      | Preview and production deployment                                                                                                 |
| `storage`       | single      | Database branch management                                                                                                        |
| `auth`          | single      | Identity provider                                                                                                                 |
| `vault`         | single      | Secret source-of-truth                                                                                                            |
| `dns`           | single      | DNS record management                                                                                                             |
| `errors`        | single      | Error tracking — env-var-activated (`HOLOCRON_SENTRY_DSN`); provider entry used by setup/doctor only                              |
| `logs`          | single      | Log aggregation — env-var-activated (`HOLOCRON_AXIOM_TOKEN` + `HOLOCRON_AXIOM_DATASET`); provider entry used by setup/doctor only |
| `tooling`       | **many**    | Sync external tool state                                                                                                          |
| `notifications` | **many**    | Send messages                                                                                                                     |
| `analytics`     | **many**    | Analytics providers                                                                                                               |
| `credentials`   | **many**    | Where this machine reads its own tokens (a 1Password Environment), tried in order before the keyring                              |

`many` capabilities accept a list of providers; `single` accept exactly one.

`errors` and `logs` are self-contained: they activate at runtime when their env
vars are present, regardless of whether a provider entry exists in config. The
config entry is for `holocron setup` (provisioning the dataset/project) and
`holocron doctor` (connectivity checks) only.

## JSON format

If you prefer not to use TypeScript:

```json
{
  "name": "my-project",
  "description": "Short description",
  "repo": {
    "name": "my-org/my-project",
    "protection": "balanced",
    "topics": ["typescript", "node"]
  },
  "workflows": ["lint:code", "test:unit"],
  "providers": {
    "source": "github",
    "vault": ["doppler", { "project": "my-project", "config": "prd" }]
  }
}
```

JSON repos (like `.github` and `.github-private`) use `holocron.config.json` since they have no `package.json` to install TypeScript.

## Global options

All commands accept these flags:

| Flag              | Default         | Description                                 |
| ----------------- | --------------- | ------------------------------------------- |
| `--dry-run`       | `false`         | Print mutations without executing them      |
| `--token <value>` | —               | Override provider token for this invocation |
| `--cwd <path>`    | `process.cwd()` | Directory to search for config              |

### `--token` forms

```bash
# Bare: fallback token for single-provider commands
holocron setup --token ghp_xxx

# Keyed: target a specific provider
```
