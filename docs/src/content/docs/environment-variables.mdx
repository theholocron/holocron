title: Environment Variables
description: Every environment variable the Holocron CLI, plugins, kyber, Sentinel and the generated workflows read, and which of them carry the HOLOCRON_ prefix.
---

A variable Holocron owns is `HOLOCRON_<NAME>`. The bare `<NAME>` is kept as a fallback, so nothing that sets it breaks, and a variable another tool reads itself is never renamed. This page is the list, sorted into the three groups of [#1864](https://github.com/theholocron/holocron/issues/1864).

## The rule

- The prefix is one constant, `PREFIX` (`"HOLOCRON"`), exported from `@theholocron/env-utils/lookup`. `holocronEnv()` reads a name as `HOLOCRON_<NAME>` and then `<NAME>`; kyber's `resolveValue(names, env, { prefix: PREFIX })` does the same through the environment and then the `credentials` providers. See [env-utils](/holocron/utils/env-utils/) and [kyber](/holocron/kyber/).
- Empty values count as unset at every step, so a blank `HOLOCRON_X=` falls through to `X`.
- A bare fallback is never removed in the same change that adds the prefixed name. Removing one is a later, separate change.
- The prefixed name is an extra way in for a name a third party reads. The bare name still works there.
- The organization variables that `repo.variables.sync` writes are `HOLOCRON_`-named too (the table at the end). A workflow reads `vars.HOLOCRON_<NAME> || vars.<NAME>` and, where a tool reads the bare name itself (turbo, wrangler, sentry-cli), maps it onto that name in the step's `env`, so the tool keeps working. The bare variable stays set in GitHub until the maintainer has renamed it and a later change removes the fallback (#1979).

### `ENVIRONMENT`

Decided: Holocron owns the name, so it moves like the others. `detectEnvironment()` and `environment.get()` read `HOLOCRON_ENVIRONMENT` first and then `ENVIRONMENT`, and `ENV` and `NODE_ENV` stay what they were (`environment.get()` only; `detectEnvironment()` ignores them). The bare name is not a third-party contract, but it is the one a deployed application, Sentinel and Comlink already have set, so it stays as a fallback and nothing that sets it breaks.

`holocron dev` sets both names for the application it runs, to one value, the way it sets `PORT` and `HOLOCRON_PORT`. A vault Environment that sets either one decides for both (`HOLOCRON_ENVIRONMENT` wins when it sets both), so a dev instance still logs `env: "development"` whichever name the application reads. A deployment sets `HOLOCRON_ENVIRONMENT=production`, or keeps `ENVIRONMENT=production`; no change is required.

## Synced organization variables

`repo.variables.sync` keeps these names in 1Password and GitHub. Workflows read `vars.HOLOCRON_<NAME> || vars.<NAME>` (the bare name is the fallback until the variable is renamed) and map the value onto the name a tool reads.

| Variable                              | Used as                                                                     | Decision                                       |
| ------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------- |
| `HOLOCRON_AXIOM_DATASET`              | `HOLOCRON_AXIOM_DATASET` in `sync-github`, `sync-repo`                      | Already prefixed                               |
| `HOLOCRON_POSTHOG_PROJECT_TOKEN`      | `HOLOCRON_POSTHOG_PROJECT_TOKEN` in `sync-github`, `sync-repo`              | Renamed (was `POSTHOG_PROJECT_TOKEN`)          |
| `HOLOCRON_VERCEL_TEAM_ID`             | `HOLOCRON_VERCEL_TEAM_ID` and `VERCEL_TEAM_ID` in `check-preview`           | Renamed (was `VERCEL_TEAM_ID`)                 |
| `HOLOCRON_CLOUDFLARE_ACCOUNT_ID`      | `accountId` of the wrangler action; `CLOUDFLARE_ACCOUNT_ID` in a shell step | Renamed; mapped onto the name wrangler reads   |
| `HOLOCRON_CLOUDFLARE_PAGES_PROJECT`   | the Pages project name in `preview`                                         | Renamed (was `CLOUDFLARE_PAGES_PROJECT`)       |
| `HOLOCRON_TURBO_TEAM`                 | `TURBO_TEAM` in each job's `env`                                            | Renamed; mapped onto the name turbo reads      |
| `HOLOCRON_SENTRY_ORG`                 | `SENTRY_ORG` in `release`                                                   | Renamed; mapped onto the name sentry-cli reads |
| `AXIOM_ORG`, `SENTINEL_AXIOM_DATASET` | Sentinel's query link and dataset in `check-dispatched`                     | Stay as they are (Sentinel's convention)       |

## The guard

`cli/cli/src/env-prefix-guard` scans every non-test TypeScript file in the workspace and fails the CLI's unit tests when source reads a bare variable that is not owned by a prefix (`HOLOCRON_`, `SENTINEL_`, `COMLINK_`), not in the allowlist and not read through the prefix helper. The helper is `holocronEnv()`, `withEnvPrefix()`, a variable declared from one, or `resolveValue(names, env, { prefix })`. A bare name is also accepted when the same file reads its `HOLOCRON_` spelling, which is the explicit pair the Axiom plugin and the logger package write out. It looks at `.get("NAME")` on an environment, `env.NAME`, `env["NAME"]`, `process.env`, and the names given to `firstEnv` and `resolveValue`; a name built at run time is not looked at, and `noProcessEnv` still bans `process.env` in the plugins and kyber.

The allowlist is `env-allowlist.ts`, in two parts: the group 2 names a third party reads itself, and the group 1 names whose move is deferred (the table above). Add a name to the first only when a third party reads it itself. A name Holocron chooses never goes in either.
