Holocron uses one Personal Access Token per capability group. Each token carries only the scopes its operations require — a leaked token's blast radius is contained to that feature alone.

Every other variable the CLI reads, and which of them carry the `HOLOCRON_` prefix, is on [Environment Variables](/holocron/environment-variables/). Where a token below has a vendor name too, the `HOLOCRON_` name is read first and the vendor name is the fallback.

## GitHub feature token resolution

For GitHub feature tokens (`HOLOCRON_READ_TOKEN`, `HOLOCRON_ADMIN_TOKEN`, etc.), the chain is:

```text
--token flag
→ HOLOCRON_<FEATURE>_TOKEN (feature-specific env var)
→ the same variable in the repo's .env file (optional, see below)
→ the same variable in a credentials provider (a 1Password Environment, see below)
→ keyring("github.<feature>") (stored via `holocron new token`)
```

Each keyring entry is read once per command: the answer, a missing entry included, is remembered until the command ends, so the OS keychain is asked once per token and not on every lookup. Nothing is cached between commands.

No broad-token fallback. If none of the above is set, the command exits with an error naming the exact env var to configure. One command differs: `sync-wiki` takes the token from the environment (`HOLOCRON_READ_TOKEN`, then `GH_TOKEN`, then `GITHUB_TOKEN`) and only then from the keyring entry `github.read`, so it works in a GitHub Actions job with no extra setup and from a token stored with `holocron new token github.read`.

## The repo's `.env` file

A `.env` file at the repo root is optional and needs no config. If it is there, the CLI reads it and its variables sit in the chain after the process environment and before the `credentials` providers, so a token written in it wins over 1Password and the keyring. It is for a developer who wants plain tokens on disk (or a file that 1Password, OpenShell or AWS Secrets Manager mounts), and a project that keeps its tokens elsewhere never creates one.

- Only `<repo root>/.env` is read, never a `.env` in the directory you ran the command from, so a checkout you cloned and ran the CLI in is not trusted.
- Use the same variable names as everywhere else (`HOLOCRON_ORG_TOKEN=...`). A blank value is skipped.
- Keep it out of git. The repo's `.gitignore` lists `.env`; check that yours does before you create one.
- The file is read once per command.

## Credentials providers

A `credentials` provider is a second place to keep these tokens, ahead of the keyring: one 1Password Environment holds them all, signs you in with Touch ID, and follows you to another machine. The keyring stays as the fallback. A token set in the process environment (or passed with `--token`) still wins, so a CI job that sets its own never asks 1Password.

```ts title="holocron.config.ts"
export default defineConfig({
  providers: { credentials: ["1password"] },
});
```

A 1Password entry with no `environment` option derives its Environment names: `<org>/<repo>` from the repository's `origin` remote, plus a layer from `detectEnvironment()`. A machine reads `<org/repo> - local` and then `<org/repo> - dev` (the only fallback; a missing `- local` is skipped silently). `holocron dev` reads `- dev`, CI reads `- ci`, a deployed app reads `- prod`, and the `test` layer reads none. A missing `- dev`, `- ci` or `- prod` is an error that names the Environment, and a layer never reads another's. A remote the CLI cannot parse is an error that asks for an explicit `environment`.

The rest of the config names a layer the same way (`layer: "ci"` on a sync entry, `vault: ["1password", { layer: "prod" }]`, `holocron sync secrets --env prod`; see [sync secrets](/holocron/commands/sync-secrets/)), through the same derivation.

An explicit name wins and is the only Environment read: a provider's own `environment` option, else the shared `credentials: { environment }` block. Use it for a checkout whose remote does not match the repo, or for a provider that does not derive (only 1Password does). Either way the CLI passes the name to the plugin when it reads; the plugin does not store it.

Each variable in the Environment is named for the env var the command already reads (`HOLOCRON_ORG_TOKEN`, `HOLOCRON_DISCORD_BOT_TOKEN`, `CLOUDFLARE_API_TOKEN`, ...), so there is no mapping to keep. The Environment is read once per command, so Touch ID asks once for all of them. If `op` is missing, locked or gives no answer within 60 seconds, the provider is skipped and the keyring is tried.

### First-time setup, once per project

`op` cannot create an Environment or set a variable (checked on `op` 2.43.0-beta.02: `op environment` only has `read` and `secret list`), so this part is by hand:

1. Install the CLI and turn on the desktop-app integration: `brew install 1password-cli`, then in the 1Password app, Settings, Developer, "Integrate with the 1Password CLI". `op environment secret list` needs a recent `op`: it is in 2.43.0-beta.02, and 2.35.0-beta.01 did not have it.
2. In the 1Password app: Developer, View Environments, then create an Environment. Name it `<org/repo> - <layer>` (`theholocron/holocron - dev`), or as the provider's `environment` option says.
3. Add one variable per token, named for the env var, for example `HOLOCRON_ORG_TOKEN`. The names each command reads are in the [provider table](#provider-tokens) and the GitHub feature-token table above.
4. Put `providers.credentials` in `holocron.config.ts` as shown; add an `environment` option only to name the Environment yourself.
5. Check it prints only the variable names: `op environment secret list "theholocron/holocron - dev"` (add `--reveal` only when you want the values).

### Checking it

`holocron doctor secrets --env local,dev` reads names only, never a value, and compares them with the tokens the configured plugins take: it shows them in the `local` and `dev` columns of its matrix, fails when a required Environment cannot be found (by name) or lacks a variable (an optional token, such as `HOLOCRON_RELEASE_TOKEN` or the Discord webhook, is a skipped row), and says which Environment and spelling matched. See [`doctor secrets`](/holocron/commands/doctor-secrets/).

### Moving the tokens you already have

`op` cannot set a variable, so the Environment is filled in the 1Password app. To get tokens that are already in the keyring there without copying each by hand, [`holocron export tokens`](/holocron/commands/export-tokens/) writes them as `NAME=value` lines, named for the env vars the plugins read, to a private file the app can import:

```sh
holocron export tokens             # the keyring, to .credentials
holocron export tokens --from-env  # also what is set in this shell
```

In the app: Developer, View Environments, the Environment (`theholocron/holocron - dev`), **Import .env file**, and choose `.credentials`. Back in the terminal, press Enter and the file is overwritten and deleted. It is created readable by you alone, refused unless git ignores it, never overwrites a file, and is deleted on Ctrl-C too, so the plain text exists only for the minutes the import takes. Then run `holocron doctor secrets` to see what is still missing. Piped, the command writes the lines to stdout instead; `--copy` puts them on the clipboard.

### Adding a token later

`holocron new token` stores the token in the keyring as before. When the config names a `credentials` provider it also prints the variable to add there, because `op` cannot write to an Environment:

```text
stored cloudflare token (account: acme)
  1password cannot be written to from the CLI: add HOLOCRON_CLOUDFLARE_TOKEN to its "Demo" environment yourself, so the token follows you to other machines
```

The name is the one the plugin lists for that keyring entry (`holocron doctor secrets --verify` shows them), or `HOLOCRON_<PROVIDER>_TOKEN`, and `HOLOCRON_<FEATURE>_TOKEN` for a key such as `github.read`. Nothing is printed outside a repo, or in a repo whose config names no `credentials` provider, and the token itself is never printed.

Names are matched exactly and `op` cannot list Environments, so the provider tries the name as written, then lowercase, Title case and UPPERCASE. A name with other casing, or the Environment's id (which `secret list` also accepts), has to be written exactly. With several accounts signed in, set `account` in the provider's options so `op` looks in the right one.

## Provider token resolution

For every other provider plugin (Axiom, Cloudflare, Sentry, Slack, Vercel, etc.), tokens are resolved in this order:

```text
--token flag
  → the plugin's own env var    (e.g. HOLOCRON_CLOUDFLARE_TOKEN)
  → the vendor's native env var (e.g. CLOUDFLARE_API_TOKEN)
  → either variable in the repo's .env file (optional, see below)
  → either variable in a credentials provider (a 1Password Environment, see below)
  → keyring("<provider>.<org>") (org-scoped — only when an org is active)
  → keyring("<provider>")       (unnamespaced fallback)
```

Both env var names for every plugin are in the [provider table](#provider-tokens). Not every plugin follows the `HOLOCRON_<PROVIDER>_TOKEN` pattern: Neon and the collections tool use `_API_KEY`, and Clerk uses `_SECRET_KEY`.

The org-scoped keyring step runs when an org name is active. Org resolution order:

1. `--org <name>` CLI flag — per-invocation override
2. `HOLOCRON_ORG` env var — set in shell profile, `.envrc`, or CI secret
3. `org` field in `holocron.config.ts` — automatic for projects that declare it

This lets a single machine hold separate credentials for multiple GitHub orgs without collision:

```bash
# Store per-org credentials once
holocron new token cloudflare --org theholocron <TOKEN-A>
holocron new token cloudflare --org client-co   <TOKEN-B>

# theholocron project (org: "theholocron" in config) → picks up TOKEN-A automatically
cd ~/Code/theholocron/some-project && holocron setup

# client-co project (org: "client-co" in config) → picks up TOKEN-B automatically
cd ~/Code/client-co/some-project && holocron setup

# One-off override
holocron setup --org client-co
```

### Check a GitHub token

`holocron probe github token` tries a token with one read per permission and reports which it reaches. GitHub lists scopes only for a **classic** token (the `X-OAuth-Scopes` header, shown on the first row); a **fine-grained** token has no list, so each permission is found by a read, and the first row says which kind was read. A read proves a token can _see_ an area, not that it can write there, so the write half of a `read/write` row in the table above is not checked. On a public repository the Contents, Actions, Issues and Pull requests reads succeed for any token, so those can show a permission is present but not that it is absent; Administration, Secrets, Environments and the organization permissions can prove both.

| Permission (declaration name)                                       | The read that needs it                                                                      |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `contents`                                                          | `GET /repos/{repo}/contents`                                                                |
| `actions`                                                           | `GET /repos/{repo}/actions/runs`                                                            |
| `issues`, `pull-requests`                                           | `GET /repos/{repo}/issues`, `/pulls`                                                        |
| `administration`                                                    | `GET /repos/{repo}/actions/permissions`                                                     |
| `secrets`, `environments`, `actions-variables`                      | `GET /repos/{repo}/actions/secrets`, `/environments`, `/actions/variables`                  |
| `custom-properties`, `pages`                                        | `GET /repos/{repo}/properties/values`, `/pages`                                             |
| `org-administration`, `org-members`, `org-variables`, `org-secrets` | `GET /orgs/{org}/actions/permissions`, `/members`, `/actions/variables`, `/actions/secrets` |
| `user-sync-contents`                                                | `GET /repos/{org}/.github-private/contents`                                                 |

With `--environment ci` (or `dev`, `local`) the probe checks **every** GitHub token that layer's 1Password Environment holds, one after another, each under a heading with its variable name and judged against its own declaration: required permissions must be reached and the absent ones must not. Without `--environment` it checks the token the plugin resolves (`HOLOCRON_READ_TOKEN`), or the one `--token-name <VAR>` names (for example `--token-name HOLOCRON_ADMIN_TOKEN`), and only describes it.

**Declared once:** the rules are the `expect` of each token in the plugin's `tokens` export (`plugins/holocron-plugin-github/src/probes/token/expectations.ts`), read through `tokenExpectations()`, and the tables below say the same ([`holocron probe docs tokens`](/holocron/commands/probe/#documentation) compares them). Every token has the same rules in `local`, `dev` and `ci`, except `HOLOCRON_RELEASE_TOKEN`, which only `ci` holds: the `sync-repo`, `sync-secrets`, `reconcile-projects` and `check-tokens` workflows read each of the others, so no split is declared (#2059). What the declaration does add is least privilege, which the probe now proves: a narrow token (`read`, `issues`, `sync`, `release`, `user-sync`) must not reach Administration or Secrets, the admin token must not reach organization secrets, and the secrets token must not reach Administration. A new permission is one change in the declaration, one row in these tables and one read in `permissions.ts`.

Two tokens have a quiet fallback: when `HOLOCRON_USER_SYNC_TOKEN` is not set, the links files are read and written with `HOLOCRON_ORG_TOKEN`, then `HOLOCRON_ADMIN_TOKEN`; and `sync roles` reads a team with `HOLOCRON_ORG_TOKEN`, falling back to `HOLOCRON_ADMIN_TOKEN`. The separate tokens exist so that neither has to be that broad. A fallback token needs the same access the dedicated one would: **Contents: read/write** on `.github-private` for the links files, and the org or admin token as documented above will not have it unless you add it, so `link account` and `sync roles` fail with a 403 or 404 until you either set `HOLOCRON_USER_SYNC_TOKEN` or grant that permission.

### Why a separate org token?

Fine-grained PATs have two resource owner modes: **personal** (your repos) and **organization** (org repos). Team management and reading a team's members require a PAT whose resource owner is the org. `HOLOCRON_ORG_TOKEN` covers these; `HOLOCRON_ADMIN_TOKEN` covers the repo-scoped operations, including a repo's custom property values.

The `projects` capability (`list projects`, `new project`, `setup project`, `doctor project`) also uses `HOLOCRON_ORG_TOKEN`. Give it the organization permission **Projects: Read and write** (Read is enough for `list projects` and `doctor project`), and **Issues: Read** and **Pull requests: Read** on the repositories whose issues sit on the board. The hourly `reconcile-projects` task does not use this token: it mints one from the GitHub App, which needs the same organization Projects permission.

### What `doctor notifications` reads

The Checkly feed and Comlink relay steps of [`holocron doctor notifications`](/holocron/commands/doctor-notifications/) use the tokens above and need no new one. Each only reads, and a missing token skips its steps with the reason:

| Provider     | Read                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------- |
| `checkly`    | the alert channels (not their URLs) and the account's checks                             |
| `cloudflare` | the Worker scripts, the routes in the zone of the relay's hostname, and secret **names** |
| `sentry`     | the integrations, projects and alert rules, with the Comlink token below                 |

Whether a narrower, read-only token would do for Checkly and Cloudflare has not been tried against those providers, so the scopes in the table above are the ones `setup` needs.

### What each Cloudflare token needs

Cloudflare has far more permissions than Holocron calls. The plugin and client call only the endpoints below, so a token needs nothing else: not Access (apps or policies), not account API tokens, not billing. Checking the token (`/user/tokens/verify`) needs no permission.

| Permission              | Id        | Resource    | `local`    | `dev`      | `ci`       | Called by                                                                   |
| ----------------------- | --------- | ----------- | ---------- | ---------- | ---------- | --------------------------------------------------------------------------- |
| Zone: Read              | `zone`    | the domains | `required` | `required` | `absent`   | every zone lookup                                                           |
| DNS: Edit               | `dns`     | the domains | `required` | `required` | `absent`   | `setup` (records), `new tunnel` and `dev` (the tunnel's `CNAME`)            |
| Workers Routes: Edit    | `routes`  | the domains | `required` | `required` | `absent`   | `setup notifications` (the relay's route)                                   |
| Workers Scripts: Edit   | `scripts` | the account | `required` | `required` | `absent`   | `setup notifications` (the Worker and its secrets), `sync secrets --worker` |
| Cloudflare Pages: Edit  | `pages`   | the account | `required` | `required` | `required` | `deploy-preview`, `preview` (CI), `deploy`                                  |
| Cloudflare Tunnel: Edit | `tunnels` | the account | `required` | `required` | `absent`   | `new tunnel`, `dev` (the tunnel and its hostname rules)                     |

The layer columns are what `holocron probe docs tokens` compares with the plugin's declaration: it fails, naming the token, layer and permission, when a cell here and the `expect` of the token differ. Add a permission as a row with its `Id`, and a layer as a column named for it.

Limit Zone, DNS and Workers Routes to the domains Holocron manages (Zone Resources: specific zones). The account permissions cannot be narrowed to one project or tunnel.

- **The `dev` Environment** (a laptop runs everything): all six.
- **The `ci` Environment** (`preview` and `deploy-preview` only): Cloudflare Pages: Edit. Add Workers Scripts: Edit only if a workflow deploys a Worker. Leave the rest off, so a leak from CI cannot change DNS or a tunnel.
- **Rotation.** Cloudflare exposes a token's expiry (`expires_on`) and the start of its validity (`not_before`) only through `/user/tokens/verify`, which needs a user token with API Tokens Read; account and zone tokens get a 401 there, so `probe cloudflare token` reports their age and expiry as not exposed. Rotate them by hand every 90 days (the default `rotation` of the token's declaration, `maxAgeDays: 90`, `warnDays: 14`); a token that does expose its dates fails the probe when it is older than that or within 14 days of its expiry. A provider that exposes neither says so in its own section.
- **Declared once.** The layers and permissions in these bullets are the `expect` of the token in the plugin's `tokens` export (`plugins/holocron-plugin-cloudflare/src/probes/token/expectations.ts`); a new permission is one change there, one row in the table above (`probe docs tokens` fails until they agree) and one probe check.
- **Check a token** with `holocron probe cloudflare token`: it tries each permission above with the account id from your config and reports which the token has. `--environment ci` (or `dev`, `local`) reads that layer's token from 1Password and checks it against the bullets below, failing on a missing or extra permission. `--token cloudflare=<token>`, or a token you paste when it asks, only reports what that token can reach. See [`probe`](/holocron/commands/probe/#cloudflare).
- **`holocron dev` alone** needs Cloudflare Tunnel: Edit, DNS: Edit and Zone: Read on the zone of the tunnel's hostname. The plugin takes one token per provider, so a token with only those three works for `dev` and for nothing else; keep the full one for `setup` and pass it with `--token cloudflare=<token>` when you need it.

### Fern, Vercel, Turbo and Codecov

None of these four can say what a token is allowed to do, so Holocron declares only the layers that hold each one, and the probes say that permissions are not checked rather than guess. The layers are the `expect` of the token in the plugin's `tokens` export (`plugins/holocron-plugin-fern/src/probes/token/expectations.ts`, `plugins/holocron-plugin-vercel/src/probes/token/expectations.ts`).

| Token   | Layers that hold it  | What the probe checks                                            | What it cannot check                                                      |
| ------- | -------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Fern    | `ci`                 | that a token is set; it makes no request                         | everything else: Fern has no endpoint that reports a token                |
| Vercel  | `local`, `dev`, `ci` | who the token belongs to (`/v2/user`) and that it lists projects | its scope (Full Account or a team): Vercel does not report it             |
| Turbo   | `ci`                 | nothing: there is no Turbo plugin, so no `probe turbo token`     | the remote-cache token is a Vercel token and has no permission list       |
| Codecov | `ci`                 | nothing: there is no Codecov plugin, so no `probe codecov token` | an upload token is bound to one repository and Codecov does not report it |

- **Check one** with `holocron probe fern token` or `holocron probe vercel token`. `--environment ci` (or `dev`, `local`) reads that layer's token from 1Password and says whether the layer is one that should hold it; `--token <provider>=<value>` only describes the token. A layer outside the table is described, never failed.
- **Turbo and Codecov** are `HOLOCRON_TURBO_TOKEN` and `HOLOCRON_CODECOV_TOKEN`, held in the `ci` Environment and synced to organization secrets. No plugin reads them, so there is nowhere to declare them and nothing for a probe to run in; that needs a plugin first. Rotating them is done in the Vercel and Codecov dashboards.

### Sentry

Three tokens. The general one above (`HOLOCRON_SENTRY_TOKEN`, keyring `sentry`) provisions projects and their DSNs and is kept in the `dev` layer. CI has its own, `HOLOCRON_SENTRY_RELEASE_TOKEN` in the `ci` layer, which only `release.yml` reads (sentry-cli creates the release and uploads sourcemaps): use an organization token (`org:ci`), not the general one, and no plugin declares it. The Comlink relay has its own, because creating an integration and an alert rule need far more:

| Env var                         | Keyring key      | Used for                                                        | What to create                                                                                                                                                                                                                              |
| ------------------------------- | ---------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HOLOCRON_SENTRY_COMLINK_TOKEN` | `sentry.comlink` | `setup notifications` — the Comlink integration, its alert rule | A **personal** auth token with `org:read`, `org:write`, `project:read`, `project:write`, `alerts:read`, `alerts:write` and `event:read` (an integration can only be made with scopes the token itself holds, and Comlink's is `event:read`) |

It needs no delete or admin permission: setup creates and updates, and never removes. When `sentry.comlink` is not set the relay falls back to the general `sentry` token as the very last resort, which only works if that token happens to carry these scopes.

This token is for the machine that runs `setup notifications`; it is not a Worker secret. Keep it in the keyring (`holocron new token sentry.comlink`) or in your own Holocron environment, never in the `Comlink` 1Password Environment: `sync secrets --env Comlink --worker comlink` pushes every key of that environment to the Worker, and the Worker only needs `COMLINK_<SOURCE>_SECRET` and `COMLINK_<SOURCE>_WEBHOOK`.

```bash
holocron new token sentry.comlink sntryu_xxx
```

`holocron doctor notifications` uses this token too, to read the integration and the alert rule back. It only reads: the integrations, the projects and the alert rules, and never the integration's signing secret. It needs no scope beyond the ones above, but whether a narrower, read-only token would do has not been tried against Sentry.

### Discord

Discord has three separate credentials, each used by a different step, so a leak of one reaches only that step. None is a GitHub token.

| Env var                                                         | Keyring key             | What it is                                             | Used by                                                                      | Get it from                                  |
| --------------------------------------------------------------- | ----------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------- | -------------------------------------------- |
| `HOLOCRON_DISCORD_BOT_TOKEN` (also `DISCORD_BOT_TOKEN`)         | `discord.holonet`       | The bot's token                                        | `setup notifications`, `create-server`, `sync roles`, `doctor notifications` | Developer portal → Bot → **Reset Token**     |
| `HOLOCRON_DISCORD_CLIENT_SECRET` (also `DISCORD_CLIENT_SECRET`) | `discord.holonet.oauth` | The application's OAuth2 client secret                 | `link account` (signing people in)                                           | Developer portal → OAuth2 → **Reset Secret** |
| `HOLOCRON_NOTIFY_WEBHOOK_<CHANNEL>` (a GitHub secret)           | _(none)_                | A channel's webhook URL; anyone with it can post there | Workflows posting to a channel; the delivery check in `doctor notifications` | Created and stored by `setup notifications`  |

The bot token and the client secret look alike and are not interchangeable.

**What the bot needs in the server.** `setup` and `create-server` need View Channels, Send Messages, Read Message History, Manage Channels, Manage Roles, Manage Webhooks, Manage Server, Create Public Threads, Create Private Threads and Send Messages in Threads, plus Pin Messages when the layout pins messages. When one is missing, the command prints an invite link that asks for exactly these and updates the bot's role in place. A server the bot creates itself needs none of this while it owns the server.

**What the application needs in the developer portal.** The **Server Members Intent** (switched on by `application.intents.members` in the layout) for `sync roles`, and the redirect `http://localhost:53682/callback` under OAuth2 → Redirects for `link account`. Making the bot public, and the verification review, stay manual.

**GitHub tokens the Discord steps also use**

| Step                                                   | Token                  | Why                                                                                       |
| ------------------------------------------------------ | ---------------------- | ----------------------------------------------------------------------------------------- |
| `setup` storing webhook URLs and role ids              | `github.secrets` (org) | Writes organization secrets (`HOLOCRON_NOTIFY_*`)                                         |
| `sync roles` reading a team                            | `github.org` (org)     | `members: read` on the organization                                                       |
| `link` and `sync roles` reading/writing the links file | `github.user-sync`     | `contents: read/write` on `.github-private` only; separate so it cannot touch other repos |

Setup order for a new machine is in [Server as Code](/holocron/server-as-code/).

## Storing tokens in the keyring

Run once per machine. Tokens are stored in the OS credential store and retrieved automatically.

```bash
holocron new token github.read    ghp_xxx
holocron new token github.issues  ghp_yyy
holocron new token github.sync    ghp_zzz
holocron new token github.release ghp_aaa
holocron new token github.admin   ghp_bbb
holocron new token github.deploy  ghp_ccc
holocron new token github.org     github_pat_xxx
holocron new token github.secrets github_pat_xxx
holocron new token github.user-sync github_pat_xxx
holocron new token discord.holonet       <bot token>
holocron new token discord.holonet.oauth <client secret>
```

All tokens are stored under keychain service `com.theholocron.cli` with the keyring key as the account name. To retrieve a token manually on macOS:

```bash
security find-generic-password -s "com.theholocron.cli" -a "github.admin" -w
```

Verify, remove, or list stored tokens:

```bash
holocron check token github.admin
holocron remove token github.read
holocron list tokens
```

## CI secrets

In GitHub Actions, map your repository or org secrets to the expected env var names in each workflow's `env:` block:

```yaml
env:
  HOLOCRON_SYNC_TOKEN: ${{ secrets.SYNC_TOKEN }}
  HOLOCRON_RELEASE_TOKEN: ${{ secrets.RELEASE_TOKEN }}
```

### CI-only tokens

These are repository secrets that a workflow reads. Storing one locally is optional. Two should stay out of the keyring: `SENTINEL_OP_SERVICE_ACCOUNT_TOKEN`, because `op` signs in on its own and the CLI has no key for it, and `HOLOCRON_DEPLOYMENTS_TOKEN`, because nothing in the CLI reads it.

| Secret                              | Read by                                                                               | What it is                                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `HOLOCRON_RELEASE_TOKEN`            | `release` (the CLI never resolves it)                                                 | Fine-grained PAT for tags, releases and changelogs. The workflow falls back to `HOLOCRON_SYNC_TOKEN`, then to `github.token` |
| `HOLOCRON_SECRETS_TOKEN`            | `sync-secrets`, passed with `--token github=…`; also the `secrets` capability locally | Organization-owned PAT with only organization **Secrets: read/write**                                                        |
| `HOLOCRON_DEPLOYMENTS_TOKEN`        | `deploy-preview`, through `secrets: inherit`                                          | PAT with only **Deployments: read/write**; creates the GitHub Deployment and posts its status for a PR preview               |
| `VERCEL_TOKEN`                      | `deploy-sentinel`, `sync-secrets`, the preview workflows                              | A Vercel personal access token (Vercel has no separate service token). The same one `holocron new token vercel` stores       |
| `SENTINEL_OP_SERVICE_ACCOUNT_TOKEN` | `sync-secrets`, exposed to `op` as `OP_SERVICE_ACCOUNT_TOKEN`                         | A 1Password **service account** token with read access to the `prod` layer Environment only                                  |
| `HOLOCRON_FERN_TOKEN`               | the `publish-wiki` reusable workflow, which passes it to the Fern CLI as `FERN_TOKEN` | The Fern API token. Password protection is set in the Fern dashboard and needs no token here                                 |

The release workflow is the one place a broader token is used as a fallback. The CLI never falls back from one GitHub feature token to another, except that the `secrets` capability tries `github.secrets` or `github.admin` depending on the scope it writes (see [Organization secrets](#organization-secrets)).

#### Creating a fine-grained PAT for CI

For `HOLOCRON_SECRETS_TOKEN` and `HOLOCRON_DEPLOYMENTS_TOKEN`:

1. Open `github.com/settings/tokens?type=beta` and choose **Generate new token**.
2. **Resource owner**: `theholocron` (the organization, not your account).
3. **Name** it after the secret and say in the description that it is CI-only and what it grants.
4. **Repository access**: irrelevant for `HOLOCRON_SECRETS_TOKEN` (organization secrets are not per repository), so pick "Public repositories". For `HOLOCRON_DEPLOYMENTS_TOKEN` choose the repositories that opt into `deploy-preview`, because that permission is per repository.
5. **Permissions**: only the one in the table (organization Secrets, or repository Deployments), read and write. Leave everything else at "No access".
6. Generate it and store it: `gh secret set <NAME> --repo theholocron/holocron`.

For `VERCEL_TOKEN`, reuse the stored local token without ever printing it:

```bash
security find-generic-password -s "com.theholocron.cli" -a "vercel" -w | gh secret set VERCEL_TOKEN --repo theholocron/holocron
```

macOS asks once to allow the keychain access. A separate CI-only token from `vercel.com/account/tokens` works too.

For `SENTINEL_OP_SERVICE_ACCOUNT_TOKEN`: in the 1Password developer tools create a service account named for CI, give it **Read** access to the `<org>/<repo> - prod` Environment and nothing else, then `gh secret set SENTINEL_OP_SERVICE_ACCOUNT_TOKEN --repo theholocron/holocron`. 1Password documents service accounts reading Environments, but a Feb 2026 community report says `op environment` returned "not found" for one; if it does, run `holocron sync secrets --env prod --cwd apps/sentinel` locally instead.

### Organization secrets

The `secrets` capability (what `sync secrets`, `secret-set` and `setup notifications` write through) picks its token by the scope it writes:

| Scope written                   | Token tried first                                   | Falls back to                                   |
| ------------------------------- | --------------------------------------------------- | ----------------------------------------------- |
| **organization** (`org=<name>`) | `HOLOCRON_SECRETS_TOKEN` / keyring `github.secrets` | `HOLOCRON_ADMIN_TOKEN` / keyring `github.admin` |
| repository, environment         | `HOLOCRON_ADMIN_TOKEN` / keyring `github.admin`     | `HOLOCRON_SECRETS_TOKEN` / `github.secrets`     |

An explicit `--token` serves every scope, and a setup with only one of the two tokens keeps working. They are separate because `github.admin` is a repository-scoped PAT, while an organization secret needs an organization-owned credential with organization **Secrets: read/write**, which no other token carries. Keeping that permission off `github.admin` keeps its blast radius small.

# Bare form: fallback for all plugins
