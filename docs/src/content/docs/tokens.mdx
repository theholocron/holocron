Holocron uses one Personal Access Token per capability group. Each token carries only the scopes its operations require — a leaked token's blast radius is contained to that feature alone.

## GitHub feature token resolution

For GitHub feature tokens (`HOLOCRON_READ_TOKEN`, `HOLOCRON_ADMIN_TOKEN`, etc.), the chain is:

```text
--token flag
→ HOLOCRON_<FEATURE>_TOKEN (feature-specific env var)
→ keyring("github.<feature>") (stored via `holocron auth set`)
```

No broad-token fallback. If none of the above is set, the command exits with an error naming the exact env var to configure. One command is looser: `sync-wiki` also accepts `GH_TOKEN` and `GITHUB_TOKEN` after `HOLOCRON_READ_TOKEN`, so it works in a GitHub Actions job with no extra setup.

## Provider token resolution

For every other provider plugin (Axiom, Cloudflare, Sentry, Slack, Vercel, etc.), tokens are resolved in this order:

```text
--token flag
  → the plugin's own env var    (e.g. HOLOCRON_CLOUDFLARE_TOKEN)
  → the vendor's native env var (e.g. CLOUDFLARE_API_TOKEN)
  → keyring("<provider>.<org>") (org-scoped — only when an org is active)
  → keyring("<provider>")       (unnamespaced fallback)
```

Both env var names for every plugin are in the [provider table](#provider-tokens). Not every plugin follows the `HOLOCRON_<PROVIDER>_TOKEN` pattern: Neon and Postman use `_API_KEY`, and Clerk uses `_SECRET_KEY`.

The org-scoped keyring step fires when an org name is active. Org resolution order:

1. `--org <name>` CLI flag — per-invocation override
2. `HOLOCRON_ORG` env var — set in shell profile, `.envrc`, or CI secret
3. `org` field in `holocron.config.ts` — automatic for projects that declare it

This lets a single machine hold separate credentials for multiple GitHub orgs without collision:

```bash
# Store per-org credentials once
holocron auth set cloudflare --org theholocron <TOKEN-A>
holocron auth set cloudflare --org client-co   <TOKEN-B>

# theholocron project (org: "theholocron" in config) → picks up TOKEN-A automatically
cd ~/Code/theholocron/some-project && holocron repo setup

# client-co project (org: "client-co" in config) → picks up TOKEN-B automatically
cd ~/Code/client-co/some-project && holocron repo setup

# One-off override
holocron repo setup --org client-co
```

## GitHub tokens

| Env var                    | Keyring key        | Type               | Used by                                                                                                                                                    | Required scopes                                                                                                                                                                                                                                                                      |
| -------------------------- | ------------------ | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `HOLOCRON_READ_TOKEN`      | `github.read`      | Fine-grained       | `clone` (lists the org's repos, so the resource owner is the org), `sync-wiki`, CI run listing                                                             | `contents: read`, `actions: read`, `metadata: read`                                                                                                                                                                                                                                  |
| `HOLOCRON_ISSUES_TOKEN`    | `github.issues`    | Fine-grained       | `issues` capability (create, transition, comment)                                                                                                          | `issues: read/write`, `metadata: read`                                                                                                                                                                                                                                               |
| `HOLOCRON_SYNC_TOKEN`      | `github.sync`      | Fine-grained       | `sync github` — push workflow templates, open PRs; the release workflow's dispatch of `sync-dispatch.yml` on `.github`                                     | `actions: read/write`, `contents: read/write`, `pull_requests: read/write`, `workflows: read/write`                                                                                                                                                                                  |
| `HOLOCRON_RELEASE_TOKEN`   | `github.release`   | Fine-grained       | semantic-release: tags, releases, changelogs                                                                                                               | `contents: read/write`, `issues: read/write`, `pull_requests: read/write`                                                                                                                                                                                                            |
| `HOLOCRON_ADMIN_TOKEN`     | `github.admin`     | Fine-grained       | `setup` — repo settings, topics, branch protection, rulesets, security toggles, labels, custom property values, environments, repo and environment secrets | `administration: read/write`, `secrets: read/write`, `environments: read/write`, `issues: read/write` (labels), `custom_properties: write` (property values), `actions_variables: read/write` (Actions variables), `pull_requests: read` (only `cleanup-preview`, on a private repo) |
| `HOLOCRON_SECRETS_TOKEN`   | `github.secrets`   | Fine-grained (org) | the `secrets` capability — **organization**-scoped secret writes (repo and environment scopes prefer `github.admin`)                                       | Resource owner: org · Organization `secrets: read/write`                                                                                                                                                                                                                             |
| `HOLOCRON_DEPLOY_TOKEN`    | `github.deploy`    | Fine-grained       | `setup` — GitHub Pages (build type, custom domain, HTTPS)                                                                                                  | `pages: read/write`, `administration: read/write` (GitHub refuses the Pages settings calls without it), `metadata: read`                                                                                                                                                             |
| `HOLOCRON_ORG_TOKEN`       | `github.org`       | Fine-grained (org) | `setup` — team sync, organization Actions variables; `sync-roles` — read a team's members                                                                  | Resource owner: org · `administration: write` · `members: read` · organization `variables: read/write`                                                                                                                                                                               |
| `HOLOCRON_USER_SYNC_TOKEN` | `github.user-sync` | Fine-grained       | `notifications link` and `sync-roles` — read and write the files that link GitHub accounts to members of other services                                    | Resource owner: org · Repository: **only** `.github-private` · `contents: read/write`                                                                                                                                                                                                |

Two tokens have a quiet fallback: when `HOLOCRON_USER_SYNC_TOKEN` is not set, the links files are read and written with `HOLOCRON_ORG_TOKEN`, then `HOLOCRON_ADMIN_TOKEN`; and `sync-roles` reads a team with `HOLOCRON_ORG_TOKEN`, falling back to `HOLOCRON_ADMIN_TOKEN`. The separate tokens exist so that neither has to be that broad.

### Why a separate org token?

Fine-grained PATs have two resource owner modes: **personal** (your repos) and **organization** (org repos). Team management and reading a team's members require a PAT whose resource owner is the org. `HOLOCRON_ORG_TOKEN` covers these; `HOLOCRON_ADMIN_TOKEN` covers the repo-scoped operations, including a repo's custom property values.

### Discord

Discord has three separate credentials, each used by a different step, so a leak of one reaches only that step. None is a GitHub token.

| Env var                                                         | Keyring key             | What it is                                             | Used by                                                                      | Get it from                                  |
| --------------------------------------------------------------- | ----------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------- | -------------------------------------------- |
| `HOLOCRON_DISCORD_BOT_TOKEN` (also `DISCORD_BOT_TOKEN`)         | `discord.holonet`       | The bot's token                                        | `notifications setup`, `create-server`, `sync-roles`, `doctor notifications` | Developer portal → Bot → **Reset Token**     |
| `HOLOCRON_DISCORD_CLIENT_SECRET` (also `DISCORD_CLIENT_SECRET`) | `discord.holonet.oauth` | The application's OAuth2 client secret                 | `notifications link` (signing people in)                                     | Developer portal → OAuth2 → **Reset Secret** |
| `HOLOCRON_NOTIFY_WEBHOOK_<CHANNEL>` (a GitHub secret)           | _(none)_                | A channel's webhook URL; anyone with it can post there | Workflows posting to a channel; the delivery check in `doctor notifications` | Created and stored by `notifications setup`  |

The bot token and the client secret look alike and are not interchangeable.

**What the bot needs in the server.** `setup` and `create-server` need View Channels, Send Messages, Read Message History, Manage Channels, Manage Roles, Manage Webhooks, Manage Server, Create Public Threads, Create Private Threads and Send Messages in Threads, plus Pin Messages when the layout pins messages. When one is missing, the command prints an invite link that asks for exactly these and updates the bot's role in place. A server the bot creates itself needs none of this while it owns the server.

**What the application needs in the developer portal.** The **Server Members Intent** (switched on by `application.intents.members` in the layout) for `sync-roles`, and the redirect `http://localhost:53682/callback` under OAuth2 → Redirects for `notifications link`. Making the bot public, and the verification review, stay manual.

**GitHub tokens the Discord steps also use**

| Step                                                   | Token                  | Why                                                                                       |
| ------------------------------------------------------ | ---------------------- | ----------------------------------------------------------------------------------------- |
| `setup` storing webhook URLs and role ids              | `github.secrets` (org) | Writes organization secrets (`HOLOCRON_NOTIFY_*`)                                         |
| `sync-roles` reading a team                            | `github.org` (org)     | `members: read` on the organization                                                       |
| `link` and `sync-roles` reading/writing the links file | `github.user-sync`     | `contents: read/write` on `.github-private` only; separate so it cannot touch other repos |

Setup order for a new machine is in [Server as Code](/holocron/server-as-code/).

## Storing tokens in the keyring

Run once per machine. Tokens are stored in the OS credential store and retrieved automatically.

```bash
holocron auth set github.read    ghp_xxx
holocron auth set github.issues  ghp_yyy
holocron auth set github.sync    ghp_zzz
holocron auth set github.release ghp_aaa
holocron auth set github.admin   ghp_bbb
holocron auth set github.deploy  ghp_ccc
holocron auth set github.org     github_pat_xxx
holocron auth set github.secrets github_pat_xxx
holocron auth set github.user-sync github_pat_xxx
holocron auth set discord.holonet       <bot token>
holocron auth set discord.holonet.oauth <client secret>
```

All tokens are stored under keychain service `com.theholocron.cli` with the keyring key as the account name. To retrieve a token manually on macOS:

```bash
security find-generic-password -s "com.theholocron.cli" -a "github.admin" -w
```

Verify, remove, or list stored tokens:

```bash
holocron auth check github.admin
holocron auth unset github.read
holocron auth list
```

## CI secrets

In GitHub Actions, map your repository or org secrets to the expected env var names in each workflow's `env:` block:

```yaml
env:
  HOLOCRON_SYNC_TOKEN: ${{ secrets.SYNC_TOKEN }}
  HOLOCRON_RELEASE_TOKEN: ${{ secrets.RELEASE_TOKEN }}
```

### CI-only tokens

These are repository secrets that a workflow reads. Storing one locally is optional. Two should stay out of the keyring: `SENTINEL_DOPPLER_TOKEN`, because the `doppler` key holds your personal login and a read-only service token would overwrite it, and `HOLOCRON_DEPLOYMENTS_TOKEN`, because nothing in the CLI reads it.

| Secret                       | Read by                                                                                           | What it is                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `HOLOCRON_RELEASE_TOKEN`     | `delivery.publish` (the CLI never resolves it)                                                    | Fine-grained PAT for tags, releases and changelogs. The workflow falls back to `HOLOCRON_SYNC_TOKEN`, then to `github.token` |
| `HOLOCRON_SECRETS_TOKEN`     | `sentinel.secretsSync.yml`, passed with `--token github=…`; also the `secrets` capability locally | Organization-owned PAT with only organization **Secrets: read/write**                                                        |
| `HOLOCRON_DEPLOYMENTS_TOKEN` | `delivery.previewDeploy`, through `secrets: inherit`                                              | PAT with only **Deployments: read/write**; creates the GitHub Deployment and posts its status for a PR preview               |
| `VERCEL_TOKEN`               | `sentinel.deploy.yml`, `sentinel.secretsSync.yml`, the preview workflows                          | A Vercel personal access token (Vercel has no separate service token). The same one `holocron auth set vercel` stores        |
| `SENTINEL_DOPPLER_TOKEN`     | `sentinel.secretsSync.yml`, exposed to the CLI as `DOPPLER_TOKEN`                                 | A Doppler **service token** for the `sentinel` project's `prd` config, **read** access only                                  |
| `HOLOCRON_FERN_TOKEN`        | the `wiki` reusable workflow, which passes it to the Fern CLI as `FERN_TOKEN`                     | The Fern API token. Password protection is set in the Fern dashboard and needs no token here                                 |

The release workflow is the one place a broader token is used as a fallback. The CLI never falls back from one GitHub feature token to another, except that the `secrets` capability tries `github.secrets` or `github.admin` depending on the scope it writes (see [Organization secrets](#organization-secrets)).

#### Creating a fine-grained PAT for CI

For `HOLOCRON_SECRETS_TOKEN` and `HOLOCRON_DEPLOYMENTS_TOKEN`:

1. Open `github.com/settings/tokens?type=beta` and choose **Generate new token**.
2. **Resource owner**: `theholocron` (the organization, not your account).
3. **Name** it after the secret and say in the description that it is CI-only and what it grants.
4. **Repository access**: irrelevant for `HOLOCRON_SECRETS_TOKEN` (organization secrets are not per repository), so pick "Public repositories". For `HOLOCRON_DEPLOYMENTS_TOKEN` choose the repositories that opt into `delivery.previewDeploy`, because that permission is per repository.
5. **Permissions**: only the one in the table (organization Secrets, or repository Deployments), read and write. Leave everything else at "No access".
6. Generate it and store it: `gh secret set <NAME> --repo theholocron/holocron`.

For `VERCEL_TOKEN`, reuse the stored local token without ever printing it:

```bash
security find-generic-password -s "com.theholocron.cli" -a "vercel" -w | gh secret set VERCEL_TOKEN --repo theholocron/holocron
```

macOS asks once to allow the keychain access. A separate CI-only token from `vercel.com/account/tokens` works too.

For `SENTINEL_DOPPLER_TOKEN`: in Doppler open the `sentinel` project → `prd` config → **Access** → **Service Tokens**, generate one named for CI with **Read** access, then `gh secret set SENTINEL_DOPPLER_TOKEN --repo theholocron/holocron`.

### Organization secrets

The `secrets` capability (what `secrets sync`, `secret-set` and `notifications setup` write through) picks its token by the scope it writes:

| Scope written                   | Token tried first                                   | Falls back to                                   |
| ------------------------------- | --------------------------------------------------- | ----------------------------------------------- |
| **organization** (`org=<name>`) | `HOLOCRON_SECRETS_TOKEN` / keyring `github.secrets` | `HOLOCRON_ADMIN_TOKEN` / keyring `github.admin` |
| repository, environment         | `HOLOCRON_ADMIN_TOKEN` / keyring `github.admin`     | `HOLOCRON_SECRETS_TOKEN` / `github.secrets`     |

An explicit `--token` serves every scope, and a setup with only one of the two tokens keeps working. They are separate because `github.admin` is a repository-scoped PAT, while an organization secret needs an organization-owned credential with organization **Secrets: read/write**, which no other token carries. Keeping that permission off `github.admin` keeps its blast radius small.

## Explicit override

```bash
# Bare form: fallback for all plugins
holocron clone --token ghp_xxx --org theholocron

# Keyed form: target a specific provider
holocron sync github --token github=ghp_zzz

# Multiple providers
holocron repo setup --token github=ghp_xxx --token vercel=v_yyy
```
