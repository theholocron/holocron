---
title: "notifications setup"
description: Apply the server layout a notifications provider declares in holocron.config.ts.
---

```bash
holocron notifications setup [--scope <scope>] [--provider <name>] [--dry-run]
```

Reads the `layout` a `notifications` provider declares in `holocron.config.ts` and creates whatever is missing: categories, channels (with their topics), a webhook per channel that asks for one, and roles. Every step looks things up by name first, so re-running it changes nothing that already exists, and `--dry-run` previews it. A step that fails is reported and the rest still run; the command exits non-zero if any did.

## Declaring a layout

```ts
providers: {
  notifications: [
    "discord",
    {
      guildId: "1303969001822486568", // the server id; not a secret
      layout: {
        categories: [
          {
            name: "ALERTS",
            channels: [
              { name: "alerts", topic: "Needs a human", webhook: true },
              { name: "errors" },
            ],
          },
        ],
        roles: [{ name: "gatekeepers", mentionable: true }],
      },
    },
  ],
}
```

A role can carry a `secret` too (`roles: [{ name: "gatekeepers", mentionable: true, secret: "HOLOCRON_NOTIFY_ALERT_ROLE" }]`): the command stores the role's id there, so a workflow can ping the role without anyone copying the id by hand. The id is not sensitive; it is a secret only because the token that writes the webhook secrets can write it too.

A role can also declare how it looks and what it may do: `color` (`#rrggbb`), `hoist` (show its members as their own group in the member list) and `permissions` (the provider's own names, for Discord `ViewChannel`, `SendMessages` and so on). The permission list is exact: a permission not named is not granted. Only what the layout states is compared and changed, and the bot can only grant permissions it holds itself.

A category or channel can declare who may see it and post in it with `access`:

```ts
categories: [
  { name: "ALERTS", access: { post: [] }, channels: [/* … */] }, // read-only: bots and webhooks post
  { name: "STAFF", access: { view: ["gatekeepers"] }, channels: [/* … */] }, // hidden from everyone but gatekeepers
];
```

`view` and `post` are each `"everyone"` (the default) or a list of role names from the layout's `roles`. A channel takes its category's access, and stating `view` or `post` on the channel replaces just that field. `setup` writes the permission overwrites explicitly, so the list is exact and replaces any set by hand; it also keeps the bot able to manage and post in a channel it has locked. The server itself is configured by a `server` section, applied last (it names channels, which exist by then):

```ts
server: {
  verification: "medium",          // none | low | medium | high | highest
  defaultNotifications: "mentions", // all | mentions
  contentFilter: "all",            // off | noRoles | all
  systemChannel: "welcome",        // where the provider posts its own notices
  rulesChannel: "rules",
  updatesChannel: "community-updates",
  community: true,                 // welcome screen, onboarding, discovery
  description: "…",
  locale: "en-US",
}
```

Each field you leave out is left alone, and the channels must be in the layout. `community: true` also needs both channels, a `verification` of at least `low` and `contentFilter: "all"`, because Discord refuses to turn community features on otherwise. Changing the server needs the Manage Server permission, which Holonet does not have by default: `setup` then stops with an explanation and a link that re-invites the bot with exactly the permissions it needs (this updates its role in place, so Manage Server can be added without touching the server's role list).

Turning community features on or off is the exception: Discord requires the **Administrator** permission for that, which is more than the bot should keep. `setup` therefore applies every other server setting first, in one request, and community in a second one. The `updatesChannel` goes in that second request when community is being turned on, because Discord refuses it on its own while community is off (it is accepted for any channel once community is on). If that second request is refused, the other settings stay applied and the message offers two ways forward: turn community on once in Discord (Server Settings → Enable Community; `setup` then leaves it alone), or give Holonet Administrator for one run with the link it prints, and re-invite it with the normal link afterwards to take it away. Turning community **off** works the same way, by hand under Server Settings → Community Settings → Disable Community, and `setup` does it before relaxing the settings Discord refuses to lower while community is on.

What a new member sees on joining is declared with `welcome` and `onboarding`, applied after the server settings (they need community features on):

```ts
welcome: {
  description: "Where the Holocron is built…",                  // up to 140 characters
  channels: [                                                    // up to five, in order
    { channel: "rules", description: "How we treat each other", emoji: "📜" },
  ],
},
onboarding: {
  defaultChannels: ["welcome", "rules", "dev"],                  // channels everyone starts with
  prompts: [
    {
      title: "What brings you here?",
      options: [
        { title: "Building with Holocron", emoji: "🛠️", channels: ["dev", "ideas"] },
        { title: "Following releases", channels: ["releases"], roles: ["gatekeepers"] },
      ],
    },
  ],
  // enabled: true,                                              // see below
},
```

Channels and roles are named as in the layout. `setup` changes only what differs and reports it (`updated welcome screen: description, channels`). Each part left out is left alone; a prompt list you do declare is exact, so a question not in it is removed. Onboarding is **not** switched on unless `enabled: true` is set: Discord only allows that with at least 7 default channels, 5 of them open for members to post in, and it answers with its own explanation when the server falls short.

For Discord, "can't post" means the Send Messages permission only. Discord refuses a change to the thread permissions on an existing channel from a bot whose own role lacks them, and Holonet's does, so members can still start threads in a read-only channel until the bot is granted Create Public Threads, Create Private Threads and Send Messages in Threads (for example by re-inviting it with those permissions). Channels that already deny them are read as the same access and left alone, and when `setup` has to change something else on such a channel it carries those denies over untouched.

A role that may `post` must also be in `view` when `view` is a list, or it could not see the channel; `setup` refuses a layout that says otherwise. A channel or category with no `access` anywhere is left alone.

Discord lets the server owner and anyone with the Administrator permission see and post everywhere, whatever the overwrites say, so "hidden from everyone but gatekeepers" means hidden from everyone who is not an administrator. Keep Administrator for the few people who need it. Roles are created first, since access names them; naming a role the layout does not declare is refused before anything is created.

`webhook: true` stores the URL in `HOLOCRON_NOTIFY_WEBHOOK_<CHANNEL>`; `webhook: { name, secret }` overrides the webhook name and the secret name. The command prints each role's id, which is what a workflow needs to ping it.

:::caution
A layout belongs to the server, not to a repo. Put it in **one** repo's config (the one that owns the server), never in a shared preset, or every repo would apply it.
:::

## Options

| Option              | Default | Description                                                      |
| ------------------- | ------- | ---------------------------------------------------------------- |
| `--scope <scope>`   | the org | Webhook secret scope: `repo`, `env=<name>`, or `org=<name>`      |
| `--provider <name>` | —       | Which `notifications` provider, when more than one can provision |
| `--dry-run`         | `false` | Print what would happen without calling the provider             |

## Security

- **Where webhook secrets live.** By default each webhook URL is stored as an **organization** secret visible to **all** repositories, so every repo's workflows can post to the channel. That is the point for shared channels like `sync`, but it means anyone who can run a workflow in the org can read the URL and post to that channel. Use `--scope repo` (or `env=<name>`) to keep a webhook to one repo. A leaked URL is revoked by deleting the webhook in the provider and re-running the command for a new one.
- **The bot token never goes to a custom host.** The Discord plugin only sends it to the real Discord API. A `baseUrl` in the provider options affects posting, not provisioning, unless `unsafeBotBaseUrl: true` is also set (for tests that stub the API).
- **Collisions.** Two channels or roles that would write the same secret (names are compared case-insensitively, as GitHub does; `release-notes` and `release_notes` normalise to the same default) are refused before anything is created; give one a distinct `secret`.
- **Write access is proven first.** Before creating any webhook, the command writes a throwaway secret (`HOLOCRON_NOTIFY_PREFLIGHT_<random>`, a new name every run so it can never overwrite one you have) at the target scope and deletes it, so a token that can read but not write fails before a webhook exists, not after (a webhook's URL is shown once). If the delete is refused, the run stops and names the secret to remove by hand. Names under `HOLOCRON_NOTIFY_PREFLIGHT` are reserved and refused in a layout.
- **Logs stay free of provider bodies.** A failing step shows the provider's response body in the terminal; the structured log records only the plain error.

## Checking it end to end

Run [`holocron doctor notifications`](/holocron/commands/doctor-notifications/) first: it reads the server and the secrets store and tells you, step by step, what matches the layout and what does not. It cannot prove that a message arrives, which is what the manual workflow below is for.

The `platform.notifyCheck` task is a manual workflow (`workflow_dispatch`) that posts one labelled test message to every notification channel, using the real org secrets, and fails the job for any channel whose webhook is missing or rejects the post. A red job names the channel to fix, and one channel failing does not hide the others. The `alerts` message pings the role from `HOLOCRON_NOTIFY_ALERT_ROLE` when it is set. Run it from the Actions tab once the org's `theholocron/.github` has the reusable workflow. Each channel names its own webhook secret (`channels` is a JSON array of `{ name, secret, mention }`), so layouts with custom secret names are checked correctly, and a channel marked `mention` fails if the role id is missing or malformed. Whether Discord lets that role be mentioned is a server-side fact the workflow cannot see; `holocron doctor notifications` (#1098) checks it.

- **An existing role is brought into line.** If a role already exists with a different `mentionable`, `color`, `hoist` or `permissions`, `setup` changes just the fields that differ and prints `updated role … : colour, hoist`. A role that already matches is left alone. Discord only lets a bot edit roles below its own highest role, so keep the bot's role above the ones it manages.
