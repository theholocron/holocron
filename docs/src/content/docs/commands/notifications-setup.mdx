---
title: "notifications setup"
description: Apply the server layout a notifications provider declares in holocron.config.ts.
---

```bash
holocron notifications setup [--scope <scope>] [--provider <name>] [--dry-run]
```

Reads the `layout` a `notifications` provider declares in `holocron.config.ts` and creates whatever is missing: categories, channels (with their topics), a webhook per channel that asks for one, and roles. Every step looks things up by name first, so re-running it changes nothing that already exists, and `--dry-run` previews it. A step that fails is reported and the rest still run; the command exits non-zero if any did.

## Declaring a layout

```ts
providers: {
  notifications: [
    "discord",
    {
      guildId: "1303969001822486568", // the server id; not a secret
      layout: {
        categories: [
          {
            name: "ALERTS",
            channels: [
              { name: "alerts", topic: "Needs a human", webhook: true },
              { name: "errors" },
            ],
          },
        ],
        roles: [{ name: "gatekeepers", mentionable: true }],
      },
    },
  ],
}
```

A role can carry a `secret` too (`roles: [{ name: "gatekeepers", mentionable: true, secret: "HOLOCRON_NOTIFY_ALERT_ROLE" }]`): the command stores the role's id there, so a workflow can ping the role without anyone copying the id by hand. The id is not sensitive; it is a secret only because the token that writes the webhook secrets can write it too.

A role can follow a GitHub team with `team: "<slug>"`: [`holocron notifications sync-roles`](/holocron/commands/notifications-sync-roles/) then gives it to every team member who has linked their account and takes it from linked people who have left. `setup` only creates the role; the membership is that command's job.

A role can also declare how it looks and what it may do: `color` (`#rrggbb`), `hoist` (show its members as their own group in the member list) and `permissions` (the provider's own names, for Discord `ViewChannel`, `SendMessages` and so on). The permission list is exact: a permission not named is not granted. Only what the layout states is compared and changed, and the bot can only grant permissions it holds itself.

A category or channel can declare who may see it and post in it with `access`:

```ts
categories: [
  { name: "ALERTS", access: { post: [] }, channels: [/* … */] }, // read-only: bots and webhooks post
  { name: "STAFF", access: { view: ["gatekeepers"] }, channels: [/* … */] }, // hidden from everyone but gatekeepers
];
```

`view` and `post` are each `"everyone"` (the default) or a list of role names from the layout's `roles`. A channel takes its category's access, and stating `view` or `post` on the channel replaces just that field. `setup` writes the permission overwrites explicitly, so the list is exact and replaces any set by hand; it also keeps the bot able to manage and post in a channel it has locked. The server itself is configured by a `server` section, applied last (it names channels, which exist by then):

```ts
server: {
  verification: "medium",          // none | low | medium | high | highest
  defaultNotifications: "mentions", // all | mentions
  contentFilter: "all",            // off | noRoles | all
  systemChannel: "welcome",        // where the provider posts its own notices
  rulesChannel: "rules",
  updatesChannel: "community-updates",
  community: true,                 // welcome screen, onboarding, discovery
  description: "…",
  locale: "en-US",
}
```

Each field you leave out is left alone, and the channels must be in the layout. `community: true` also needs both channels, a `verification` of at least `low` and `contentFilter: "all"`, because Discord refuses to turn community features on otherwise. Changing the server needs the Manage Server permission, which Holonet does not have by default: `setup` then stops with an explanation and a link that re-invites the bot with exactly the permissions it needs (this updates its role in place, so Manage Server can be added without touching the server's role list).

Turning community features on or off is the exception: Discord requires the **Administrator** permission for that, which is more than the bot should keep. `setup` therefore applies every other server setting first, in one request, and community in a second one. The `updatesChannel` goes in that second request when community is being turned on, because Discord refuses it on its own while community is off (it is accepted for any channel once community is on). If that second request is refused, the other settings stay applied and, with a terminal attached, `setup` walks you through it: it prints the link that gives Holonet Administrator, waits for you to approve it and press Enter, and retries; then it prints the link that takes Administrator away again, waits, and checks that Holonet no longer holds it (a permission still held is reported as a failure, so a forgotten step does not go unnoticed). The approval clicks stay yours, on Discord's own authorization screen. Without a terminal (a script, CI) nothing waits: the message offers the same two ways forward, turn community on once in Discord (Server Settings → Enable Community; `setup` then leaves it alone), or give Holonet Administrator for one run with the link it prints and re-invite it with the normal link afterwards. A server the bot created itself needs none of this, because its owner can do everything. Turning community **off** works the same way, by hand under Server Settings → Community Settings → Disable Community, and `setup` does it before relaxing the settings Discord refuses to lower while community is on.

What a new member sees on joining is declared with `welcome` and `onboarding`, applied after the server settings (they need community features on):

```ts
welcome: {
  description: "Where the Holocron is built…",                  // up to 140 characters
  channels: [                                                    // up to five, in order
    { channel: "rules", description: "How we treat each other", emoji: "📜" },
  ],
},
onboarding: {
  defaultChannels: ["welcome", "rules", "dev"],                  // channels everyone starts with
  prompts: [
    {
      title: "What brings you here?",
      options: [
        { title: "Building with Holocron", emoji: "🛠️", channels: ["dev", "ideas"] },
        { title: "Following releases", channels: ["releases"], roles: ["gatekeepers"] },
      ],
    },
  ],
  // enabled: true,                                              // see below
},
```

Messages that should stay at the top of a channel are declared with `pinned`, applied after the channels exist:

```ts
pinned: [
  { channel: "welcome", content: "Welcome to the Holocron. Start in #rules, then pick your roles." },
],
```

`setup` posts each message and pins it, without letting it mention anyone. A `#name` in the text that is one of the server's channels becomes a clickable link to it; a name that matches no channel, or more than one, stays as written. The layout is the whole set of messages the bot has pinned in a channel it names: a pin that says exactly this is left alone, a pin the layout does not declare (or a second copy of one it does) is removed, and a copy left unpinned by a failed earlier run is pinned instead of posted again. Old pins are removed only after the new one is pinned, except in a channel at Discord's limit of 50 pins, where an obsolete one goes first to make room. Only messages the bot itself posted count, and only among the channel's last hundred messages, so a pin that has scrolled further back than that is not found and would be posted again. Two runs at once can each post the same message; each run keeps the oldest and removes the rest. Pinning needs **Pin Messages** (Discord's own permission; Manage Messages no longer covers it), which Holonet does not have by default. With a terminal attached, `setup` prints the link that adds it, waits for you to approve it and press Enter, and retries (this updates the bot's role in place, and unlike Administrator the permission stays). Without a terminal it stops with the same link in the message. You can also turn it on by hand under Server Settings → Roles → Holonet → Pin Messages. If the role has it but the pin is still refused, a permission override on the channel is taking it away; `setup` says so, and the fix is to remove the override under Edit Channel → Permissions. The text can be up to 2000 characters, and the channel must be one in the layout. Works without community features.

Channels and roles are named as in the layout. `setup` changes only what differs and reports it (`updated welcome screen: description, channels`). Each part left out is left alone; a prompt list you do declare is exact, so a question not in it is removed. Onboarding is **not** switched on unless `enabled: true` is set: Discord only allows that with at least 7 default channels, 5 of them open for members to post in, and it answers with its own explanation when the server falls short.

For Discord, "can't post" means the Send Messages permission only. Discord refuses a change to the thread permissions on an existing channel from a bot whose own role lacks them, and Holonet's does, so members can still start threads in a read-only channel until the bot is granted Create Public Threads, Create Private Threads and Send Messages in Threads (for example by re-inviting it with those permissions). Channels that already deny them are read as the same access and left alone, and when `setup` has to change something else on such a channel it carries those denies over untouched.

A role that may `post` must also be in `view` when `view` is a list, or it could not see the channel; `setup` refuses a layout that says otherwise. A channel or category with no `access` anywhere is left alone.

Discord lets the server owner and anyone with the Administrator permission see and post everywhere, whatever the overwrites say, so "hidden from everyone but gatekeepers" means hidden from everyone who is not an administrator. Keep Administrator for the few people who need it. Roles are created first, since access names them; naming a role the layout does not declare is refused before anything is created.

`testChannel: "<channel>"` names the channel set aside for test posts (it must declare a webhook): [`holocron doctor notifications`](/holocron/commands/doctor-notifications/) leaves one `🧪 test:` message there on a full run to prove delivery works.

`webhook: true` stores the URL in `HOLOCRON_NOTIFY_WEBHOOK_<CHANNEL>`; `webhook: { name, secret }` overrides the webhook name and the secret name. The command prints each role's id, which is what a workflow needs to ping it.

A webhook's picture comes from `webhookAvatar` on the layout (every webhook), or `webhook: { avatar }` (one). Either is a path to a PNG, JPEG or GIF, read from where the CLI runs, or an `https://` URL. WebP is refused, because providers do not take it; convert it first. A picture that cannot be read stops the run before anything is created. The picture is set on a webhook that has none, and an existing one is left alone: Discord stores a hash, not the image, so there is no way to tell whether the one it holds is the same. To change it, remove the picture in Discord and run `setup` again.

:::caution
A layout belongs to the server, not to a repo. Put it in **one** repo's config (the one that owns the server), never in a shared preset, or every repo would apply it.
:::

## Channels fed by another service

A service that has its own alerting can post into a channel directly, without a workflow in between. Declare it on the channel:

```ts
{ name: "uptime", webhook: true, feeds: { monitoring: true } }
```

`setup` gives the channel a **dedicated webhook** for that service (named after the provider, `Checkly` here, or whatever `feeds.monitoring.webhook` says, with the picture `feeds.monitoring.avatar` names, a file path or `https://` URL, or else the layout's `webhookAvatar`; a picture is set only on a webhook that has none, so to change it, delete the webhook and run `setup` again) and hands its URL straight to the monitoring provider as an alert channel named `Message to #uptime` (or `feeds.monitoring.name`). The URL is shown once, so it is never stored in a secret: only the service that needs it has it, and deleting that webhook revokes that service alone and leaves every other webhook untouched.

With Checkly, the alert channel is a webhook formatted for Discord, sending failures, recoveries and degraded notices, and it is subscribed to every check on the account. Checks made through an API are never subscribed on their own, so a check added later is picked up by the next `setup` run. Checkly already labels a channel with its type ("Discord …"), which is why the default name is `Message to #uptime` and does not repeat it. An alert channel with the same name that already exists is adopted and brought in line (a new URL, the missing subscriptions) and keeps its own message template and send settings; nothing is duplicated.

A channel named differently (for example `Discord #uptime` from an earlier version) is not found by name. **Rename it in Checkly to the new default name before running `setup`**; otherwise `setup` makes a second channel for the same webhook and both alert, or, if the webhook's URL cannot be read back, fails because it can neither find a channel to update nor create one. Once renamed, do not run `setup` from an older release: it looks for the old name and will not find the renamed channel.

If the dedicated webhook already exists, its URL cannot be read back, so an existing alert channel keeps the URL it has and only its subscriptions are reconciled. Creating an alert channel that does not exist yet needs a fresh webhook: delete the old webhook in Discord and run `setup` again.

This needs a `monitoring` provider that manages alert channels (`["checkly", { accountId }]`). The checks themselves are declared wherever the service they watch lives; the feed only needs the provider. A `--dry-run` previews the webhook and alert channel and calls nothing.

## Options

| Option              | Default | Description                                                      |
| ------------------- | ------- | ---------------------------------------------------------------- |
| `--scope <scope>`   | the org | Webhook secret scope: `repo`, `env=<name>`, or `org=<name>`      |
| `--provider <name>` | —       | Which `notifications` provider, when more than one can provision |
| `--dry-run`         | `false` | Print what would happen without calling the provider             |

## Security

- **Where webhook secrets live.** By default each webhook URL is stored as an **organization** secret visible to **all** repositories, so every repo's workflows can post to the channel. That is the point for shared channels like `sync`, but it means anyone who can run a workflow in the org can read the URL and post to that channel. Use `--scope repo` (or `env=<name>`) to keep a webhook to one repo. A leaked URL is revoked by deleting the webhook in the provider and re-running the command for a new one.
- **The bot token never goes to a custom host.** The Discord plugin only sends it to the real Discord API. A `baseUrl` in the provider options affects posting, not provisioning, unless `unsafeBotBaseUrl: true` is also set (for tests that stub the API).
- **Collisions.** Two channels or roles that would write the same secret (names are compared case-insensitively, as GitHub does; `release-notes` and `release_notes` normalise to the same default) are refused before anything is created; give one a distinct `secret`.
- **Write access is proven first.** Before creating any webhook, the command writes a throwaway secret (`HOLOCRON_NOTIFY_PREFLIGHT_<random>`, a new name every run so it can never overwrite one you have) at the target scope and deletes it, so a token that can read but not write fails before a webhook exists, not after (a webhook's URL is shown once). If the delete is refused, the run stops and names the secret to remove by hand. Names under `HOLOCRON_NOTIFY_PREFLIGHT` are reserved and refused in a layout.
- **Logs stay free of provider bodies.** A failing step shows the provider's response body in the terminal; the structured log records only the plain error.

## Checking it end to end

Run [`holocron doctor notifications`](/holocron/commands/doctor-notifications/) first: it reads the server and the secrets store and tells you, step by step, what matches the layout and what does not. It cannot prove that a message arrives, which is what the manual workflow below is for.

The `platform.notifyCheck` task is a manual workflow (`workflow_dispatch`) that posts one labelled test message to every notification channel, using the real org secrets, and fails the job for any channel whose webhook is missing or rejects the post. A red job names the channel to fix, and one channel failing does not hide the others. The `alerts` message pings the role from `HOLOCRON_NOTIFY_ALERT_ROLE` when it is set. Run it from the Actions tab once the org's `theholocron/.github` has the reusable workflow. Each channel names its own webhook secret (`channels` is a JSON array of `{ name, secret, mention }`), so layouts with custom secret names are checked correctly, and a channel marked `mention` fails if the role id is missing or malformed. Whether Discord lets that role be mentioned is a server-side fact the workflow cannot see; `holocron doctor notifications` (#1098) checks it.

- **An existing role is brought into line.** If a role already exists with a different `mentionable`, `color`, `hoist` or `permissions`, `setup` changes just the fields that differ and prints `updated role … : colour, hoist`. A role that already matches is left alone. Discord only lets a bot edit roles below its own highest role, so keep the bot's role above the ones it manages.

## The bot application and @everyone

`application` sets what the bot's page in the developer portal says, and `everyone` changes what ordinary members may do. Both are applied last, with the server's settings.

```ts
application: {
  description: "…",                       // up to 400 characters
  tags: ["automation", "github"],         // up to 5, each up to 20 characters
  install: { scopes: ["bot"], permissions: ["ViewChannel", "SendMessages"] },
  termsUrl: "https://…",
  privacyUrl: "https://…",
  roleConnectionsUrl: "https://…",
  intents: { members: true },             // the Server Members Intent, switched on from code
  redirectUris: ["http://localhost:53682/callback"], // checked only: the API cannot set them
},
everyone: { deny: ["MentionEveryone"] },  // only the bits named change
```

`intents.members` switches the Server Members Intent on or off. It is the toggle the portal shows for an app Discord has not verified (`GATEWAY_GUILD_MEMBERS_LIMITED`), and it is what lets `sync-roles` list who holds a role. `redirectUris` is the opposite case: Discord accepts a write to it and silently ignores it, so `setup` and the doctor only **check** that each one is registered, and say what to add under **OAuth2 → Redirects** in the developer portal. A missing one fails the run until it is added.

A field left out is left alone. After each write the plugin reads the application back and fails, naming the field, if Discord did not keep it, so a field the API silently ignores shows up as a failure and not a false success. `everyone` never replaces the whole permission set: it adds what `allow` names and removes what `deny` names, and refuses a permission that is in both.

`install` sets the default install link, and Discord only allows one on a **public** bot. On a private bot the write is refused (`APPLICATION_INSTALL_NEEDS_PUBLIC_INTEGRATION`) and `setup` says so; leave `install` out, and invite the bot with a link you build (`setup` prints one when a permission is missing). Turning on Public Bot lets anyone add the bot to their server, so it is not something `setup` does.

Some things stay in the developer portal because the API does not expose them: whether the bot is public, and the verification review.
