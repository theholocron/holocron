---
title: sync issues
description: Keep the issues on one tracker up to date from another, one direction, without echoing back.
---

```bash
holocron sync issues --from <source> --to <target> [--since <time>] [--limit <n> [--order <oldest|newest>]] [--yes] [--dry-run]
```

`--from` and `--to` are `provider` or `provider:key=value,...`, as for [migrate](/holocron/commands/migrate/), for example `--from github --to linear:team=ENG`. GitHub to Linear and Linear to GitHub are the same command with the ends swapped; run them separately and configure them separately. Two one-way syncs never share state, so an interrupted run on one side cannot leave the other wrong.

Unlike `migrate`, a sync updates what it made. For each issue on the source it finds the issue it made on the target (by the recorded source address) and:

- creates it when it is missing, as `migrate` does;
- sets title, description, state, priority, labels and assignee to what the source has, when they differ;
- adds the comments the target lacks, oldest first. A comment is never edited or deleted.

It writes nothing to the source, ever, and changes a target issue only when a `migrate` or a sync made it (the `holocron:migrated-from` marker on GitHub, the attachment on Linear). An issue someone made on the target by hand is not touched, and one whose marker was edited out is treated as unknown and made again.

| Flag        | Meaning                                                                                                                          |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `--since`   | only issues changed since a date (`2026-03-01`) or a span back from now (`30m`, `12h`, `7d`, `2w`)                               |
| `--limit`   | read at most this many issues from the source, a positive whole number, counted after `--since`; see [A trial run](#a-trial-run) |
| `--order`   | with `--limit`: `oldest` (the default) reads the first created, `newest` the last created; no effect without `--limit`           |
| `--yes`     | do not ask first (a scheduled run needs it; without a terminal the command refuses instead of hanging)                           |
| `--dry-run` | read both sides and write nothing; prints what would be created or updated, and what would not carry across                      |

## Progress

On a terminal, a spinner with a counter shows the read (`Reading issues from github… 12 of 40`) and the write (`Writing to linear… 3 of 20`; `Checking linear…` on a dry run), and is cleared before the result lines and the confirmation question. When the output is piped, in CI or with `--quiet`, nothing extra is printed.

## A trial run

`--limit <n>` reads only `n` issues from the source; `--order oldest` (the default) keeps the first created and `--order newest` the last created. The limit counts issues that survive `--since` and the skipping of pull requests, the order comes from the source's creation time and the cut is made before each issue's comments and links are read. A dry run and a real run print `limited to N of M`. The loop guard drops copies after the read, so it can leave fewer than `N` to sync. A second run with the same limit selects the same issues; to continue, run again with a larger `--limit`, or without one.

## The loop guard

A sync skips any source issue that itself carries a recorded address from the other tracker. An issue copied from GitHub to Linear has a `Migrated from` attachment on Linear, so the Linear to GitHub sync skips it; an issue copied from Linear to GitHub has the marker, so the GitHub to Linear sync skips it. The check is made on the source, before anything is written, and each skipped issue is listed. Running GitHub to Linear and then Linear to GitHub on the same pair creates nothing in either tracker the second time.

## The report

Every issue prints a row (`created`, `updated: title, state`, `unchanged`), then one summary line with the counts:

```text
github to linear: created 3, updated 1, unchanged 40, skipped (guard) 2, left 0
```

and the same `not carried across` list as `migrate`, with one line per loss and the number of issues it hit.

## Effort and dates

Effort, the start date and the target date travel with the issue (`migrate` and `sync` alike). On GitHub they are the organization's `Effort`, `Start date` and `Target date` issue fields; on Linear Effort is the estimate (1 low, 3 medium, 5 high, any other number is no effort) and the target date the due date. Linear has no start date, so it is listed as `startDate (Linear has no start date)`. A target only gets a value the record carries: nothing is ever cleared, and `migrate` writes only to issues it makes, while `sync` sets an issue it made to the source's value when they differ. A field the target lacks, an option it has no `Effort` for or a team with estimates off is a `not carried across` line, never a failure. Not verified against live GitHub or Linear yet.

## Interrupted and rate limited runs

A failure part-way leaves every finished issue correct, and the next run continues. A provider rate limit stops the run cleanly: the issues not reached are the `left` count, and running it again does them. A write that errored is not repeated inside the run, so an errored create cannot become two issues.

## Running it on a schedule

The `sync-issues` task runs this command every hour (`ci.sync-issues.yml`, from the reusable `sync-issues.yml`) in a repo whose `tasks:` lists it. Its `with:` inputs are the command's endpoints:

```ts
tasks: [{ name: "sync-issues", with: { from: "github", to: "linear:team=ENG", both: true } }];
```

| Input   | Meaning                                                                           |
| ------- | --------------------------------------------------------------------------------- |
| `from`  | where the issues are read from (required)                                         |
| `to`    | where they are written (required)                                                 |
| `since` | only issues changed since then (default `2d`)                                     |
| `both`  | also run the swapped direction after the first, in the same job (default `false`) |

The job reads the Linear key from the `HOLOCRON_LINEAR_TOKEN` secret and GitHub's from `HOLOCRON_ISSUES_TOKEN`, or the job's own token when that is not set. A repo with one tracker lists nothing and gets no workflow; this repo does not list it. A failed run reaches `#alerts`.

## The assignees file

A GitHub login and a Linear account are not the same name, so the pairs live in a file in the org's private config repo, next to the Discord links file (`<org>/.github-private`, `issues/assignees.json`). Nobody signs in to write it, since both trackers are readable by the org: a maintainer edits it by hand.

```json
{ "version": 1, "links": [{ "login": "octocat", "email": "octo@acme.dev" }] }
```

`sync issues` reads it once, through the `source` provider, and only when a record has an assignee. Going to GitHub, a Linear user is found by email and the issue is assigned to the login; going to Linear, a GitHub login is found and the issue is assigned to the user with that email. A login or an email may appear once. A missing file means nobody is mapped; a file that is not valid fails the run before anything is written, naming the file.

## Limits

- **Assignees** are carried across by the assignees file (below). A person the file does not name is matched by email on Linear, and on GitHub is left unassigned and reported as `assignee (not mapped)`, since a Linear user carries no GitHub login. A source with no assignee leaves the target's assignee alone, and an assignee is never cleared.
- **Labels** on the target are set to the source's. A label added by hand to a synced Linear issue is removed by the next run; GitHub `status:*` labels are kept.
- **Priority** on GitHub is the `priority: <level>` label, as in `migrate`.
- A comment edited on the source after it was copied is not copied again. A comment deleted on the target is added back.
- A source issue that is deleted leaves its copy in place. An issue moved between teams on Linear is new on the next run.
- Two syncs running at once on the same pair can make a duplicate, so the scheduled task runs the two directions one after the other in one job.

A provider takes part as a source with `export` and as a target with the optional `sync` method of the `issues` capability. GitHub and Linear have both.
