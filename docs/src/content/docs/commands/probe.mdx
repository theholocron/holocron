---
title: "probe"
description: Poke a live provider on purpose, to inspect it or to prove something works end to end.
---

```bash
holocron probe                          # on a terminal: a menu of every provider and probe; otherwise the list
holocron probe <provider>               # list one provider's probes
holocron probe <provider> <probe> [<argument>...] [--dry-run] [--yes] [--lcov <path>]
```

A probe is a small, named check that talks to a real provider: _which integrations does Sentry have, and what do they allow?_ or _does a failing check reach #uptime?_ It is for the questions you would otherwise answer with a throwaway script. It is not [`doctor`](/holocron/commands/doctor/), which compares what `holocron.config.ts` declares with what exists; a probe has no layout to compare against.

On a terminal, `holocron probe` opens a menu: pick a provider, then a probe (a probe that changes things is marked, and offers a dry-run preview first). From the top-level `holocron` menu, choose `probe`. In a pipe or CI it prints the same list as plain text.

Probes come from the plugins your config names (a plugin offers them next to its capabilities), plus the CLI's own `core` group. `holocron probe core providers` lists which capabilities loaded and, for any that did not, why, then each provider with the probes it offers. Other commands skip a provider that fails to load without saying so.

## The rules every probe follows

- **Nothing secret is printed.** Output passes through one filter: the tokens in use, anything a probe marks as secret, and anything shaped like a credential (a Discord webhook URL, a `Bearer` header, a Sentry token) is replaced with `«hidden»`. A probe reports facts such as "secret visible: false", never the value.
- **A probe that changes things says so.** `holocron probe` marks it `(changes things)`. It asks before it runs, and without a terminal it needs `--yes`.
- **`--dry-run` is enforced.** A probe changes things only through `write`, which on a dry run prints `would <what>` and does nothing.
- **It cleans up.** What a probe makes, it removes again: when it succeeds, when it fails and on Ctrl-C. A clean-up that fails is reported as a failure.
- **Exit code 1** if any row fails.

## Options

| Option      | Default | Description                                                                                                    |
| ----------- | ------- | -------------------------------------------------------------------------------------------------------------- |
| `--dry-run` | `false` | Show what a probe that changes things would do, without doing it                                               |
| `--yes`     | `false` | Run a probe that changes things without asking first (required without a terminal)                             |
| `--lcov`    | none    | Also write the coverage a [`docs`](#documentation) probe measures to this lcov file, relative to the repo root |

## Connection, for every provider

Every provider offers `connection` (for example `holocron probe github connection`). It is the first thing to run when something fails and you do not know whether the cause is the network or the credential. It checks, in order, and reports each step:

| Step           | What it tells you                                                                                                                                                                                                                                              |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DNS <host>`   | The name resolves, and to which address. Fails with the cause (`ENOTFOUND`, `EAI_AGAIN`).                                                                                                                                                                      |
| `reach <host>` | The host answers over TLS, and how fast. Any HTTP answer counts, even a 401. Fails with the cause: a timeout (firewall, VPN or proxy), a refused or reset connection, or an untrusted certificate (a proxy that re-signs traffic needs `NODE_EXTRA_CA_CERTS`). |
| `token`        | A token was found, and where to put one if not. The value is never printed.                                                                                                                                                                                    |
| `accepted`     | The provider accepts the token, and who it belongs to. Not tried when an earlier step failed, so one cause is reported once.                                                                                                                                   |

1Password has no API host of its own (`op` signs in by itself), so it checks that `op` is installed and signed in. Fern has no way to check a token, so it only checks that one is set.

## Sentry

These use the same token as the Comlink relay (`sentry.comlink`, the general Sentry token as a last resort) and the `org` of the `sentry` provider.

| Probe                                | Changes things | What it shows                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `holocron probe sentry integrations` | no             | Each custom integration: scopes, whether its alert action is on, where its webhook points (host and path only) and whether the client secret is visible to the token. Never the secret                                                                                                                                                                                 |
| `holocron probe sentry rules`        | no             | Each alert rule: enabled or not, how many projects it covers and what each action sends to. A rule using the old `sentry_app` action, or naming something that is not an alertable integration, fails                                                                                                                                                                  |
| `holocron probe sentry rule-update`  | yes            | Makes a disabled alert rule with nothing to send, changes its frequency from 5 to 10 with the same `PUT` the relay's adopt path uses, reads it back and deletes it, even if a step fails or you press Ctrl-C. It hangs on the issue stream of the project named in `HOLOCRON_SENTRY_PROBE_PROJECT`, else of any project. Needs the token to be allowed to write alerts |
| `holocron probe sentry send-error`   | yes            | Sends one labelled test error (`HolocronProbeError`) so you can follow it through the rule to #errors. The target is `SENTRY_DSN`, or the first client key of the project named in `HOLOCRON_SENTRY_PROBE_PROJECT`. A probe cannot delete a Sentry issue, so resolve it by hand                                                                                        |

## Checkly

These use the `checkly` provider's token and `accountId`, and the Discord alert channel `notifications setup` makes (`Message to #uptime`; set `HOLOCRON_CHECKLY_PROBE_CHANNEL` to use another).

| Probe                            | Changes things | What it does                                                                                                                                                                                                                                                                                                                                |
| -------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `holocron probe checkly channel` | no             | Where the channel posts (host only), whether its template is the shipped one, and how many of the account's checks use it. Fails with the command that fixes it                                                                                                                                                                             |
| `holocron probe checkly deliver` | yes            | Makes a throwaway API check (`https://example.com`, every 5 minutes) that must fail, subscribes it to the channel, waits until Checkly sees it fail, tells you to look for the red embed in #uptime, then makes it pass and waits for the recovery and the green embed. Takes 10 to 20 minutes. The check is always deleted, also on Ctrl-C |

`deliver` removes a check of its own that an earlier run left behind (it is found by name and the `delivery-proof` tag), and refuses to touch a check with that name that lacks the tag. It reports what Checkly sees; whether the embed arrived in Discord is for you to check, since the probe cannot read the channel.

## Comlink

The relay Worker (`apps/comlink`) is an app, not a provider, so these are the CLI's own. They find the relay in the notifications layout (`relay.host`) and the source from the `errors` provider (`sentry`).

| Probe                             | Changes things | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `holocron probe comlink unsigned` | no             | Sends the relay requests it must refuse and checks the answers: a `GET` is 405, an unsigned `POST` is 401 and an unknown source is 404. A 404 on the real source means the Worker is not deployed on that host                                                                                                                                                                                                                                                    |
| `holocron probe comlink bindings` | no             | Whether the Worker has `COMLINK_SENTRY_WEBHOOK` and `COMLINK_SENTRY_SECRET`, by name, and which other secrets it holds. Never the values. Needs a `workers` provider that can list secrets (Cloudflare can)                                                                                                                                                                                                                                                       |
| `holocron probe comlink deliver`  | yes            | Sends the relay a correctly signed test alert, so an embed titled `Holocron probe: Comlink delivery check` lands in #errors. It needs the signing secret. It reads it from `COMLINK_SENTRY_SECRET` if set, else from the vault in the app's own config (`apps/comlink/holocron.config`, found from the Worker's `relay.code`, so with your Doppler token from the keyring and no `doppler run`), else from the repo's vault. The message stays; delete it by hand |

## Dependencies

The `deps` group is the CLI's own, like `core` and `comlink`. It reads every workspace `package.json` and `pnpm-workspace.yaml` live on each run (nothing is cached or generated) and checks them against the catalog rule written at the top of `pnpm-workspace.yaml`: a dependency used by two or more groups (a top-level folder) is in the default `catalog:`, one used by a single group is in that group's named catalog (`catalog:configs`), peer ranges stay out of catalogs, and a package that lives in this repo is linked with `workspace:`.

| Probe                            | Changes things | What it does                                                                                                                                  |
| -------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `holocron probe deps report`     | no             | Prints a markdown report of every dependency, its catalog and range, and how widely it is used                                                |
| `holocron probe deps who <name>` | no             | Lists the packages that use the dependencies whose name contains `<name>`, by group, with how (`prod`, `dev`, `peer`)                         |
| `holocron probe deps check`      | no             | Fails for each hard-coded version, workspace package pinned to a version, dependency in the wrong catalog or unused catalog entry. CI runs it |

CI runs `holocron probe deps check` on every pull request (the `Dependency catalogs / Check` required check).

## Documentation

The `docs` group is the CLI's own as well. It measures how much of each public package's exported API carries a doc comment: functions, classes, interfaces, type aliases, constants, enums and the public members of those, read with the repo's TypeDoc from each package's entry point (`src/index.ts`, or `index.ts`). TSDoc comments are the source of truth for the API reference, so this is the number that says how complete it is. A symbol that a package re-exports from another one is measured in its own package: when TypeDoc sees it only through the other package's `dist/` declarations, which lose the comments on inline members, it is left out.

| Probe                          | Changes things | What it does                                                                                                                                    |
| ------------------------------ | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `holocron probe docs coverage` | no             | Prints each package's documented share and the total                                                                                            |
| `holocron probe docs patch`    | no             | Fails for each export a PR adds or changes without a doc comment (against `BASE_SHA`, or `origin/alpha`). Old undocumented exports do not count |
| `holocron probe docs lcov`     | yes            | Writes `coverage/docs.lcov`, one line per exported symbol (hit when it has a doc comment)                                                       |

`docs patch` follows [`repoValidation.docsCoverage`](/holocron/config/#doc-comment-coverage): `off` (the default) skips it, `warn` reports each miss without failing, `required` fails. The other two always run.

`--lcov <path>` adds that report to `docs coverage` and `docs patch` from the same measurement, without the prompt `docs lcov` needs: `docs patch --lcov coverage/docs.lcov` gates a PR and writes the file in one pass, and `docs patch` without it measures only the packages the PR touched. On `--dry-run` nothing is written.

CI runs the `Docs coverage` workflow on every pull request and on pushes to `alpha`. It runs `docs coverage --lcov`, which measures every package and writes the report without failing, and uploads the file to Codecov as the `documentation` flag, so `codecov/patch/documentation` and `codecov/project/documentation` show next to the test coverage. They are separate from `codecov/patch` and `codecov/project`, which count only the tests. In this repo `codecov/patch/documentation` is a required check (it is listed in `extraRequiredChecks`, and `holocron repo setup` writes it into the ruleset); `codecov/project/documentation` is not. The probe no longer gates in CI: the Codecov status does, and `docs patch` stays in the CLI for a person to run before pushing (#1511).

## CI references

The `ci` group is the CLI's own. `ci refs` counts the references to the reusable workflows and composite actions hosted in the org's `.github` repository, across every active repository of the org (templates and the org site included). It shallow-clones each one with `gh` and searches the files, because GitHub code search skips repositories that are not indexed. It is the exit test for removing the forwarding shims in `.github`: they can go when the count outside `.github` is zero.

| Probe                          | Changes things | What it does                                                                                                  |
| ------------------------------ | -------------- | ------------------------------------------------------------------------------------------------------------- |
| `holocron probe ci refs [max]` | no             | Counts the references per repository, split into workflow, action and other. Fails when above `max`, if given |
| `holocron probe ci ref-list`   | no             | Prints every reference with its file and line                                                                 |

It needs `gh` signed in with read access to the org, and a config that names the org.

## Generated files

The `generated` group is the CLI's own too. `holocron repo setup` writes a set of files from the config alone (the thin-caller workflows, the lint and editor configs, the git hooks, `codecov.yml`, `turbo.json` and the edits that go with it), and `holocron repo sync` writes the workflows and `turbo.json` from the same function. `generated check` runs that function with no provider and no token, so it works in CI, and compares what it makes with the committed files.

| Probe                            | Changes things | What it does                                                                                                                                                                                                                                                                                                            |
| -------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `holocron probe generated check` | no             | Fails for each generated file that is missing or differs from the committed copy, for each file whose second generation differs from the first, and for each workflow in `.github/workflows` that nothing generates and that is not marked `# HAND-MAINTAINED`. The fix for a difference is `repo setup` or `repo sync` |

A workflow that another package's config generates (its `# Source package:` marker is not `.`) is left to that package. `platform.syncTemplates.yml`, which is committed ahead of its task on purpose, is the one named exception (`UNMANAGED_WORKFLOWS`). Not covered: `.github/CODEOWNERS` (it needs the organization from the provider), the installed skills, the agent prompts and the engineering structure.

CI runs `holocron probe generated check` on every pull request (the `Generated files / Check` required check, `.github/workflows/sourceQuality.generatedFiles.yml`).

## Writing a probe

A plugin returns `probes` from `createPlugin`, next to `capabilities`. The probe closes over the plugin's own token and client.

```ts
import type { PluginProbes } from "@theholocron/cli";

export function probes(ctx: PluginContext): PluginProbes {
  return {
    integrations: {
      summary: "List the custom integrations, their scopes and whether their secret is visible.",
      writes: false,
      async run(probe) {
        for (const app of await ctx.client().sentryApps.list(ctx.options.org!)) {
          probe.secret(app.clientSecret);
          probe.say({ status: "info", label: app.name, detail: `scopes: ${app.scopes.join(", ")}` });
        }
      },
    },
  };
}
```

Use `probe.write(label, fn)` for anything that changes the provider, `probe.cleanup(label, fn)` right after making something so it is undone, and declare `writes: true`. A probe that did not declare `writes` cannot call `write`.
