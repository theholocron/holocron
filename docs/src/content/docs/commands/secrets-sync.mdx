---
title: "secrets sync"
description: Read a vault environment and fan KEY=VALUE pairs out to CI secrets and deployment env vars.
---

```bash
holocron secrets sync <environmentId> [--project-id <id>] [--target production preview] [--dry-run]
```

Pulls all secrets from a vault environment and fans them out to:

- **CI secrets** via the `secrets` capability (e.g. GitHub Actions secrets)
- **Deployment env vars** via the `deployment` capability (e.g. Vercel env vars) when `--project-id` is provided
- **A Worker's secrets** via the `workers` capability when `--worker <script>` is given. The Worker must already be deployed; the values are write-only and never printed

This is the primary way to keep CI and deployment platform secrets in sync with the vault (1Password, Doppler, Infisical, etc.).

## Arguments and options

| Argument / Option | Default              | Description                                                                                                                            |
| ----------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `<environmentId>` | _(required)_         | Vault environment id to read (provider-specific — e.g. a 1Password Environment id, Doppler config name)                                |
| `--project-id`    | —                    | Deployment project id (e.g. Vercel `prj_xxx`). Required when syncing to the `deployment` capability                                    |
| `--target`        | `production preview` | Deployment targets to sync to (space-separated). Options: `development`, `preview`, `production`                                       |
| `--worker`        | —                    | A deployed Worker (script name) to set every vault key on as a secret, e.g. `comlink`. Needs a `workers` provider that can set secrets |
| `--dry-run`       | `false`              | Print what would be set without writing secrets                                                                                        |

## Examples

```bash
# Sync all secrets from the "production" Doppler config to GitHub Actions
holocron secrets sync production

# Also sync to Vercel's production and preview environments
holocron secrets sync production --project-id prj_xxx

# Only sync to production (not preview)
holocron secrets sync production --project-id prj_xxx --target production

# Set the Comlink relay's signing secret on its Worker (from apps/comlink's 1Password Environment)
holocron secrets sync prd --cwd apps/comlink --worker comlink

# Dry-run to see what would be synced
holocron secrets sync production --dry-run
```

## One environment, several scopes

Declare where an environment's keys go in `repo.secrets.sync`, and `secrets sync <environment>` follows it: each entry whose `environment` matches pushes its `keys` (every key the vault holds when omitted) to its `scope` (`repo`, `env=<name>` or `org=<name>`), one step per scope. An Environment that holds both organization and repository secrets is then one command:

```ts
repo: {
	secrets: {
		sync: [
			{ environment: "Holocron - GitHub Actions", scope: "org=theholocron", keys: ["AXIOM_TOKEN", "TURBO_TOKEN"] },
			{ environment: "Holocron - GitHub Actions", keys: ["CODECOV_TOKEN", "VERCEL_TOKEN"] },
		],
	},
},
```

```bash
holocron secrets sync "Holocron - GitHub Actions" --dry-run
```

`--github-secret` (and `--github-secret-scope`) describe one route by hand and win over the config for that run. [`doctor secrets`](/holocron/commands/doctor-secrets/) reads the same entries to check what should have been pushed.

## Actions variables from a vault environment

GitHub Actions **variables** (non-secret values such as `TURBO_TEAM`) can be filled the same way, so there is one place to edit them. Keep them in a vault environment of their own: a vault does not tell a visible value from a secret one, and a variable is readable in GitHub afterwards. Declare it in `repo.variables.sync`, names only:

```ts
repo: {
	variables: {
		sync: [
			{
				environment: "Holocron - GitHub Actions variables",
				scope: "org=theholocron", // "repo" (the default) or "org=<name>"
				keys: ["AXIOM_DATASET", "CLOUDFLARE_ACCOUNT_ID", "TURBO_TEAM"],
				visibility: "all", // organization only; "all" (the default) or "private"
			},
		],
	},
},
```

```bash
holocron secrets sync "Holocron - GitHub Actions variables" --dry-run
```

Each key is written through the `source` provider (`syncVariables`, or `syncOrgVariables` for an organization), one call per key, and nothing is deleted. A blank or missing value is skipped, so GitHub keeps what it has until the vault is filled. An environment that only has variable entries pushes nothing to `secrets` or `deployment`. Values are never printed.

A name may be given by `repo.variables.sync` or as a literal in `repo.variables.repo` or `repo.variables.org`, not both: that is a config error, as is `prune: true` together with `sync`. [`doctor variables`](/holocron/commands/doctor-variables/) checks that the names exist.

## Blank and missing values

A key that is blank in the vault (`NAME=""`, a placeholder for a value still to be found) is skipped in every destination, in a dry run too, with a row saying so. Pushing it would overwrite a working secret with nothing, and no provider can read a secret back to undo that. A listed key the vault does not hold is a skipped row as well, not silently ignored. Skipped rows do not fail the run.

## Names GitHub refuses

GitHub Actions secrets and variables (repository, environment and organization alike) must use only letters, digits and underscores, must not start with a digit, and must not start with `GITHUB_`. A name that breaks a rule gets a bare 422 from the API, and retrying cannot help. When the `secrets` or `source` provider is `github`, the sync checks each name first and writes a skipped row, `invalid name: <reason>`, without calling GitHub. The run does not fail on it, and the key still goes to the other destinations (Vercel accepts `GITHUB_APP_ID`; Sentinel's App id and key are `SENTINEL_GITHUB_APP_ID` and `SENTINEL_GITHUB_APP_PRIVATE_KEY` for that reason).

If a vault environment holds such a key (Sentinel's old `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY`), keep it out of the GitHub routes with `--github-secret` or the `keys` of a `repo.secrets.sync` entry, which also removes the skipped row.

## Flow

1. The `vault` capability reads all KEY=VALUE pairs from `<environmentId>`
2. Each key is set as a CI secret (via the `secrets` capability) at the scope `repo.secrets.sync` gives it, or at repo scope with no entry
3. If `--project-id` is provided, each key is also set as a deployment env var for each `--target`

## Syncing to a Worker

`--worker` only adds and updates secrets; it never removes a binding. A Worker also holds secrets that are not in the vault (for Comlink, `COMLINK_<SOURCE>_WEBHOOK`, which `notifications setup` sets), so a key deleted from the vault has to be deleted from the Worker separately. Keys are written one at a time and each is reported. If one fails the exit code is 1, and re-running finishes the rest, since every write is idempotent.

## Authentication

- Vault plugin token (e.g. `HOLOCRON_DOPPLER_TOKEN`, `HOLOCRON_INFISICAL_TOKEN`)
- `HOLOCRON_SECRETS_TOKEN` / `github.secrets` for writing GitHub secrets (an org-resource-owner token, needed for `org=` scope); `org=` scope uses it first; repo and environment scopes use `HOLOCRON_ADMIN_TOKEN` / `github.admin` first, and each falls back to the other
- Deployment plugin token (e.g. `HOLOCRON_VERCEL_TOKEN`) if `--project-id` is used
