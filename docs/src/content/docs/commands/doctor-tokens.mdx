---
title: "doctor tokens"
description: Check that each token a configured plugin takes is set and still accepted. Read-only; no token is printed.
---

```bash
holocron doctor tokens
```

For every token a configured plugin lists, finds the token the way the plugin does (its environment variable, then the OS keyring) and asks the plugin's `verifyToken` whether it is still accepted. It prints one row per token and exits non-zero while any is rejected or has 7 days or fewer left. It changes nothing and never prints a token.

The GitHub plugin takes nine separate tokens, one per kind of operation (see the [Token Reference](/holocron/tokens/)). Plain [`doctor`](/holocron/commands/doctor/) only exercises the one its shallow check happens to use, and a fine-grained token that has expired or been revoked is otherwise found when the operation that needs it fails, in CI or part-way through [`repo setup`](/holocron/commands/repo-setup/). This is the check that says which are due for replacing.

```text
  ✓ github.read      user @ cnewton (keyring), expires in 41 days
  ✗ github.admin     rejected (HOLOCRON_ADMIN_TOKEN): Bad credentials
  ✗ github.org       user @ cnewton (keyring), expires in 3 days
      - expires in 3 days: renew it
  ✓ github.sync      user @ cnewton (keyring)

2 ok, 2 fail, 0 skipped
```

## What each row means

| Row                 | When                                                                                                                                                                       |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ok                  | The token is set and the plugin accepts it. The row says whose it is, where it came from (the variable name, or `keyring`) and, for a token that expires, how long is left |
| fail                | The token is set and is rejected (expired, revoked, malformed), or verifying it threw. The row carries the provider's message                                              |
| fail: expires soon  | The token is accepted but expires within 7 days (`TOKEN_EXPIRY_WARN_DAYS`). The row gets a problem line, `expires in 3 days: renew it`                                     |
| skip: not set       | Neither the environment variable nor the keyring has it. Whether a token is needed depends on what you run, so this is never a failure                                     |
| skip: cannot verify | The token is set but its plugin has no `verifyToken`                                                                                                                       |
| skip: plugin        | The plugin package could not be loaded here, with the reason                                                                                                               |

When no configured plugin lists any token, the one row says so.

## Expiry

GitHub returns a fine-grained token's expiry in the `github-authentication-token-expiration` response header of any authenticated call; the GitHub plugin reads it from the `/user` call it already makes to verify the token and passes it on as `expiresAt`. A token with no expiry (a classic token set to never expire) shows nothing extra. A token that has already expired is simply rejected by GitHub.

A warning is a failure: the check has three statuses (ok, fail, skip) and no fourth, and a failure is what turns a scheduled run red. A token inside the 7-day window therefore fails its row with a problem line, until it is renewed.

### Running it on a schedule

The `security.tokenExpiry` task runs this check daily from CI (a generated `.github/workflows/security.tokenExpiry.yml` calling a reusable workflow in `theholocron/.github`), so GitHub's failed-workflow notification reaches the team before an operation breaks. It runs daily rather than weekly: the window is 7 days, so a weekly run could land just outside it and the next one just after the token lapsed, whereas a daily run fails every day inside the window until the token is renewed. Add `"security.tokenExpiry"` to `tasks` and run `holocron repo sync`; the GitHub tokens are read from the organization secrets of the same names (see the [Token Reference](/holocron/tokens/)). A token with no secret is skipped, not failed. Tokens of other plugins are not passed to the job yet.

## What it does not check

- **What a token may do.** GitHub does not return a fine-grained token's permissions, so "has the permissions the token reference lists" cannot be read back. A token can be accepted here and still be refused by an operation it lacks a permission for.
- Plugins other than GitHub, until they list their `tokens` (see [Plugins](/holocron/plugins/overview/)). Their main token is exercised by plain `doctor`.
