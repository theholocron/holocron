---
title: "deploy"
description: Trigger a deployment via the configured deployment capability.
---

```bash
holocron deploy <branch> --project-id <id> [--target production|staging] [--dry-run]
holocron deploy <app> --env <environment>... [--dry-run]
```

Triggers a deployment of a git branch via the configured `deployment` capability (e.g. Vercel). Omit `--target` for a branch preview deployment.

## Arguments and options

| Argument / Option | Required | Description                                           |
| ----------------- | -------- | ----------------------------------------------------- |
| `<branch>`        | Yes      | Git branch to deploy                                  |
| `--project-id`    | Yes      | Deployment project id (e.g. Vercel `prj_xxx`)         |
| `--target`        | No       | `production` or `staging` — omit for a branch preview |
| `--dry-run`       | No       | Print what would be deployed without triggering       |

## Examples

```bash
# Branch preview
holocron deploy feature/my-feature --project-id prj_xxx

# Production deploy
holocron deploy main --project-id prj_xxx --target production

# Staging deploy (dry-run)
holocron deploy main --project-id prj_xxx --target staging --dry-run
```

## Deploying an app by name

`holocron deploy <app> --env prod` deploys one of the workspace's apps (a package under `apps/`) without its identifiers
written out (spec `tool-app-deploy-sync`, #2608). Run it from the repository root, or from inside the app's folder and
leave the name off.

```bash
holocron deploy sentinel --env prod
cd apps/sentinel && holocron deploy --env production
holocron deploy sentinel --env production --env preview --dry-run
```

| Option                   | Description                                                                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `--env`, `--environment` | An environment to deploy to: `production` (or `prod`) or `preview`. Repeat the flag for more than one; production goes first. Required. |

The values are the standard environments of `@theholocron/env-utils`, with their aliases. `local`, `development`, `ci` and `test` are refused: an app is never deployed to them.

Nothing is written into the command. The app is found under the workspace by its folder's name, the project takes that
name, and the app's own `holocron.config` says which `deployment` provider it uses and the `domain` it serves. Before
anything is built, the project must serve that domain (`Deployment.listDomains()`); if it does not, the command fails
with both names and writes nothing. The app is then built (`pnpm run build`), staged (`deploy stage`) and its files
deployed (`deploy --files`), so the result is what the app's `deploy` script did.

**A preview instance.** An app can declare one in its `deployment` options (`instances: { preview: { project, domain } }`;
Sentinel's is `sentinel-preview`). `--env preview` then deploys to that project, as the project's own production
deployment, from a payload whose `vercel.json` has no `crons` (the crons belong to production), and the project must
serve the instance's `domain` before anything is written. The payload is staged apart from production's
(`.vercel-deploy-preview`). An app with no instance keeps the earlier meaning of `--env preview`, a Vercel preview
deployment of its one project.

An app with no `deployment` provider has nothing to deploy, and the command says so and exits 0: Comlink's Worker is
made by `setup notifications`, which has the channel webhooks it needs, and
Council is an Obsidian plugin installed by hand. `--dry-run` runs the domain check, then lists what it would do.

A first value that is not an app's name is a branch, exactly as before.

## Authentication

Uses the configured `deployment` plugin's token. For Vercel: `HOLOCRON_VERCEL_TOKEN` / `vercel` keyring entry.
