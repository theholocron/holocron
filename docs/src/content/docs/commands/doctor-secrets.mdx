---
title: "doctor secrets"
description: Show where every secret and variable lives and check it against the config. Read-only, names only.
---

```bash
holocron doctor secrets [--env <list>] [--only-secrets | --only-variables] [--strict] [--name <name>] [--verify]
```

Compares the secret names the config says must exist with the names the `secrets` provider holds, and prints one row for each scope that has something expected: the repository, the organization and each environment. It changes nothing, shows no value (GitHub never returns one), and exits non-zero while any row fails.

A workflow that reads a secret which does not exist fails quietly, and a secret is quick to forget when a repo is set up by hand. This is the check that says which are missing. To see everything that does exist, use [`list secrets`](/holocron/commands/list-secrets/).

```text
  ✓ repository secrets exist    2 of 2 exist
  ✗ organization secrets exist  2 problem(s)
      - missing secret HOLOCRON_NOTIFY_WEBHOOK_SYNC
      - missing secret NPM_TOKEN

1 ok, 1 fail, 0 skipped
```

## The `local` and `dev` columns

These replace `doctor credentials`. They read names only: the credentials providers are loaded without being asked for a value, and each lists the variable names of an Environment (`Credentials.inspect`). A name counts as present when `<org/repo> - local` or `- dev` holds it, as a machine reads them. A required Environment that does not exist is a failing row, by name; a token a plugin needs that neither holds is a failing row (`missing from ...`); a token a plugin only falls back to (`optional`, such as `HOLOCRON_RELEASE_TOKEN` or the Discord webhook) is a skipped row. The rest is one `ok` row per provider that says how many tokens are present and which spelling of the Environment's name matched. A provider that cannot list names, a config with no `environment`, or no plugin that lists tokens is a skipped row that says so. With no `credentials` provider the two columns are left out, unless you ask for them with `--env local` or `--env dev`, when one skipped row says so.

## The matrix

The default output is a matrix: one row per name, one column per place that can store it. Names only; no value, hash or length is ever printed. The columns come from the config and are grouped by what stores them: the vault (1Password), GitHub (repository, organization and environment secrets, and variables) and the deployments `repo.secrets.deploy` feeds. There are two blocks, **Secrets** and then **Variables**, each with a heading, so a visible value is never mistaken for a concealed one.

```text
Secrets
name     1Password ci  1Password prod  GitHub repo  Deploy prod
TOKEN_A  ok            n/a             ok           ?
TOKEN_B  ok            n/a             MISSING      ?
APP_ONE  n/a           ok              n/a          ?

Legend
  ok       present where it should be
  n/a      not needed here
  MISSING  needed here, not found
  extra    found here, but nothing feeds it
  ?        could not read this place
```

The cells are words, not symbols or colour, so a pipe or a log reads the same, and the legend is always printed. When the table would pass the width of the terminal, each name is shown as a short list instead.

- **Needed** comes from the config: `repo.secrets.sync` (its `keys`, `scope`), `repo.secrets.deploy`, `repo.secrets.repo`, `org` and `environments`, `repo.variables` and `repo.variables.sync`, and the notification layout. The Environment a sync entry or a deploy entry names is a 1Password column.
- **MISSING** is a failure. Where another row already reports a GitHub name, the matrix adds none; a 1Password name that an entry lists and the Environment lacks fails in its own row.
- **extra** is advisory: an `info` row (shown as skipped), exit 0. `--strict` makes it a failure. An organization holds secrets for other repositories too, so for an organization only the names this config feeds are shown. A secret you set by hand on purpose goes in `doctor.manualSecrets` (names only, beside `doctor.sharedVariables`) and is never reported:

  ```ts
  doctor: { manualSecrets: ["HOLOCRON_LIGHTHOUSE_TOKEN"] },
  ```

- **?** is a place that could not be read (no provider, a missing or refused token, an Environment not found). It is a skipped row that names the place and why, never a failure, and the other places are still compared. A deployment is always `?`: the project or Worker is named when you run `sync secrets` (`--project-id`, `--worker`), not in the config.

`--only-secrets` and `--only-variables` show one block and read only that side; with neither, both are shown.

### Looking up one name

`holocron doctor secrets --name TOKEN_A` prints one line for each place that holds or needs the name, and why, for example `GitHub repo (secrets): MISSING, synced to repository secrets by entry 1 of repo.secrets.sync (from acme/demo - ci)`. It is informational and exits 0. A name is matched without regard to case.

### Verifying the tokens

`--verify` also asks each vendor whether the tokens the configured plugins take are still accepted. It is opt-in because it goes online (slower, and subject to the vendors' rate limits); the default stays offline. This replaces `doctor tokens`. For every token a plugin lists, the token is looked up the way the plugin does it (the process environment, then the repo's `.env` and the `credentials` providers, then the OS keyring) and the plugin's `verifyToken` is asked. Each `verify:<token>` row says where the token came from; a token is never printed. A token that is not set is a skipped row, since whether it is needed depends on what is run. One that is set and rejected (expired, revoked, malformed) fails, and so does one that expires in 7 days or fewer. A credentials provider that could not be read fails its own row, because its tokens would then fall through to the keyring. What a token may do is not checked: GitHub does not return a fine-grained token's permissions.

The scheduled `check-tokens` workflow runs `holocron doctor secrets --verify` daily, so a token that is rejected or about to expire reaches the team before an operation breaks.

### Variables

The Actions variables of `repo.variables` are checked here too, in the Variables block and in the rows below it: one row for the repository's variables and one for the organization's, each only when the config declares that scope, and one per `repo.variables.sync` entry (the values are in the vault, so only names are compared). A variable that exists but is not declared is a problem only with `repo.variables.prune`; without it, it is an `extra` name in the matrix. (This replaces the old `doctor variables` command.)

## Choosing environments with `--env`

`--env` takes a list of `local`, `dev`, `ci`, `test` and `prod`, comma-separated or repeated: `--env ci,prod` and `--env ci --env prod` are the same. A name that is not one of them is an error that lists the five. Duplicates count once, and the rows come out in the order `local`, `dev`, `ci`, `test`, `prod` whatever order you typed.

| Environment | What it compares                                                                                                                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci`        | The GitHub side (secrets and variables) and the vault Environments that feed it: the names the config expects ([below](#what-must-exist)), the `repo.secrets.sync` entries and who can read the organization secrets |
| `prod`      | The `deploy-<environment>` rows for `repo.secrets.deploy` ([below](#skips))                                                                                                                                          |
| `local`     | The tokens the configured plugins take (their `tokens` export) against `<org/repo> - local`, then `- dev`: a machine reads the first it finds. A missing `- local` is not mentioned                                  |
| `dev`       | The same tokens against `<org/repo> - dev`                                                                                                                                                                           |
| `test`      | Has no layer: tests use fakes and read none. A skipped row says so                                                                                                                                                   |

With no `--env`, `local`, `dev`, `ci` and `prod` all run; `test` appears only when you ask for it. With `--env`, only the ones you name run, so `--env prod` reads no GitHub secret and `--env test` reads nothing.

```text
holocron doctor secrets --env test

  · test environment  test: has no layer (tests use fakes and read none)
```

## What must exist

Nothing is expected beyond these, and a secret that exists but is not expected is never a problem, since many legitimate ones are not listed anywhere.

| Scope        | Expected                                                                                                                                                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repository   | `repo.secrets.repo`, and the Chromatic token of each project of a `test:visual` task: `CHROMATIC_PROJECT_TOKEN` for `tokenName: "default"` (or none), otherwise `CHROMATIC_PROJECT_TOKEN_<TOKENNAME>`                                                                        |
| Organization | `repo.secrets.org`, and the secrets the notification layout fills: each channel's webhook secret (`webhook.secret`, else `HOLOCRON_NOTIFY_WEBHOOK_<CHANNEL>`) and each role's `secret`. The organization is `--org`, `HOLOCRON_ORG`, the config's `org`, or the repo's owner |
| Environment  | `repo.secrets.environments.<name>`                                                                                                                                                                                                                                           |

Declare the rest in `holocron.config.ts`. Names only, never values; `new secret` and `sync secrets` write them.

```ts
repo: {
  secrets: {
    repo: ["TURBO_TOKEN", "VERCEL_TOKEN"],
    org: ["NPM_TOKEN"],
    environments: { production: ["DATABASE_URL"] },
  },
},
```

Names are compared without regard to case, as GitHub does. Fragments from presets add up: each list is a union.

## Secrets filled from a vault

`holocron sync secrets --env <environment>` pushes the keys of a vault environment into GitHub secrets. Declare which keys go where in `repo.secrets.sync`: the sync follows it (see [sync secrets](/holocron/commands/sync-secrets/)) and the doctor expects those names too:

```ts
repo: {
  secrets: {
    sync: [
      { environment: "prd" }, // every key the vault holds, as repository secrets
      { environment: "ci", keys: ["AXIOM_TOKEN"], scope: "org=theholocron" }, // one key, as an organization secret
    ],
  },
},
```

| Field         | Meaning                                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `environment` | The vault environment id, as given to `sync secrets`                                                                         |
| `keys`        | The `--github-secret` allowlist. Leave it out for every key the environment holds; the doctor then asks the `vault` for them |
| `scope`       | `repo` (the default), `env=<name>` or `org=<name>`, as `--github-secret-scope` words it                                      |
| `repos`       | `org=` only, required there: the repositories that can read the secrets (visibility `selected`)                              |

The names join the scope's own row (an `org=` other than the organization above gets its own row). Only key names are kept: the `vault` provider returns an environment as KEY=VALUE pairs, and the doctor drops the values at once, never logging or printing them. An entry with `keys` needs no vault at all. Entries merge across presets by environment and scope; if any fragment leaves `keys` out, that entry stays "every key".

## Who can read an organization secret

For each organization with a `repo.secrets.sync` entry that has `repos` (#2062), an `org-secret-access` row (`org-secret-access-<org>` for another organization) reads who can read each synced secret, by name, and compares it with the entry. It fails for a secret readable by more repositories than its entry says (visibility `all` or `private`, or `selected` with a repository the entry does not list) and for one missing a listed repository. When all match it says how many secrets sit at each list:

```text
  ✓ theholocron organization secrets are readable only by their entries' repositories  9 selected [.github, holocron]; 5 selected [holocron]
  ✗ no organization secret is overridden by a repository secret of the same name  1 problem(s)
      - HOLOCRON_ORG_TOKEN exists at repository and organization level: the repository secret overrides it
```

The secrets a notification layout fills (`HOLOCRON_NOTIFY_*`) are compared the same way with the layout's `readers` (#2131), in the same row; a layout with no `readers` declares nothing here, and `setup notifications` refuses to write them. A secret that does not exist is the "exist" row's finding. The `org-secret-shadowed` row fails for a name that exists at both levels, because the repository secret wins and keeps the old value after a rotation. Both rows are skipped, with the reason, when the provider cannot report it or the token cannot read it. Only names and repository names are read.

## Skips

A row is a **skip**, not a failure, when it cannot be read: no `secrets` provider is configured or it could not load, or the provider has no token for that scope. When nothing is expected anywhere, the one row says `none declared`.

Each Environment in `repo.secrets.deploy` (what [`sync secrets`](/holocron/commands/sync-secrets/) may send to a deployment or Worker) gets a `deploy-<environment>` row that lists the key names it would send and the ones it keeps back, read from the vault in memory. It does not fail; it makes a token that should not go out visible before the sync. A vault that cannot list the Environment makes it a skipped row.

An entry of `repo.secrets.sync` without `keys` is its own skipped row (`sync-<environment>`), with the reason, when there is no `vault` provider, it has no token, or it cannot list that environment. The rest of the check is unaffected. `repo.variables.sync` (Actions variables, not secrets) is separate and is checked by [`doctor secrets`](/holocron/commands/doctor-secrets/). An entry whose `scope` is not `repo`, `env=<name>` or `org=<name>` fails.

A row **fails** when a secret is missing, when there is an organization secret to look for but no organization to look under, and when the provider reports an error for that scope (for example an environment that does not exist).

## Authentication

Reads use the same tokens as [`list secrets`](/holocron/commands/list-secrets/): `github.secrets` for the organization scope, `github.admin` for the repository and environments.

`doctor notifications` keeps its own step for the layout's secrets, so a problem there shows in both.

`sync secrets` takes the same word as `--env`, but exactly one, because it writes: `holocron sync secrets --env ci`.
