---
title: "doctor secrets"
description: Check that the secrets the config relies on exist. Read-only, names only.
---

```bash
holocron doctor secrets
```

Compares the secret names the config says must exist with the names the `secrets` provider holds, and prints one row for each scope that has something expected: the repository, the organization and each environment. It changes nothing, shows no value (GitHub never returns one), and exits non-zero while any row fails.

A workflow that reads a secret which does not exist fails quietly, and a secret is quick to forget when a repo is set up by hand. This is the check that says which are missing. To see everything that does exist, use [`list secrets`](/holocron/commands/list-secrets/).

```text
  ✓ repository secrets exist    2 of 2 exist
  ✗ organization secrets exist  2 problem(s)
      - missing secret HOLOCRON_NOTIFY_WEBHOOK_SYNC
      - missing secret NPM_TOKEN

1 ok, 1 fail, 0 skipped
```

## What must exist

Nothing is expected beyond these, and a secret that exists but is not expected is never a problem, since many legitimate ones are not listed anywhere.

| Scope        | Expected                                                                                                                                                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repository   | `repo.secrets.repo`, and the Chromatic token of each project of a `test:visual` task: `CHROMATIC_PROJECT_TOKEN` for `tokenName: "default"` (or none), otherwise `CHROMATIC_PROJECT_TOKEN_<TOKENNAME>`                                                                        |
| Organization | `repo.secrets.org`, and the secrets the notification layout fills: each channel's webhook secret (`webhook.secret`, else `HOLOCRON_NOTIFY_WEBHOOK_<CHANNEL>`) and each role's `secret`. The organization is `--org`, `HOLOCRON_ORG`, the config's `org`, or the repo's owner |
| Environment  | `repo.secrets.environments.<name>`                                                                                                                                                                                                                                           |

Declare the rest in `holocron.config.ts`. Names only, never values; `new secret` and `sync secrets` write them.

```ts
repo: {
  secrets: {
    repo: ["TURBO_TOKEN", "VERCEL_TOKEN"],
    org: ["NPM_TOKEN"],
    environments: { production: ["DATABASE_URL"] },
  },
},
```

Names are compared without regard to case, as GitHub does. Fragments from presets add up: each list is a union.

## Secrets filled from a vault

`holocron sync secrets <environmentId>` pushes the keys of a vault environment into GitHub secrets. Declare which keys go where in `repo.secrets.sync`: the sync follows it (see [sync secrets](/holocron/commands/sync-secrets/)) and the doctor expects those names too:

```ts
repo: {
  secrets: {
    sync: [
      { environment: "prd" }, // every key the vault holds, as repository secrets
      { environment: "ci", keys: ["AXIOM_TOKEN"], scope: "org=theholocron" }, // one key, as an organization secret
    ],
  },
},
```

| Field         | Meaning                                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `environment` | The vault environment id, as given to `sync secrets`                                                                         |
| `keys`        | The `--github-secret` allowlist. Leave it out for every key the environment holds; the doctor then asks the `vault` for them |
| `scope`       | `repo` (the default), `env=<name>` or `org=<name>`, as `--github-secret-scope` words it                                      |
| `repos`       | `org=` only, required there: the repositories that can read the secrets (visibility `selected`)                              |

The names join the scope's own row (an `org=` other than the organization above gets its own row). Only key names are kept: the `vault` provider returns an environment as KEY=VALUE pairs, and the doctor drops the values at once, never logging or printing them. An entry with `keys` needs no vault at all. Entries merge across presets by environment and scope; if any fragment leaves `keys` out, that entry stays "every key".

## Who can read an organization secret

For each organization with a `repo.secrets.sync` entry that has `repos` (#2062), an `org-secret-access` row (`org-secret-access-<org>` for another organization) reads who can read each synced secret, by name, and compares it with the entry. It fails for a secret readable by more repositories than its entry says (visibility `all` or `private`, or `selected` with a repository the entry does not list) and for one missing a listed repository. When all match it says how many secrets sit at each list:

```text
  ✓ theholocron organization secrets are readable only by their entries' repositories  9 selected [.github, holocron]; 5 selected [holocron]
  ✗ no organization secret is overridden by a repository secret of the same name  1 problem(s)
      - HOLOCRON_ORG_TOKEN exists at repository and organization level: the repository secret overrides it
```

A secret that does not exist is the "exist" row's finding. The `org-secret-shadowed` row fails for a name that exists at both levels, because the repository secret wins and keeps the old value after a rotation. Both rows are skipped, with the reason, when the provider cannot report it or the token cannot read it. Only names and repository names are read.

## Skips

A row is a **skip**, not a failure, when it cannot be read: no `secrets` provider is configured or it could not load, or the provider has no token for that scope. When nothing is expected anywhere, the one row says `none declared`.

Each Environment in `repo.secrets.deploy` (what [`sync secrets`](/holocron/commands/sync-secrets/) may send to a deployment or Worker) gets a `deploy-<environment>` row that lists the key names it would send and the ones it keeps back, read from the vault in memory. It does not fail; it makes a token that should not go out visible before the sync. A vault that cannot list the Environment makes it a skipped row.

An entry of `repo.secrets.sync` without `keys` is its own skipped row (`sync-<environment>`), with the reason, when there is no `vault` provider, it has no token, or it cannot list that environment. The rest of the check is unaffected. `repo.variables.sync` (Actions variables, not secrets) is separate and is checked by [`doctor variables`](/holocron/commands/doctor-variables/). An entry whose `scope` is not `repo`, `env=<name>` or `org=<name>` fails.

A row **fails** when a secret is missing, when there is an organization secret to look for but no organization to look under, and when the provider reports an error for that scope (for example an environment that does not exist).

## Authentication

Reads use the same tokens as [`list secrets`](/holocron/commands/list-secrets/): `github.secrets` for the organization scope, `github.admin` for the repository and environments.

`doctor notifications` keeps its own step for the layout's secrets, so a problem there shows in both.
