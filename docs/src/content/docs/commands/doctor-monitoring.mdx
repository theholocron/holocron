---
title: "doctor monitoring"
description: Check the monitoring checks declared for the monitoring provider against the ones its account holds. Read-only.
---

```bash
holocron doctor monitoring
```

Compares the checks the `monitoring` provider declares in `holocron.config.ts` (the `checks` in its provider options, the same list [`check monitor`](/holocron/commands/check-monitor/) runs) with the checks that exist in the provider's account, and prints one row. It changes nothing, and it exits non-zero while the row fails.

It is the check for [`setup`](/holocron/commands/setup/), which creates and updates the checks. Run it after `setup`, or when an alert you expected never came.

```text
  ✗ monitoring checks match  3 problem(s)
      - missing check Sentinel health
      - check Sentinel webhook uptime frequency: declared 5, found 10
      - check Sentinel webhook uptime assertions: declared status_code equals 405, found none

0 ok, 1 fail, 0 skipped
```

## What counts as a problem

| Finding                                                                      | A problem when                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A declared check is not in the account                                       | always. Checks are matched by name                                                                                                                                                                                    |
| A declared check has another URL or method                                   | always. A check that states no method is a `GET`                                                                                                                                                                      |
| Another frequency, locations, tags, activated, should-fail, body, assertions | the config states that setting (for `tags`, only a declared tag the check lacks; an extra tag on it is not a problem). A setting the config leaves out is not compared, since the provider then picks its own default |
| A check is in the account but not declared                                   | never a failure: the account may hold checks made by hand or by another tool. One a dashboard or status page shows is named in an `info` row (see below)                                                              |

Locations and assertions are compared without regard to their order. Only the settings the provider can return are compared; an assertion on something the config cannot express (for example a JSON body in Checkly) is not read back.

## Checks no config declares

A check made by hand in the provider's UI that carries the tag of a declared dashboard or status page component is counted in that component's status, though nothing in the repo says it exists. When some declared dashboard or component picks checks by tag, an `info` row (shown as skipped, never a failure) names each such check that no config declares:

```text
  - checks no config declares  info: 1 check(s) a declared dashboard or component picks up, declared nowhere: Docs staging (docs)
```

A check counts as declared when the root config or any workspace package's own `holocron.config.*` declares a check of that name (`apps/sentinel` and `apps/comlink` declare theirs there, so a run from the root reads every package's declarations through its `monitoring` provider; no token is read for that and nothing is requested from the provider). A check that carries none of those tags is not reported, and heartbeats are not compared. The name is the identity, so a check renamed in the provider's UI is named here and its declared name is missing in the checks row.

The row is a skip that names the package when a package's config cannot be read, because the check may be declared there. There is no row when no declared dashboard or component has a tag, or when the checks could not be listed (the checks row says why).

## Skips

The row is a **skip**, not a failure, when it cannot be read:

- the `monitoring` provider is configured but could not load (its reason is shown),
- the provider cannot list its checks, or
- the provider's token is not set.

When no provider is configured or it declares no checks, the row says `none declared`.

## Not covered

The alert channel, its alert settings (`feeds.monitoring.alerts`) and its subscriptions, including which checks are routed to it with `alertChannels`, come from the notification layout, so they belong to [`doctor notifications`](/holocron/commands/doctor-notifications/). Whether an alert reaches the channel is a probe, not a doctor check.

## Authentication

Uses the same token as `setup` for the provider (for Checkly, `CHECKLY_API_KEY` or `holocron new token checkly`), read-only.
