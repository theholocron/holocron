---
title: "doctor variable-owners"
description: Flag a variable name that lives in more than one place, across 1Password Environments and GitHub Actions secrets and variables. Read-only, names only.
---

```bash
holocron doctor variable-owners
```

A variable that lives in two places drifts: one copy is rotated and the other is not, or the two carry different names for one value. This check gathers the **names** of the variables in every place the config points at and reports a name that two places hold. It changes nothing, never reads or prints a value, and exits non-zero only while a name lives in more than one place that nothing explains. The rule it checks is [one owner per variable](/holocron/environment-variables/#one-owner-per-variable).

```text
  ✗ SENTINEL_WEBHOOK_SECRET                    lives in 2 places
      - held by Environment "theholocron/holocron - prod"
      - held by organization secrets
  · TURBO_TEAM and HOLOCRON_TURBO_TEAM         info: both exist (TURBO_TEAM in organization variables; HOLOCRON_TURBO_TEAM in organization variables). Fine during a rename; a leftover after it
  - Environment "theholocron/holocron - dev"        could not read it with 1password: Environment not found

0 ok, 1 fail, 2 skipped
```

## Where it reads

| Place                  | How                                                                                                                                                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1Password Environments | `Credentials.inspect`, which lists names without a value. The Environments are the ones the config names: each `credentials` provider's, `githubApps[].environment`, `dev.environment`, and every `repo.secrets.sync` and `repo.variables.sync` entry's |
| GitHub secrets         | The `secrets` provider: the repository, the organization, and each Environment a sync entry or `repo.secrets.environments` names                                                                                                                        |
| GitHub variables       | The `source` provider: the repository and the organization. Environment-scope variables are not read                                                                                                                                                    |

The Environments are listed by a loader that never reads a value from a `credentials` provider, so only names are ever loaded for them. The GitHub reads use a second loader that does read the `credentials` providers, so the GitHub plugin finds its token in the usual chain (flag, process environment, `.env`, a `credentials` provider such as a 1Password Environment, keyring); a token is only used to authenticate and is never printed. The tokens are the ones those providers already use, so there is nothing new to set: the organization's secrets use `HOLOCRON_SECRETS_TOKEN` (the admin token when it is not set), the repository's and an Environment's secrets use `HOLOCRON_ADMIN_TOKEN`, and the organization's variables use `HOLOCRON_ORG_TOKEN`. See [tokens](/holocron/tokens/). Names are compared without regard to case, as GitHub does.

## What counts as a finding

| Row                     | When                                                                                                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| fail, one per name      | Two places hold the name and nothing below explains it. The problem lines name the places                                                                                      |
| info (shown as skipped) | A bare name and its prefixed one exist (`X` with `HOLOCRON_X`, `SENTINEL_X` or `COMLINK_X`). The fallback is deliberate during a rename; a pair that outlives it is a leftover |
| ok                      | Nothing is reported, and at least one place was read. The row counts the names and places                                                                                      |

Not reported:

- **The sync fan-out.** An Environment that `repo.secrets.sync` or `repo.variables.sync` copies to a GitHub place is the one allowed copy. The GitHub copy of a name an Environment fills is left out; a second Environment holding the same name is still reported.
- **Deliberate sharing.** A name listed in `doctor.sharedVariables` in `holocron.config.ts` (names only). Use it for a value two Environments hold on purpose, such as `HOLOCRON_DISCORD_BOT_TOKEN`. The same goes for a token the CLI reads locally and the CI reads from the `ci` layer Environment (`<org>/<repo> - ci`) (`HOLOCRON_ADMIN_TOKEN`, `HOLOCRON_SYNC_TOKEN` and the rest of the org tokens): each is listed by name, and the value is rotated in both places.
- **The instances of one GitHub App.** The Environments in `githubApps` (the `prod` and `dev` layers of this repository) hold the same names by design and count as one place.

```ts
export default defineConfig({
  doctor: { sharedVariables: ["HOLOCRON_DISCORD_BOT_TOKEN"] },
});
```

## Skips

A place that cannot be read is a skip with the reason, never a failure, and the other places are still compared:

- no `credentials` provider is configured, or it cannot list names without reading values,
- an Environment the provider cannot find,
- no `secrets` or `source` provider, or one that cannot list,
- a missing or refused token for a GitHub scope, and
- no organization (set `org` in the config or run inside a repository).

When nothing at all could be read, the check is a skip.
