---
title: "new issue"
description: File an issue in the repo's tracker from the command line.
---

```bash
holocron new issue <title> [--body <text> | --body-file <path|->] [--label <name>]... [--assignee <login>]... [--milestone <number|title>] [--type bug|feature|task] [--priority urgent|high|medium|low] [--effort high|medium|low] [--start-date <YYYY-MM-DD>] [--target-date <YYYY-MM-DD>] [--parent <key>] [--blocked-by <key>]... [--project <board>] [--area <name>]... [--dry-run] [--yes]
```

Files an issue through the repo's `issues` provider (`Issues.create`), so it lands in GitHub or Linear, whichever the config names, and the command knows nothing about a tracker. It prints the new issue's key in that tracker's syntax (`#2134`, `RANDO-7`).

```bash
holocron new issue "Fix the retry in codecov-upload" --label bug --body "It gives up after one attempt."
```

## Behavior

- **Asks first** unless `--dry-run` or `--yes`. Without a terminal it refuses to run without one of them.
- **`--dry-run`** prints the title, the first lines of the text and the labels, assignee, milestone and fields, and files nothing.
- **The fields are checked before anything is filed.** A date that is not `YYYY-MM-DD`, a target before the start, an area the repo does not declare, or the same key as parent and blocker is a failing row and files nothing.
- **A field the tracker refuses does not lose the issue.** The issue is made first and its key printed; a Type, field, parent or blocker the tracker will not take is listed under `not carried across`.
- **No duplicate check.** Filing the same title twice makes two issues.
- **A failure is a row.** If the provider is missing, is not available or refuses the request, the row says why and the exit code is 1.
- Rows print like every [`doctor <capability>`](/holocron/commands/doctor/), then `N ok, N fail, N skipped`.

## What a tracker cannot hold

A tracker that cannot hold something the call asked for files the issue anyway and lists it under `not carried across`, as [`migrate`](/holocron/commands/migrate/) does. On GitHub an assignee is a login and the milestone is found by its title. On Linear an assignee is matched by email, name or id (only one, extra names are listed), and the milestone names a project.

| Field                           | GitHub                                                         | Linear                                                                          |
| ------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `--type`                        | The issue Type (Bug, Feature, Task, or a declared one)         | A label: `bug`, `enhancement`, `chore`, or the declared Type's `label`          |
| `--priority`                    | The organization's `Priority` issue field                      | Linear's priority                                                               |
| `--effort`                      | The organization's `Effort` issue field                        | The estimate (low 1, medium 3, high 5); a team with estimates off may refuse it |
| `--start-date`, `--target-date` | The `Start date` and `Target date` issue fields                | Target date is the due date; a start date is dropped (Linear has none)          |
| `--parent`, `--blocked-by`      | Sub-issue link and blocked-by dependency, same repository only | Parent issue and `blocks` relation                                              |

A field the organization lacks (no `Effort` field, no such Type) is a `not carried across` line, not a failure. These writes follow GitHub's documented shapes and have not been run against the live API.

`--project <board>` puts the filed issue on a board the config declares in `providers.projects.boards` (found by name among the open boards, never made by this command), with its priority where the board has an option for it. A failure there is a failing row printed after the key, so the issue is never lost.

`--area <name>` adds the label `area:<name>` and is checked against `repo.labels.areas` in the config (spec `tech-github-area-labels`, #2430); a repo that declares no areas refuses it. Making the labels, `setup` and Sentinel's labeling are later parts of that spec.

## Options

| Option                 | Default | Description                                                                          |
| ---------------------- | ------- | ------------------------------------------------------------------------------------ |
| `--body <text>`        | none    | The issue's text                                                                     |
| `--body-file <path>`   | none    | Read the text from a file, or from standard input with `-`; not with `--body`        |
| `--label <name>`       | none    | A label to put on it; repeat the option for more                                     |
| `--assignee <login>`   | none    | A person to assign, by login (`me` is you); repeat for more where the tracker allows |
| `--milestone <value>`  | none    | The milestone, by number or exact title (case-insensitive)                           |
| `--type <kind>`        | none    | `bug`, `feature`, `task` or a Type the organization declares (`issueTypes`)          |
| `--priority <level>`   | none    | `urgent`, `high`, `medium` or `low`                                                  |
| `--effort <size>`      | none    | `high`, `medium` or `low`; the `work-effort` skill says how to choose                |
| `--start-date <date>`  | none    | When work starts, `YYYY-MM-DD`                                                       |
| `--target-date <date>` | none    | When it is due, `YYYY-MM-DD`                                                         |
| `--parent <key>`       | none    | The issue it is a sub-issue of                                                       |
| `--blocked-by <key>`   | none    | An issue that blocks it; repeat for more                                             |
| `--project <board>`    | none    | A declared board to put it on                                                        |
| `--area <name>`        | none    | An area from `repo.labels.areas`; adds `area:<name>`; repeat for more                |
| `--dry-run`            | `false` | Show what would be filed, without filing it                                          |
| `--yes`                | `false` | File without asking (required without a terminal)                                    |

Run without a title and the [interactive menu](/holocron/cli/) asks for the title and the text.

## Tokens

The `issues` provider reads its token through the usual chain (`--token`, the environment, `.env`, the `credentials` providers, the keyring). The command needs the `issues` provider's plugin package to resolve, as every command that calls a provider does.
