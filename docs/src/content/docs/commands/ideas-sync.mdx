---
title: "ideas sync"
description: File the idea notes that are ready as issues, and record the issue in each note.
---

```bash
holocron ideas sync [--dry-run] [--yes]
```

An idea starts as a note in a folder of Markdown files (an Obsidian vault). `ideas sync` is the step that turns an idea into an issue: it reads the ideas through the repo's `ideas` provider, creates an issue through its `issues` provider for each one that is ready, and records the issue on the idea, so it is never filed twice. The command knows nothing about Obsidian: where the ideas are kept is the provider's, so a second place to keep them is a provider entry and a plugin, not a change here. The design is [SPEC-0072](https://github.com/theholocron/holocron/issues/1994).

## Configuration

The provider says where the ideas are, and an `ideas` block holds the workflow setting:

```ts
providers: {
	ideas: ["obsidian", { dir: "~/Library/Mobile Documents/iCloud~md~obsidian/Documents/holocron" }],
},
ideas: { states: { file: "in-progress" } },
```

| Key                 | Default       | Meaning                                                                                                                                            |
| ------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `providers.ideas`   | none          | The `ideas` provider and its options. For [Obsidian](/holocron/plugins/obsidian/), `dir` is the folder of notes; a leading `~` is the home folder. |
| `ideas.states.file` | `in-progress` | The `status:` that means "file this idea". Another repo can use its own word for the state.                                                        |
| `ideas.dir`         | none          | Deprecated: read as `providers.ideas: ["obsidian", { dir }]` when `providers.ideas` is absent.                                                     |

`HOLOCRON_IDEAS_DIR` overrides the Obsidian provider's `dir`, because the path differs per machine (see [environment variables](/holocron/environment-variables/)). A config with only the older `ideas.dir` keeps working, and `providers.ideas` wins when both are set. The `ideas` capability is optional: a repo with no `providers.ideas`, no `ideas.dir` and no variable is unaffected, and the command reports that it has nowhere to read from. A wrong shape is a `ConfigError` that names the path, such as `ideas.states.file`.

## What it files

The Obsidian provider reads every `.md` file under `dir`, except in folders whose name starts with `_` or `.` (`_templates`, `.obsidian`, `.trash`, `_archive`). A note is filed when its `status:` property equals the filing state and it has no `issue:` property (or an empty one).

- **Title** is the first `#` heading, else the file name without `.md`.
- **Body** is the note's text without its frontmatter, then a blank line and `Filed from idea: <title>`. With no note left to hold `issue:`, that line is how an issue is traced to its idea. A last line, `<!-- holocron:idea <the idea's key> -->` (for Obsidian, the note path relative to `dir`), is a hidden marker (an HTML comment) that ties the issue to its note.
- **`issue:`** is then added to the note's frontmatter in the tracker's own syntax (`#1234` for GitHub, `ENG-42` for Linear). Everything else in the file, including line endings, is left as it was.
- **Embedded files** (`![[photo.png]]`, `![](assets/a.png)`) cannot go into an issue body, so a note that has one is reported and skipped. An image with a web address is plain text and does not count.

## Behavior

- **Quiet output.** A row is printed only for a note that is to be filed (`ok`, `fail`, or `skipped` as `would file` on a dry run) and for a note that needs your attention (embedded files, a note that cannot be read). Notes in another state and notes that already have an `issue:` get no row; they are counted on a line after the summary (`41 note(s) not ready`). Rows are printed like every [`doctor <capability>`](/holocron/commands/doctor/), then `N ok, N fail, N skipped`. Exit code 1 if any row fails.
- **No second issue for the same note.** Before it creates an issue, it looks through the tracker's 100 most recently updated issues (`Issues.search`) for the note's marker. If one carries it, nothing is created: that issue's key is written into the note and the row reads `already filed as <key>`. If the look itself fails, the notes get a failing row and nothing is created. An issue older than the 100 most recent is not found, so a very old unfinished filing can still be filed again.
- **Asks first** unless `--dry-run` or `--yes`. Without a terminal it refuses to run without one of them.
- **`--dry-run`** reads the notes and prints `would file "<title>"`. It writes nothing and loads only the `ideas` provider, never the `issues` one.
- **Never deletes.** A filed note stays in the folder with `issue:` set; moving it out of the vault belongs to the [Council plugin](/holocron/council/), which runs this command and trashes the note once it has an `issue:`, since the provider has no `retire`.
- **A second run changes nothing**, because `issue:` is now set.
- **A note that cannot be filed is a failing row, not the end of the run.** If the issue was created but the note could not be written, the row says so and gives the key to add by hand; a rerun also finds the issue by its marker and writes the key itself.

The next step, once an idea is a spec candidate, is [`ideas promote`](/holocron/commands/ideas-promote/), which turns the filed issue into a draft spec.

## Options

| Option      | Default | Description                                                    |
| ----------- | ------- | -------------------------------------------------------------- |
| `--dry-run` | `false` | Show what would be filed, without creating or writing anything |
| `--yes`     | `false` | File without asking (required without a terminal)              |

## Tokens

The `issues` provider reads its token through the usual chain (`--token`, the environment, `.env`, the `credentials` providers, the keyring). The `ideas` provider needs no token. The command needs the plugin packages (`@theholocron/holocron-plugin-obsidian` and the `issues` provider's) to resolve, as every command that calls a provider does.
