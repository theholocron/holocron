`@theholocron/comlink` is Holocron's alert relay: one Cloudflare Worker that takes webhooks from services whose alerts Discord cannot read, checks who sent them, and posts them to a channel as Discord messages.

It exists because Sentry's free plan has no Discord integration and what an internal integration sends is Sentry's own JSON. Other services that post a webhook in their own shape can use the same Worker.

:::note
Comlink is a **private app, deployed rather than published**. It is not on npm, so there is nothing to `pnpm add`. The build produces a single Worker module that `holocron setup notifications` uploads.
:::

## How it fits

Sentinel watches the repositories. Comlink carries the alerts. It is deployed as part of the [server as code](/holocron/server-as-code/) flow: a channel declared with `feeds: { errors: true }` and a layout `relay` gets a dedicated Discord webhook, a DNS record pointing at the Worker, and the Worker itself, all through `holocron setup notifications`.

## How it works

There is one route per source, `https://comlink.theholocron.dev/<source>`.

1. The path picks the source (`/sentry`). An unknown path is a 404.
2. A body over 256 KB is refused (413) before it is hashed. The source verifies the request with its bound secret before anything in the body is trusted (401 if not).
3. The source formats the delivery as a Discord embed with pings turned off. It can also say it does not carry the delivery (202, acknowledged and dropped so the service does not retry), or that it cannot read one it should carry (422).
4. The message is posted to the source's own webhook (502 if Discord refuses, fails or takes over 8 seconds, 500 if none is bound).

| Source   | Path      | Verified by                                                                  | Carries                      |
| -------- | --------- | ---------------------------------------------------------------------------- | ---------------------------- |
| `sentry` | `/sentry` | `Sentry-Hook-Signature`: hex HMAC-SHA256 of the body under the client secret | issue alerts (`event_alert`) |

## Relaying more Sentry projects

`relay.errors.projects` in the layout is the list of Sentry projects whose issues are sent. Add a project's slug to it and run the two commands again:

```ts
relay: { host: "comlink.theholocron.dev", errors: { projects: ["holocron-cli", "sentinel"] } },
```

```bash
holocron setup notifications      # attaches the one alert rule to each listed project's issue stream
holocron doctor notifications     # one problem line per listed project that has no rule, a disabled one, or one that does not send through the integration
```

`setup` is idempotent: it adds a newly listed project to the rule it already made and leaves the rest alone, and it stops before changing anything if a listed project does not exist in the Sentry organisation. It never detaches a project that is no longer listed.

## The Project field

Sentry's `event_alert` payload carries the project only as a number (`data.event.project`), which the embed leaves out. The Project field is taken from the event's API address instead, `data.event.url` (`.../api/0/projects/<org>/<project>/events/<id>/`), which names the project by slug. It is read only after the signature has been verified, and nothing is looked up, so the Worker needs no Sentry token.

## Secrets

Each source has two bindings, never echoed: `COMLINK_<SOURCE>_SECRET` and `COMLINK_<SOURCE>_WEBHOOK`.

- The signing secret is kept in the `prod` layer of the 1Password Environments (`theholocron/holocron - prod`, beside Sentinel's values) and pushed to the Worker with `holocron sync secrets --env prod --cwd apps/comlink --worker comlink`. With `relay.errors` configured, `holocron setup notifications` creates the Sentry integration and alert rule itself and deploys the Worker with the integration's secret.
- The webhook URL is not kept in the Environment. `holocron setup notifications` creates each channel's webhook and sets its URL on the Worker directly, so run `setup` before `sync secrets`.

See [`sync secrets`](/holocron/commands/sync-secrets/) and [`setup notifications`](/holocron/commands/setup-notifications/). `holocron probe comlink deliver` reads the signing secret from the config's vault (or from `COMLINK_SENTRY_SECRET` in the environment) to exercise delivery.

## Adding a source

A source is one file under `src/sources/<id>/` implementing `Source` (`verify` and `format`), plus one entry in the list in `src/worker.ts`. Nothing else changes.

## Sending a delivery by hand

`apps/comlink/postman/` holds a Postman collection and an environment for a Worker run locally, with `COMLINK_SENTRY_SECRET` set to the environment's `sentrySecret` (an empty secret-type variable) and `COMLINK_SENTRY_WEBHOOK` set to a throwaway Discord webhook. A pre-request script signs each body as `Sentry-Hook-Signature`.

| Folder                     | What it sends                                                               | What the relay does                   |
| -------------------------- | --------------------------------------------------------------------------- | ------------------------------------- |
| `Rejected`                 | a GET, an unknown source, a POST with no signature, a POST with a wrong one | 405, 404, 401, 401; nothing is posted |
| `Signed, nothing posted`   | a resource the source does not carry, an `event_alert` with no event        | 202, 422                              |
| `Signed, posts to Discord` | an `event_alert`                                                            | posts an embed, pings off             |

`holocron probe comlink deliver` sends the signed delivery from the command line.

`holocron setup --cwd apps/comlink` pushes the collection and the environment through the [Postman plugin](/holocron/plugins/postman/) into the `Holocron` workspace (made when missing; one collection per app). The environment keeps a `sentrySecret` you set in Postman. The plugin reads `HOLOCRON_POSTMAN_TOKEN`; add `--dry-run` to see the steps first.

## Build and deploy

```bash
pnpm --filter @theholocron/comlink build
```

This writes `dist/worker.js`, a single ES module with no imports, which is uploaded as it stands. Deployment is `holocron setup notifications`'s job, through the `workers` capability.
