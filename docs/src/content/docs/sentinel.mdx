`@theholocron/sentinel` is Holocron's GitHub App: a webhook receiver that validates a repo's `holocron.config.ts` on its default branch, syncs the resolved capabilities to GitHub custom properties, and posts check runs. It watches, validates and reports.

:::note
Sentinel is a **private app, deployed rather than published**. It is not on npm, so there is nothing to `pnpm add`. It is deployed as its own product, with its own `holocron.config.ts` separate from the monorepo root's.
:::

## How it fits

Sentinel reads the same configuration the [CLI](/holocron/cli/) acts on, so a repo is checked centrally by the rules it runs locally:

- [`@theholocron/datapad`](/holocron/datapad/) executes the `holocron.config.*` fetched from GitHub (as content, not a local file).
- [`@theholocron/astromech`](/holocron/astromech/) supplies the task registry that config is validated against, the merge of `astromech.config.*` over `holocron.config.*`, and the lint ignore lists.
- `@theholocron/cli` supplies the derivations behind the custom properties and the compliance baseline, imported unchanged so a check and `holocron sync` can never disagree.
- `@theholocron/github-client` does every GitHub call, including webhook signature verification.

## What it does

| Piece                                | Job                                                                                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parseWebhookEvent`                  | Verifies the `X-Hub-Signature-256` signature and normalizes the delivery. Handles installation events, pushes to the default branch and PR opened or synchronized               |
| `validateConfig`                     | Reads `holocron.config.*` (and an optional `astromech.config.*`) and checks every task name against the registry. Returns `valid`, `no-config`, `unknown-tasks` or `load-error` |
| `syncPropertiesFromConfig`           | Syncs the resolved capabilities and profile to GitHub custom properties, the same fields `holocron sync` computes                                                               |
| `postCheckRun`                       | Posts one capability-compliance check run, `sentinel:validate:config / Run Holocron config compatibility`                                                                       |
| `handleWebhookRequest(request, env)` | A plain `(Request, Env) => Response` function that runs the pipeline above plus the central source-quality checks                                                               |

The central checks run in the same pipeline: commit standards, DCO, inclusive language, formatting, editorconfig, markdown lint, static analysis (eslint and actionlint), repo validation, and an advisory PR config validation. The advisory docs-presence check runs the same shared rules as `holocron probe docs presence`: it warns about a new public package, or a `feat` to one, that ships without a docs change, unless `[skip docs] <reason>` is in the PR description or a commit message, and it re-runs when the PR title or description is edited. An opt-out auto-fix commit can repair the mechanical formatting, editorconfig and markdown failures. The handler's module docstring in `src/handler/handler.ts` is the source of truth for the current list.

Every check Sentinel posts is named `sentinel:<task id> / <Action>`, for example `sentinel:lint:code / Run eslint` or `sentinel:validate:specs / Validate ADRs and specs`. The task id is lowercase, as in the Actions checks, and the action starts with `Run` or `Validate`. The `sentinel:` prefix is temporary: the Actions checks of the same task ids still run, and the prefix keeps the two apart (and keeps Sentinel's checks out of the `ci / Required checks` aggregate). When the Actions checks are removed, `SENTINEL_CHECK_PREFIX` is set to an empty string and the rulesets that require a Sentinel check are pointed at the new names. See `ci-sentinel-check-names`.

## Role sync

Sentinel also keeps Discord roles equal to GitHub teams, so nobody has to run [`holocron sync roles`](/holocron/commands/sync-roles/). It acts on two org-level deliveries: a person added to or removed from a team (`membership`), and a member removed from the org (`organization`). A team delivery syncs the roles that follow that team; an org delivery syncs every role that follows a team. It runs the same `syncRoles()` function as the command, so what counts as in sync, and that a holder nobody has linked is never removed, are identical.

It is off until three settings exist in Sentinel's environment:

| Setting                      | What it is                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| `SENTINEL_ROLE_SYNC_REPO`    | `owner/repo` whose default-branch `holocron.config.ts` declares the Discord layout (its `roles[].team`) |
| `HOLOCRON_DISCORD_BOT_TOKEN` | The Holonet bot token                                                                                   |
| `HOLOCRON_USER_SYNC_TOKEN`   | The `github.user-sync` token that reads the links file in the org's private config repo                 |

The GitHub App also needs the organization permission Members: read and the `membership` and `organization` events. A sync that fails or only partly works answers HTTP 500 and logs an error, so the delivery shows as failed in the App's "Recent deliveries" and can be redelivered (the sync is idempotent). Design: `.notes/tech-sentinel-role-sync.spec.md`.

## Key points

- **Default branch only.** The config is read from a repo's default branch, never a fork or an unreviewed PR branch, and `validateConfig` only validates and never writes. This is the hard security boundary of the design. The exception is the auto-fix check, which reads a same-repo PR branch to see what that branch declares.
- **Org-portable.** The repo and installation id come from the webhook payload, so one registration handles any number of orgs and accounts.
- **Quiet on a bad config.** A missing or broken config is acknowledged without a check run.
- **Out of scope for v1.** Autonomous fix PRs or comments triggered by an event, and dashboards, are tracked in issue 674.
- **Environment.** `SENTINEL_GITHUB_APP_ID`, `SENTINEL_GITHUB_APP_PRIVATE_KEY` and `SENTINEL_WEBHOOK_SECRET` (a deployment that still has the bare `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` keeps working: the `SENTINEL_` name is read first, then the bare one), plus two log-shipping values (`SENTINEL_AXIOM_INGEST_TOKEN`, `SENTINEL_AXIOM_DATASET`), and the three optional role-sync settings above. They live in the `prod` layer of the 1Password Environments (`theholocron/holocron - prod`) and are fanned out with [`holocron sync secrets`](/holocron/commands/sync-secrets/).

## Deployment

Sentinel runs as a serverless function: it needs a real filesystem and dynamic `import()` to execute a fetched config, which Workers-style isolates do not offer. Its own config wires the `deployment`, `dns` and `vault` providers (Vercel, Cloudflare and 1Password today). A Netlify deploy target is the subject of the `tech-sentinel-deploy-target-netlify` wiki spec, and the [Netlify plugin](/holocron/plugins/netlify/) was built for it.

```bash
# Recurring: build, stage, deploy to production
pnpm run deploy

# One time: attach the custom domain and hand the DNS challenge to the dns provider
holocron setup --cwd apps/sentinel
```

- **A development instance.** `pnpm dev` in `apps/sentinel` ([`holocron dev`](/holocron/commands/dev/)) runs the same handler locally, with a second GitHub App and its own secrets (the `dev` layer, `theholocron/holocron - dev`) behind a named tunnel (`holocron new tunnel`); the Sentinel README has the steps. Production stays the only deployment.
- **Production only.** A GitHub App has a single webhook URL, so there is no staging deployment. `holocron deploy --dry-run` verifies the wiring, and the unit tests exercise the handler directly.
- **Automated.** A workflow deploys on merges to `main` that touch the app, and a `deploy` task with `on: "release"` deploys it after a release that changes it (see [`holocron deploy`](/holocron/commands/deploy/)).
- **Secrets.** `holocron sync secrets prod --cwd apps/sentinel` syncs the 1Password Environment of the `prod` layer to the deployment. It targets production only, deliberately, so the app's private key is never exposed to PR preview deployments. The sync writes nothing to repository Actions secrets here (an Environment with no `repo.secrets.sync` entry is refused unless `--github-secret` names the destination, #2104). GitHub refuses names that start with `GITHUB_`, which is why the App's id and key are `SENTINEL_GITHUB_APP_ID` and `SENTINEL_GITHUB_APP_PRIVATE_KEY`. An Environment that still holds the old bare names has them reported as skipped (`invalid name`) rather than failing with a 422; they are read by the deployed app from Vercel, not by Actions, so nothing is lost. Pass `--github-secret SENTINEL_AXIOM_INGEST_TOKEN` (as the Sentinel Secrets Sync workflow does) to keep the other keys out of GitHub as well.

## GitHub App registration

Registering the App is a one-time, manual web-UI flow, done under the org. Deploy first and attach the custom domain, then register with `https://sentinel.theholocron.dev/api/webhook` as the webhook URL.

| Setting                | Value                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------- |
| Repository permissions | Contents, Checks, Custom properties, Issues, Pull requests and Actions at write; Metadata at read |
| Subscribed events      | `push`, `pull_request`, `installation`                                                            |
| User authorization     | Not used. Sentinel only uses installation access tokens                                           |
| Webhook secret         | Generated by you, stored as `SENTINEL_WEBHOOK_SECRET`                                             |
| Private key            | Generated once after creation, stored as `SENTINEL_GITHUB_APP_PRIVATE_KEY`                        |

The package README on [GitHub](https://github.com/theholocron/holocron/tree/alpha/apps/sentinel) has the full permission rationale and the registration walkthrough. The design is in the `tech-sentinel-v1` and `tech-sentinel-ci-runner` wiki specs.
