## Config

```ts
providers: {
  issues: ["linear", {
    // Required: the key of the team the issues and boards belong to
    team: "ENG",
    // Optional: the states the inProgress and inReview slots move an issue to.
    // Left out, the team's first "started" state (and a started state named like "review") is used.
    states: { inProgress: "In Progress", inReview: "In Review" },
    // Optional, for `holocron provider linear setup` and `doctor` (names only, no secrets):
    labels: ["bug", "enhancement", "chore"], // made on the team when missing
    project: "Roadmap", //                      made when missing
    automation: {
      autoClose: { months: 3, state: "Canceled" }, // team autoClosePeriod / autoCloseState
      autoArchive: { months: 6 }, //                  team autoArchivePeriod
    },
  }],
  projects: ["linear", { team: "ENG" }],
}
```

## Authentication

Create a personal API key at **Linear → Settings → Account → Security → API keys**, then:

```bash
holocron auth set linear <KEY>
```

or set `HOLOCRON_LINEAR_TOKEN` (or `LINEAR_API_KEY`).

### What permissions the key needs

A personal API key lets you pick its permissions (Read, Write, Admin, Create issues, Create comments) and the teams it can reach. Do not give it more than the command in front of you needs, and limit it to the team you use.

| Key                       | Permissions                          | Team access  | Use it for                                                                                                  | Keep it                                                  |
| ------------------------- | ------------------------------------ | ------------ | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **Everyday key**          | Read, Write                          | the one team | `migrate`, the doctor, and `provider linear setup` steps that make labels and a project                     | in the keyring (`holocron auth set linear <KEY>`)        |
| **Setup key** (one-off)   | Read, Write, Admin                   | the one team | `provider linear setup` steps that change team settings: auto-close, auto-archive, git automation, statuses | for one command (`--token <KEY>`), then revoke it        |
| **Narrowest key** (a try) | Read, Create issues, Create comments | the one team | copying issues and their comments only                                                                      | untested: labels, relations and projects will be refused |

Linear does not say which permission covers each call, so the table is what we ask for, not a guarantee. What we know from the calls the client makes: issues, comments and attachments map to the two "create" permissions; labels, relations, projects and workflow states are most likely `Write`; team settings are most likely `Admin`. A key also cannot do more than your own role in the workspace allows, so `Admin` needs a workspace admin. If a step is refused, the doctor row for it says so. Raise the key by one permission and run it again.

## How Linear maps onto the capabilities

| Holocron                | Linear                                                                  |
| ----------------------- | ----------------------------------------------------------------------- |
| issue key               | `ENG-42` (a bare `42` or `#42` takes the team key)                      |
| lifecycle `inProgress`  | the `states.inProgress` state, else the first `started` state           |
| lifecycle `inReview`    | the `states.inReview` state, else a `started` state named like "review" |
| lifecycle `done`        | the first `completed` state                                             |
| `create({ milestone })` | a Linear **project**, by id or name                                     |
| board (`projects`)      | a Linear project of the team                                            |
| board status            | one of the **team's** workflow states                                   |
| board `Priority` field  | Linear's built-in priority (Urgent, High, Medium, Low)                  |
| board rules             | the team's auto-archive and auto-close settings (read-only)             |

## Differences from GitHub

Linear does not need to match GitHub feature for feature. Keep this table in mind when moving **back** to GitHub.

| Thing                 | GitHub                                    | Linear                                                                     |
| --------------------- | ----------------------------------------- | -------------------------------------------------------------------------- |
| Priority              | a project field (the repo uses `P0`…`P3`) | built into every issue; migrates as a `priority: <level>` label on GitHub  |
| Statuses              | per project (`Status` field)              | per **team**, shared by every project; `ensure` adds, never removes        |
| Custom fields         | yes (single select, number, date, …)      | none; a template's extra fields come back as `todos`                       |
| Views                 | managed by `project setup`                | not managed; a template's views come back as `todos`                       |
| Automation            | project workflows (read, report)          | team auto-archive / auto-close (read); turning one on is a `todo`          |
| Milestone             | milestone                                 | project (`create` and `migrate --milestone` use a project's name)          |
| Backdating            | no                                        | yes, so a migrated issue keeps its created date                            |
| Parent and blocked-by | read through GraphQL                      | native; **not set** when importing into GitHub                             |
| Assignee              | a login                                   | matched by email on import; unmatched assignees are dropped                |
| Comment author        | the commenter                             | comments are posted by the token's user, with the author named in the text |
| Move between boards   | rewrites the project item                 | an issue is in one project, so `project move` changes its project          |

## Setup and doctor

`holocron provider linear setup` makes what the block above declares, and `holocron provider linear doctor` compares it with the team, one row per setting. See [provider](/holocron/commands/provider/) for the rules both follow (idempotent, never deletes, `--dry-run`, asks first unless `--yes`).

| Step             | What setup does                                                                                                                                                                                                                                                                                             | What the doctor checks                                                         |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `labels`         | `issueLabelCreate` on the team for each missing name, in GitHub's colour when `CANONICAL_LABELS` has the name. An existing label (any case) is left alone                                                                                                                                                   | each name is present on the team or workspace                                  |
| `project`        | makes the project, for the team, when no open project of the team has the name                                                                                                                                                                                                                              | an open project of the team has the name                                       |
| `autoClose`      | `teamUpdate` of `autoClosePeriod` (months; `0` sends `null`, which the schema calls disabled) and, when `state` is given, `autoCloseState`; a state the team lacks fails the row                                                                                                                            | the team's period and state equal the declaration                              |
| `autoArchive`    | `teamUpdate` of `autoArchivePeriod`                                                                                                                                                                                                                                                                         | the team's period equals the declaration                                       |
| `automation.git` | for each `{ event, state, branch? }`: `gitAutomationStateCreate` (a `gitAutomationTargetBranchCreate` first for a named `branch`, reused when a rule already names it), or `gitAutomationStateUpdate` when the rule for that event and branch points at another state; a state the team lacks fails the row | a rule for the event (and exact branch) exists and moves to the declared state |
| `templates`      | not applied: each `{ name, file }` is validated and reported as a skipped row                                                                                                                                                                                                                               | not compared (skipped)                                                         |

A wrong shape is a `ConfigError` naming the path (`providers.issues.automation.autoClose.months must be a non-negative integer`). Changing team settings needs a key with admin access to the team; a refused write is a failing row, and the rest of the steps still run. The team's missing **statuses** are not part of this command: [`project setup`](/holocron/commands/project/) adds them from the board template, and `doctor project` reports a board rule (auto-archive, auto-close) that is off.

The Linear side of GitHub's project workflows (what moves an issue on its own) is therefore: auto-close and auto-archive, and Linear's git automation (`event` is one of `draft`, `review`, `start`, `mergeable`, `merge`, Linear's own names). A rule is found by its event and its target branch, so one made by hand is adopted and only its state is compared; `branch` is an exact branch name (a regular-expression target in Linear never matches it), and a rule the block does not declare is never touched. A target branch that exists with no rule cannot be listed through the API, so making a rule for it fails the row (a name conflict) until a rule for it exists; delete the branch in Linear or make one rule for it by hand.

Issue templates are the one declared thing that is not applied. Linear's schema documents a template's `templateData` only as a JSON string of pre-filled attributes, with no shape for an issue, and the template's markdown (`content`) is read-only, so neither writing a template from `.holocron/linear/*.md` nor comparing it with the team can be done with certainty. Each run reports the declaration as a skipped row; make the template in Linear: **Settings → Templates**. GitHub's workflows cannot be created from the API, so that side stays a `todo` in `doctor project`.

### Without a config entry

A repo that keeps GitHub as its `issues` and `projects` provider can still run Linear's setup and doctor: give the options on the command line instead of in `holocron.config`. Put the block in a file (no secrets):

```json
{
  "team": "ENG",
  "labels": ["bug", "enhancement"],
  "project": "Roadmap",
  "automation": { "autoClose": { "months": 3 } }
}
```

Save it as `linear-trial.json` and run:

```bash
holocron provider linear doctor --with linear-trial.json
holocron provider linear setup --with linear-trial.json --dry-run
holocron provider linear setup --with linear-trial.json --with team=OPS --token linear=<ADMIN_KEY> --yes
```

The config file is not touched. See [provider](/holocron/commands/provider/) for how `--with` combines with a config entry.

## Migrating

`holocron migrate` moves issues between any two providers that have `export` and `import` — GitHub and Linear today. See [migrate](/holocron/commands/migrate/). Every run, dry or not, ends by listing what the target could not carry.
