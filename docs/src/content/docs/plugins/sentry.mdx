## Self-contained activation

The Sentry plugin activates automatically at runtime when `HOLOCRON_SENTRY_DSN`
(fallback: `SENTRY_DSN`) is present in the environment — no provider entry in
`holocron.config` is required for the CLI to route errors to Sentry.

The `errors` provider entry is used by `holocron setup` — it calls
`ensureProject` and pushes the DSN at repo scope via the `secrets` capability
— and by `holocron doctor` (connectivity). Once setup has run, the env var
alone is sufficient.

`SENTRY_DSN` is pushed for any repo with the `errors` provider.
`NEXT_PUBLIC_SENTRY_DSN` (the same DSN, which the Sentry Next.js SDK reads for
browser code) is pushed only when Next.js is detected: the root `package.json`
or any workspace package's lists `next` in `dependencies` or `devDependencies`.
A DSN is built to be embedded in client code, so it is not a true secret.
Setup never removes `NEXT_PUBLIC_SENTRY_DSN`: a repo that drops Next.js deletes that secret by hand.
In this repo it is synced as the organization Actions variable `HOLOCRON_SENTRY_DSN` (from the 1Password
Environment `theholocron/holocron - ci`), which the CLI's telemetry reads before `SENTRY_DSN`; `setup`
still pushes `SENTRY_DSN` as a repo secret, the name consumer repos' SDKs read.

```bash
# Sentry activates in any environment where this is set
export SENTRY_DSN=https://...@sentry.io/...
```

## Config

The provider entry is optional at runtime but required if you want `holocron setup`
to provision the project for you:

```ts
providers: {
  errors: ["sentry", {
    // Required for setup: your Sentry organization slug
    org: "my-org",
  }],
}
```

## Authentication

1. Go to [sentry.io/settings/account/api/auth-tokens/](https://sentry.io/settings/account/api/auth-tokens/)
2. Click **Create New Token**
3. Enable scopes: **project:read**, **project:write**, **org:read**
4. Click **Create Token** and copy it

For CI, prefer an org-level token: **Settings → [Your Org] → Developer Settings → Auth Tokens**.

```bash
holocron new token sentry <TOKEN>
```

Or via env var:

```bash
export HOLOCRON_SENTRY_TOKEN=<TOKEN>
# Also recognized:
export SENTRY_AUTH_TOKEN=<TOKEN>
```

Check what a token can read with `holocron probe sentry token` (organizations, projects, alert rules); `--environment ci` or `dev` also judges it against [what each Sentry token needs](/holocron/tokens/#what-each-sentry-token-needs), for each declared token the Environment holds. See [`probe`](/holocron/commands/probe/#sentry).

## What `errors` provides

- `describe()` — returns the provider name, the env var keys always needed (`envKeys`: `SENTRY_DSN`) and, per framework, the extra keys needed only there (`frameworkEnvKeys`: `next` adds `NEXT_PUBLIC_SENTRY_DSN`)
- `whoami()` — verifies the token by fetching the organization
- `ensureProject(input)` — create or retrieve a Sentry project, returning its DSN and whether it already existed
- `ensureRelay(input)` — make the integration and the one alert rule that sends the issues of every project in `input.projects` to the Comlink relay (see [Server as Code](/holocron/server-as-code/) and [Comlink](/holocron/comlink/) for adding a project)
- `inspectRelay(input)` — read the integration and the rule back without changing anything, for `holocron doctor notifications`: whether the integration posts to the relay and is offered as an alert action, and for each project whether the rule is on it, enabled and sending through the integration. The integration's signing secret is not read.

## Example

```ts
import { createPlugin } from "@theholocron/holocron-plugin-sentry";

const plugin = createPlugin({
  token: process.env.HOLOCRON_SENTRY_TOKEN,
  org: "my-org",
});
const errors = plugin.capabilities.errors();

const { dsn, alreadyExists } = await errors.ensureProject({
  name: "my-app",
  platform: "node",
});
console.log(`DSN: ${dsn} (${alreadyExists ? "existing" : "created"})`);
```
