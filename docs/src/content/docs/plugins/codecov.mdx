`coverage` is a provider-neutral capability for the service that holds a repository's coverage, so another service could implement it. `checkToken()` asks whether the service accepts the configured token for the repository. `checkRepo()` compares the flags and components the config declares with the ones the service has. Required statuses are not compared yet, and there is no `doctor coverage`; `holocron probe codecov repo` is the way to run the comparison.

:::note
The organization's `holocron_capabilities` property must allow `coverage` (`holocron apply properties`) before a repo declares `providers.coverage`. Until then the plugin is not loaded by any config; `holocron probe codecov token` needs it to be named under `providers.coverage`.
:::

## Config

```ts
providers: {
  coverage: "codecov",
}
```

The repository is the one the CLI is operating on (`owner/name`), or the active org with a bare repo name. Set it explicitly when the checkout does not match Codecov:

```ts
providers: {
  coverage: ["codecov", { owner: "theholocron", repo: "holocron", service: "github" }],
}
```

| Option    | Default                         | Description                                                                        |
| --------- | ------------------------------- | ---------------------------------------------------------------------------------- |
| `service` | `github`                        | The git service Codecov knows the owner by (`github`, `gitlab`, `bitbucket`, ...). |
| `owner`   | the active repo's owner, or org | The user or organization.                                                          |
| `repo`    | the active repo                 | The repository name, or `owner/name`.                                              |

## Authentication

```text
--token flag
→ HOLOCRON_CODECOV_UPLOAD_TOKEN (env var)
→ CODECOV_TOKEN (Codecov's own variable — vendor fallback)
→ keyring "codecov.upload.<org>" (org-namespaced)
→ keyring "codecov.upload" (unnamespaced fallback)
```

That is the repository upload token, held in the `ci` layer's Environment and synced to an organization secret (`measure:bundle` reads it). Only `ci` is declared for it, so a copy in another layer fails `holocron doctor tokens`.

A second, optional token reads flags and components: `HOLOCRON_CODECOV_API_TOKEN` (a Codecov personal API token), read from `HOLOCRON_CODECOV_API_TOKEN`, then the keyring entry `codecov.api` (`--token` is the upload token and is not used for it). There is no fallback to the upload token, which the REST API answers with a 401. It is declared for `dev` and `ci` and is optional, so a layer without it is not a failure. It is held in 1Password only: it is not in `repo.secrets.sync`, so it is never copied to GitHub, and no workflow reads it; `holocron doctor secrets` does not report it as `extra`: the plugin lists it as an optional token, and this repo also names it in `doctor.manualSecrets`.

## Two kinds of Codecov token

This is what the Codecov REST API documentation says, and what the plugin does about it:

| Token                       | What it is for                                         | Accepted by the REST API (`api.codecov.io/api/v2`)?                                                    |
| --------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| API token (personal)        | Reading the API: repos, flags, components, commits     | Yes, as `Authorization: Bearer <token>`. Created in the account's Access settings                      |
| Repository **upload** token | Uploading coverage and bundle stats (`measure:bundle`) | Not documented. The API reference describes only the personal token, and the plugin cannot assume more |

`HOLOCRON_CODECOV_UPLOAD_TOKEN` is the repository upload token. Codecov has no read-only endpoint that proves an upload token (the upload endpoints create a commit, which a check must not do). So the probe asks the API for the repository and reports what came back, and does not call a 401 a failure.

## Checking a token

`holocron probe codecov token` reads the repository from Codecov's REST API with the token:

| Codecov answered         | Row                                                                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 200                      | `ok`: it answered for the repository with this token. A public repository answers without a token, so an `info` row says it proves little |
| 401 or 403               | `info`: an upload token cannot be checked this way; a revoked or wrong API token answers the same, so Codecov cannot say which it is      |
| 404                      | `info`: Codecov has no such repository, or the token cannot see it                                                                        |
| a network error or a 5xx | `fail`: it says nothing about access                                                                                                      |

It always ends with an `info` row that permissions are not checked: Codecov has no permission model and reports none. `--environment ci` reads the CI Environment's token and confirms `ci` is a layer that should hold it; `--token codecov=<value>` checks another one. The probe never prints the token. See [what can be checked for Fern, Vercel, Turbo and Codecov](/holocron/tokens/#fern-vercel-turbo-and-codecov).

## What `coverage` provides

- `checkToken()` — asks Codecov for the repository with the token; returns `outcome` (`accepted`, `refused` or `not-found`), `repoPrivate` and `status`, and throws for an error that says nothing about the token.
- `checkRepo({ flags, components })` — reads the repository's flags (`GET /{service}/{owner}/repos/{repo}/flags/`, paginated) and components (`GET /{service}/{owner}/repos/{repo}/components/`) with the API token and returns, for each list, the names expected, those missing on Codecov and those on Codecov the config does not declare. The caller passes the expected names, so the plugin never reads the config. Without `HOLOCRON_CODECOV_API_TOKEN` (or when Codecov answers 401, 403 or 404) it returns `checked: false` with a `reason` naming what to set, and does not throw. Names only, never a token.
- `upload(input)` — optional; uploads coverage reports, one flag per group, with the Codecov CLI. It is what [`holocron upload coverage`](/holocron/commands/upload-coverage/) calls. See below.
- `statusContexts({ components, documentation })` — optional, pure and offline: the commit statuses Codecov posts on a pull request, as `{ name, required }` and sorted. `codecov/patch` and `codecov/project` are always there and required; each component adds an informational `codecov/patch/<component>`; with `documentation` at `warn` or `required` there are also `codecov/patch/documentation` and `codecov/project/documentation`, and only the patch one is required, and only at `required`. The CLI passes the result to the task runner, so which contexts the `ci` aggregate polls and the ruleset requires is Codecov's to say, not the generators'. No token and no repository are needed.

## Comparing flags and components

`holocron probe codecov repo` compares what `holocron sync` writes to `codecov.yml` (a flag per package, none for `docs`, plus `documentation` when `repoValidation.docsCoverage` is `warn` or `required`; a component per package) with what Codecov has. It reads only.

| Result                                        | Row                                                                                                   |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| a list matches                                | `ok` (`components`, `flags`)                                                                          |
| a component declared but not on Codecov       | `fail`: `codecov.yml` has not reached the default branch, or Codecov has not read it                  |
| a flag declared but not on Codecov            | `info`: Codecov knows a flag only after an upload carried it, so a package with no tests yet has none |
| a flag or component on Codecov, not declared  | `info`: a hand-made or retired name                                                                   |
| no `HOLOCRON_CODECOV_API_TOKEN`, or a 401/403 | `info`, naming the variable to set; never a failure                                                   |

`probe codecov repo --environment ci` (or `dev`, `local`, or an Environment name the config names) reads that Environment in memory, the way the `token` probes do, and checks with its `HOLOCRON_CODECOV_API_TOKEN`. The probe runs once per Codecov token the Environment holds and is told which with `--token-name`: for the API token it asks Codecov with it, and for `HOLOCRON_CODECOV_UPLOAD_TOKEN` it says it does not check that token (`info`). An Environment with no API token gets the same `info` row as before, since the API token is optional. A bare `--token codecov=<value>` is still the upload token, which the REST API does not take, so this probe never uses it and says so; use `--environment`. Without `--environment` the API token is read from `HOLOCRON_CODECOV_API_TOKEN` or the keyring as before. The token is never printed.

```sh
holocron probe codecov repo                    # the API token from the shell or keyring
holocron probe codecov repo --environment ci   # the ci layer's API token
holocron probe codecov repo --environment dev
```

The expected names come from `coverageExpectations()` (exported by `@theholocron/cli`), which calls the same functions the `codecov.yml` generator uses.

## Uploading coverage

`upload()` replaces the shell in `ci/actions/codecov-upload`. It needs no token of its own: it asks the Actions runtime for the job's OIDC token (the job needs `permissions: id-token: write`), a fresh one before every upload, and masks it in the log. In order, it:

- downloads the Codecov CLI and checks the signature of its checksum file with `gpg` (Codecov's published key, imported into a private keyring) and the binary's SHA-256, making it executable only when both hold;
- runs `create-commit` and `create-report`, then one `do-upload` per group; the token reaches the CLI in `CODECOV_TOKEN`, never in argv;
- leaves out a report that names no source file, and uploads each other report as a copy whose relative `SF:` paths start at the repo root (the package is the report's folder less a trailing `coverage`; a report at the repo root is left as it is);
- tries each upload four times, waiting 15 seconds times the attempt between tries.

It returns, per flag, the files uploaded or why a group was skipped or failed, and the number of flags uploaded: names and counts only. Each step is a small function with its own test, and the Codecov CLI is run through an injected `spawnSync`, so the tests start no process. Nothing here has run against the live service from a developer machine: the upload is proven by a real pull request's `codecov/patch`.
