The `op` CLI must be installed separately. Install it from [1password.com/downloads/command-line](https://1password.com/downloads/command-line/) or via Homebrew:

```bash
brew install --cask 1password/tap/1password-cli
```

## Config

```ts
providers: {
  vault: ["1password", {
    // Optional: 1Password vault name where items live. Only `list()` needs it.
    vault: "acme-app",
    // Optional: 1P account UUID (--account flag on every op call)
    account: "ABCDEFGHIJKLMNOPQRSTUVWXYZ",
  }],
}
```

## Authentication

**On laptop:** Sign in via the 1Password desktop app or `op signin`. The plugin uses the active session automatically.

**In CI:** Create a service account token and set it in your workflow:

1. Go to [my.1password.com/developer-tools/service-accounts](https://my.1password.com/developer-tools/service-accounts)
2. Click **New Service Account**, name it (e.g. "CI"), and grant access to the vaults the plugin needs
3. Copy the token (shown once) and store it as a repository secret named `OP_SERVICE_ACCOUNT_TOKEN`

```yaml
env:
  OP_SERVICE_ACCOUNT_TOKEN: ${{ secrets.OP_SERVICE_ACCOUNT_TOKEN }}
```

`holocron new token 1password` does not store a token — it prints the `AUTH_HINT` instead.

## Secret reference format

1Password item references follow the format `op://Vault/Item/field`:

```bash
# Read a secret
op://acme-app/database/password
```

In the `vault` capability this format is used with `vault.read(reference)`.

## Using it for your tokens (`credentials`)

The plugin can also be where the CLI finds its own tokens, ahead of the keyring: one 1Password Environment holds them all and Touch ID asks once per command. With no `environment` option the name is derived from the repo's `origin` remote and the layer (`<org/repo> - local`, then `- dev` on a machine; `- ci`; `- prod`); an `environment` option on the entry, or `credentials.environment` for every provider, names it explicitly and wins. The CLI hands the name to the plugin when it reads, so the plugin never stores it. Creating the Environment is a one-time step by hand; see [Credentials providers](/holocron/tokens/#credentials-providers).

```ts
providers: { credentials: ["1password"] },
```

`holocron doctor credentials` checks the Environment: it exists, holds every variable the configured plugins take, and which spelling of its name matched. It asks `op environment secret list` without `--reveal`, so no value is read.

## Moving an Environment (`export-environment`)

`holocron probe 1password export-environment <environment>` copies one Environment's variables into a private file so you can import them into another Environment, for the renames and merges where the values are held by hand otherwise. `op` cannot write to an Environment, so the last step is the app's import.

```bash
holocron probe 1password export-environment "theholocron/holocron - dev"
holocron probe 1password export-environment dev --only SENTINEL_WEBHOOK_SECRET --only SENTINEL_APP_ID
holocron probe 1password export-environment prod --dry-run
```

The argument is an Environment name or id as `op` takes it, or a layer word (`local`, `dev`, `ci`, `prod`), which is the `<org/repo> - <layer>` Environment of this repository, the same resolution `secrets sync` uses. It is a probe that changes things, so it asks first (`--yes` without a terminal).

| Where you run it            | Where the `NAME=value` lines go                                                                                 |
| --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| A terminal                  | A new `.credentials` file next to the config (mode 0600), which must be ignored by Git. It is never overwritten |
| A pipe                      | stdout. The probe's own rows go to stderr, so they never mix with the lines                                     |
| `--copy`                    | The clipboard, whatever stdout is                                                                               |
| A redirected file (`> out`) | Refused: it would leave plaintext secrets on disk with none of the protections                                  |

With the file, the probe prints where it is, asks you to import it in the 1Password app (Developer, View Environments, the target Environment, Import .env file), and deletes it when you press Enter. It is also deleted if the probe fails or you press Ctrl-C.

**Warning:** until it is deleted, `.credentials` holds the Environment's real secrets in plain text, and a pipe or the clipboard holds them until you clear it.

- `--only NAME` (repeatable) exports only those variables; a name the Environment lacks is an error and nothing is written.
- `--dry-run` reads the Environment and lists the variable names and a count; no value is shown and nothing is written.
- Values are never printed, logged or put in an error. The names and counts are all the output carries.

## What `vault` provides

- `read(reference)` — reads a secret by `op://Vault/Item/field` reference
- `write(reference, value)` — writes a secret value
- `list()` — lists the item titles in the configured vault (needs `vault`)
- `readSecret?(name)` — reads one variable of the Environment named by the plugin's `environment` option, so a caller can ask for a secret by its bare name (the `comlink deliver` probe does). Refuses without that option
- `readEnvironment?(name or id)` — reads every variable of a 1Password Environment, by name or id (supports `holocron secrets sync`). `op environment read` takes only an id, so this goes through `op environment secret list`

There is no `ensureProject` or `ensureEnvironment`: the vault and an Environment are created in the 1Password app, once. There is no `environments()` either, because no `op` command lists Environments.
