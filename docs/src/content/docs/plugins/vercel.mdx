## Config

```ts
providers: {
  deployment: ["vercel", {
    // Optional Vercel team id (required for team-owned projects)
    teamId: "team_xxx",
    // Default framework for new project creates (default: "nextjs")
    defaultFramework: "nextjs",
  }],
}
```

## Authentication

```bash
# Store in keyring
holocron new token vercel v_xxx

# Or via env var
export HOLOCRON_VERCEL_TOKEN=v_xxx
```

Generate a token at [vercel.com/account/tokens](https://vercel.com/account/tokens). Use "Full Account" scope for team operations.

## Checking a token

`holocron probe vercel token` asks who the token belongs to (`/v2/user`) and whether it can list projects, and never prints it. Vercel does not report a token's scope, so the probe says that permissions are not checked. `--environment <layer>` reads that layer's token (`local`, `dev` or `ci`) and confirms the layer should hold it; `--token vercel=<token>` checks another one. See [what can be checked for Fern, Vercel, Turbo and Codecov tokens](/holocron/tokens/#fern-vercel-turbo-and-codecov).

[`holocron doctor tokens`](/holocron/commands/doctor-tokens/) runs the same probe for the `local`, `dev` and `ci` layers, one row each: `ok` when the token is accepted and lists projects, `fail` when Vercel rejects it or the layer is declared to hold it and does not. A repo whose own config deploys elsewhere still gets these rows when a workspace package's config names `vercel` (this repo: Sentinel), with no `providers` key for it in the root config.

## What `deployment` provides

- List and create Vercel projects
- Update project settings (preview deployments, git integration)
- List and set environment variables per target (`development`, `preview`, `production`)
- Trigger deployments from a branch (preview or named environment)
- Poll deployment status
- Make the team webhook for a [Comlink relay source](/holocron/comlink/#the-vercel-source) (`ensureRelaySource`, `inspectRelaySource`)

## Relay source (Comlink)

`relay.sources.vercel` in the notifications layout, with `capability: "deployment"`, makes Vercel post deployment events to the relay, with no dashboard step:

```ts
relay: {
  host: "comlink.theholocron.dev",
  sources: {
    vercel: { capability: "deployment", events: ["deployment.error"], scope: ["prj_abc"] },
  },
},
// and on a channel: feeds: { relay: { vercel: true } }
```

`events` are Vercel's event names and `scope` is a list of project ids (left out, the webhook covers every project). `setup notifications` lists the team's webhooks (`GET /v1/webhooks`), finds the one whose URL is `https://<relay.host>/vercel` and, when there is none, makes it (`POST /v1/webhooks`). Vercel returns the signing secret only in that response, so the secret goes to the Worker as `COMLINK_VERCEL_SECRET` in the same deploy and is never printed. A second run adopts the webhook and changes nothing; the plugin never updates or deletes one (the API reference has no update call), so `doctor notifications` reports a webhook whose events or projects differ and a person fixes it in Team Settings, Webhooks. If the secret is lost (the webhook was made and the Worker deploy then failed), delete the webhook in the dashboard and run `setup notifications` again. Team webhooks need a Pro or Enterprise team: a 402 or 403 is reported as a failing `todo`. The same `HOLOCRON_VERCEL_TOKEN` is used; Vercel tokens have no per-endpoint scopes, so no permission is added and the token probe is unchanged. Not checked against a live Vercel account.

## Example: deploy to production

```bash
holocron deploy main --project-id prj_xxx --target production
```

## Example: sync secrets to Vercel

```bash
# Pull from Doppler "production" config → push to GitHub secrets + Vercel production + preview
holocron sync secrets --env production --project-id prj_xxx
```
