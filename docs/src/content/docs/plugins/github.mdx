## Config

```ts
providers: {
  source: "github",
  ci: "github",
  secrets: "github",
  environments: "github",
  issues: ["github", {
    // Optional: map lifecycle slots to issue label names
    labels: {
      inProgress: "status: in-progress",
      inReview: "status: in-review",
    },
  }],
}
```

### Options

| Option              | Type     | Description                                                                          |
| ------------------- | -------- | ------------------------------------------------------------------------------------ |
| `repo`              | `string` | `"owner/name"` — derived from `repo.name` in config or git remote when absent        |
| `repoRoot`          | `string` | Absolute path to repo root for workflow file operations. Defaults to `process.cwd()` |
| `labels.inProgress` | `string` | Label name to set when transitioning an issue to `inProgress`                        |
| `labels.inReview`   | `string` | Label name to set when transitioning an issue to `inReview`                          |

## Authentication

Requires up to five separate fine-grained PATs depending on which capabilities you configure:

```bash
holocron auth set github.admin   ghp_xxx  # source, secrets, environments
holocron auth set github.read    ghp_yyy  # ci, clone
holocron auth set github.issues  ghp_zzz  # issues
holocron auth set github.sync    ghp_aaa  # sync-github
holocron auth set github.release ghp_bbb  # semantic-release
```

See the [Token Reference](../tokens#github-tokens) for the exact PAT scopes each needs.

## What `source` provides

- Repo settings (squash merge, delete-branch-on-merge, auto-merge)
- Branch rulesets and classic branch protection
- Security toggles (vulnerability alerts, secret scanning, CodeQL, etc.)
- Workflow file read/write (`.github/workflows/`)
- Arbitrary repo file write (`.github/dependabot.yml`, etc.)
- Labels, custom properties, topics, teams, description, homepage sync

## What `issues` provides

- Search by assignee, open-only filter or `text` (title or body, any case)
- Create issues with summary, body, labels, milestone
- Transition issues via label: `inProgress` → sets `labels.inProgress`, `done` → closes
- Add comments
- `doctor()` — lists available labels and validates lifecycle slot mapping

### Searching by text

`search({ text })` returns the issues whose title or body contains the text, compared without regard to case, and
leaves out pull requests. `openOnly`, `assignee` and `limit` (default 50) still apply. It does not use GitHub's
issue search (`GET /search/issues`): that index matches words, so punctuation and a hidden HTML comment such as
`<!-- holocron:idea notes/a.md -->` cannot be relied on to match. It is also limited to 30 requests a minute and is
eventually consistent, so an issue made a moment ago may be missing. Instead the plugin lists the issues, newest
update first, 100 a page, and compares the text itself until it has `limit` matches or the issues run out. It reads
at most 20 pages, the 2000 most recently updated issues, so in a repository larger than that an older match is not
found. Without `text`, `search` makes one request as before.

### Migrating and syncing

`export`, `import` and `sync` let `holocron migrate` and `holocron sync issues` move issues to and from another tracker. A copy carries a `<!-- holocron:migrated-from <url> -->` marker at the end of its body, which is how a later run finds it and how the reverse sync knows to skip it. `sync` updates title, description, state and labels (priority is the `priority: <level>` label) of a copy, keeps its `status:*` labels, and adds the comments it lacks; an assignee is not mapped, because a Linear user is not a GitHub login. A 429, or a 403 that names the rate limit, stops the run with the rest left for the next one. See [sync issues](/holocron/commands/sync-issues/).

## What `projects` provides

GitHub Projects v2 boards over GraphQL, for `holocron project ...`. It uses the org token with the **Projects**
organization permission. Items are keyed `#N` in the configured `repo` and `owner/repo#N` elsewhere.

- `list` / `find`: every project of the organization (open and closed), or the open one with an exact name
- `create`: copies the board a template names as `source` (fields, options, views and automation rules, no items), or
  creates a project and applies the template
- `close`: `updateProjectV2` with `closed: true`, reversible
- `read` / `ensure`: the live board, and adding what the template lists and the board lacks. `ensure` never deletes. It
  sends every existing status option with its `id`, because an option list sent without ids blanks the field on every
  item; it stops if the field cannot be read, and writes values back by name if a re-read shows any gone
- `items` / `setStatus`: each item's status, category, open state and open blockers; an idempotent status change
- `move`: puts open items on another board with status and priority (only where the target has none); closed and merged
  items stay and are set to the done status when theirs is not a done one
- `addItems`: puts issues on a board by node id (`addProjectV2ItemById`) and sets Status and Priority through the single
  select update, only where the item has none; used by `holocron migrate project --to github`. A status or priority with
  no option on the board is reported, never created. Priority matches an option named `urgent`, `high`, `medium`, `low`
  or `P0` to `P3`
- Automation rules cannot be created or switched on through the API, nor can a view's grouping; `ensure` returns them
  as `todos`

## Webhook events

The plugin exports a `parseWebhook` function for normalizing GitHub webhook payloads into `AuthEvent` shapes (for repos using GitHub as a lightweight auth event source):

```ts
import { parseWebhook } from "@theholocron/holocron-plugin-github";

const event = await parseWebhook({
  body: req.body,
  headers: req.headers,
  signingSecret: process.env.GITHUB_WEBHOOK_SECRET!,
});
// event.type: "user.created" | "user.updated" | "user.deleted"
// event.user: NormalizedAuthUser
```
